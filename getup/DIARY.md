## 報酬関数の一覧（学習で使う報酬、2026-10-16 時点）

起き上がりの学習（getup-v1〜v4）で使う報酬の項。式はコードのまま（`envs/getup_env{1,2,3}.py` の `_reward_<名前>`。3 つの版で式は同じで、
v3 から `action_smoothness2` が増えた）。重みの出所は各版の `train_getup{1,2,3,4}.py` の `get_cfgs()` の `reward_scales`（v4 は v2 の値に `--add` で足す）。
計画書 §4.4 の設計（ねらい・予想されるハックと対策）もあわせて見ること。

### 共通の記号

| 記号 | 意味 |
|---|---|
| `u` | 重力の向き（base 座標）の x 成分。胸が床の方を向いている度合い。四脚の姿勢・平らなうつ伏せで +1、横向き 0、仰向け −1、二足の直立 0 |
| `ĥ_腰`・`ĥ_胸` | 高さを 0〜1 にしたもの: `clip((h − h_prone)/(h* − h_prone), 0, 1)`。h* は四脚の公称姿勢（腰 0.1932 m・胸 0.1937 m）、h_prone はうつ伏せ（u0 ≥ 0.9）の中央値（腰 0.0858 m・胸 0.0814 m）。値は初期状態バンク `bank_v1.pt` の meta |
| `q`・`q*` | 関節角（22 軸）・四脚の公称姿勢（歩行 v31 の初期姿勢） |
| `h_腰` | 胴体（base_link）の高さ |
| 成功（その瞬間） | §3.2 の条件を今の歩で満たす: `u > 0.966`、全関節 `abs(q − q*) < 0.3 rad`、`h_腰 ≥ 0.175 m`、端以外（下の 13 リンク）が床に触れない、胴体の角速度 < 0.5 rad/s。1 秒続けるのは評価だけ |
| 端以外のリンク | 胴体・胸・頭・左右の肩・上腕・股関節（上下）・大腿の 13 リンク（前腕と足、すね・足首・肘は含まない） |
| `a` | 方策の行動（±1 で切った値。目標角への写像の前） |
| `τ_lim` | トルクの上限＝URDF の effort（1.373 N·m）。v3 と v4 の cap90 でシミュの上限を下げても、ここは仕様の値のまま |

### 報酬の項

報酬は毎歩、各項 × 重み × dt（0.02 秒）の和。下の重みは dt を掛ける前の値。

| 項 | 式 | ねらい |
|---|---|---|
| `height` | `σ((u − 0.7)/0.05) · ½(ĥ_腰 + ĥ_胸)` | 胴体と胸を四脚の高さまで持ち上げる（胸を入れて「お尻だけ上げる」局所解を防ぐ。u で胸が下を向いているときだけ） |
| `upright` | `((u + 1)/2)²` | 胸を床の方へ向ける（うつ伏せは最初から満点。横向き・仰向けからの寝返り用） |
| `pose` | `exp(−mean_j (q_j − q*_j)² / 0.25²) · σ((u − 0.9)/0.03) · clip((h_腰 − 0.15)/0.03, 0, 1)` | 実際の関節角を四脚の公称姿勢に近づける（向きと高さが揃ったときだけ。伏せたまま関節だけ合わせるのを防ぐ） |
| `success` | 成功（その瞬間）なら `exp(−(‖v‖² + 0.1‖ω‖²)/0.05)`、そうでなければ 0（v: 胴体の速度、ω: 角速度、base 座標） | 四脚の姿勢で静止する（跳ねて高さを稼ぐのを防ぐ） |
| `body_ground_contact` | 端以外のリンクの床との接触の数 × 1[h_腰 > 0.12] | 頭や胴体を支点にしない（持ち上がってから） |
| `torque_limits` | `Σ_j clamp(abs(τ_j)/τ_lim − 0.85, 0)²` | 仕様の 85 % を超えるトルクを抑える（歩行は 0.60 から。起き上がりは持ち上げの探索を潰さないよう 0.85） |
| `dof_vel_limits` | `Σ_j clamp(abs(q̇_j) − 6.0, 0)` | 関節速度 6 rad/s 超を抑える |
| `dof_pos_limits` | 可動域の端から 0.03 rad 以内に入った関節の数 | 可動域の端に打ち付けない |
| `action_rate` | `Σ_j (a_t − a_{t−1})²` | 行動の急な変化（震え）を抑える |
| `action_smoothness2` | `Σ_j (a_t − 2a_{t−1} + a_{t−2})²`（2 階差分） | 毎歩の向きの反転（カクつき）を抑える（歩行 v10 以降と同じ形） |

重み（dt を掛ける前の値。版ごと）:

| 項 | v1 | v2 | v3 | v4 |
|---|---|---|---|---|
| `height` | +2.0 | +2.0 | +2.0 | +2.0 |
| `upright` | +1.0 | +1.0 | +1.0 | +1.0 |
| `pose` | +2.0 | +2.0 | +2.0 | +2.0 |
| `success` | +3.0 | +3.0 | +3.0 | +3.0 |
| `body_ground_contact` | −1.0 | −1.0 | −1.0 | −1.0 |
| `torque_limits` | −10 | −10 | −10 | −10 |
| `dof_vel_limits` | −0.5 | −0.5 | −0.5 | −0.5 |
| `dof_pos_limits` | −5.0 | −5.0 | −5.0 | −5.0 |
| `action_rate` | −0.005 | −0.005 | **−0.02** | −0.005（`smooth` は −0.02） |
| `action_smoothness2` | なし | なし | **−0.01** | なし（`smooth` は −0.01） |

- 報酬以外: シミュレーションが破綻した体は、その歩の報酬を **−20**（dt を掛けない）に置き換えてリセット。ほかの打ち切りは無い（転んでも続ける）。
  時間切れ（v1・v2・v4 は 8 秒、v3 は 16 秒）は価値で継ぎ足す（`time_outs`）。生存ボーナスは置かない。
- v1〜v4 で報酬の式は変えていない。変えたのは `action_rate` の重みと `action_smoothness2` の有無だけ（v3、v4 の `smooth`）。
  v4 の `cap90`・`ent0`・`delta03` は報酬を変えない（シミュのトルクの上限・エントロピーの係数・目標角の速さの制限）。
- 計画書 §4.4 は h* を 0.1946 m と書いていたが、コードは初期状態バンクの値（腰 0.1932 m・胸 0.1937 m）を使っていたので、この一覧を作るときに計画書を直した（10/16）。
- 先輩（三宅）の方法の再現（計画書 §4.9 の M0）は、先輩の報酬関数をそのまま使う。先輩のコードは公開の許可がまだ無いので、式はここに載せない
  （項の名前と考え方は `experiments/getup/miyake_code_review.md`、修論 §4.4・§4.5）。

## getup-v1（2026-10-14、実装と GPU の小試験まで。本番の学習はまだ）

### 動機

計画書 §4.8 の最初の版。歩行の再学習キュー（四脚 v1〜v31 の URDF 是正後）が GPU を使っている間に、CPU でできるところまで作る。
GPU の小試験（§4.2-5、200 iter で速さと記憶域を測る）はキューが 88/88 になってから。

### 作ったもの

1. **別名 URDF**（`tools/make_getup_urdf.py`）: 事前検証 1 で、凸包が実形状より最大 17〜38 mm 外側に出ていた 12 リンク
   （胸 2・前腕・太ももの付け根 2 種・すね・足首）を、CoACD で凸な部品に分けた。部品の数は、はみ出しの最大が 5 mm 未満になる
   最小の数をリンクごとに選んだ（3〜8 個、合計 57 個）。はみ出しの最大は 15.8〜37.6 mm → 3.7〜5.2 mm。
   - 足（l/r_foot）は分けない: STL が閉じておらず分解も測定も当てにならない。凸包でも足裏の平面は正しく、歩行で検証済み。
   - 確認（`tools/verify_getup_urdf.py`、`experiments/getup/urdf/verify.json`）: 質量 1.6 kg で同じ、四脚の公称姿勢の高さ 0.1932 m と傾きも同じ。
     v31 はこの URDF でも元と同じに歩く（速さの差 0.003 m/s 以内、傾きの差 0.2° 以内）。衝突形状 25 → 70 個、CPU 64 体で 1 ステップ 10.8 → 12.3 ms。
2. **共通後処理層**（`khr_common/action_post.py`）: 非対称な写像・変化の速さの制限・可動域（§4.3.2）。numpy と torch の両方。自己テストつき。
3. **h_est**（`khr_common/height_est.py`）: URDF から順運動学で、関節角と重力の向きから胴体の高さを求める。
   空中のランダムな姿勢 64 体で、Genesis の衝突形状の最低点との差 0.05 mm 以内（頂点を間引くと最大 2.7 mm 低く出たので、既定は間引かない）。
4. **初期状態バンク**（`gen_init_states.py`）: §4.3.1 の手順。自己めり込み 5 mm 以上を捨てる（捨てたのは主に左右の脚の交差）。
5. **環境 getup-v1**（`envs/getup_env1.py`）と**学習**（`train_getup1.py`）: §4.3〜4.5・§4.7 のとおり。計画書からの変更・具体化:
   - 関節角の観測ノイズは 0.01 rad（歩行は 0.05）。関節速度を観測の差分で作るので、0.05 rad だと ±5 rad/s の雑音になる。
     系統的なずれは「サーボの 0 点のずれ ±0.02 rad（方策から見えない）」として入れた（実際の角度 = 指令 + ずれ、返る角度 = 実際 − ずれ）。
   - IMU の取り付け誤差 0〜3°（体ごとに一定）を v1 から入れた。10/13 の実機歩行で、学習環境とのずれの主因が IMU の取り付け誤差程度の
     一定の傾き（横 +2°・前後 −2〜−3°）だった（`experiments/sysid/README.md`）。
   - 胴体の質量 ±0.08 kg・重心 ±1 cm（§4.6 の案。歩行の −0.1〜+0.5 kg は使わない）。
   - 床との接触は `get_contacts(with_entity=床)`（自己接触を含まない）。「端以外」は胴体・頭・肩・上腕・股関節・太もも（13 リンク）。
   - 成功判定（§3.2）: u > 0.966・全関節が公称から 0.3 rad 以内・角速度 < 0.5 rad/s・胴体高 ≥ 0.175 m・端以外の接地なし、を 1 秒連続。
     報酬の `success` はその瞬間の条件（§4.4）。
   - 観測の正規化あり（rsl-rl の obs_normalization）、actor・critic とも [256,128,64]。

### 動作確認（CPU）

- 観測 184 次元・特権観測 99 次元。**リセット直後の観測は状態から計算した値と完全に一致**（角速度・重力・関節角・関節速度 0・前回目標・履歴）。
- 四脚の公称姿勢では、床に触れるのは 4 端（両前腕・両足）だけ。近傍 L0 から行動 0 で約 1 秒で成功の判定になる。
- `train_getup1 --cpu -B 32 -I 3` で学習ループが回る（報酬・成功率・段階・破綻の割合が記録される）。

### 初期状態バンク bank_v1（`data/banks/bank_v1.pt`、3.3 MB、CPU で 40 分）

- 主 20,000・近傍 4,000（評価用 4,800 は学習に使わない）。採用率 約 55 %。捨てた理由は、空中で自分の体に 5 mm 以上めり込む
  （主に左右の脚の交差）が 33 %、2.5 秒で落ち着かない（|v| ≥ 0.05 m/s か |ω| ≥ 0.2 rad/s）が 12 %、シミュレーションの破綻 0。
- 主の u0: ≥ 0.9（L1）3,775、≥ 0.5（L2）7,966、≥ 0（横向きまで）10,823、< 0（仰向け寄り）9,177。
  半分を「うつ伏せから 60° 以内」で置いても、落ちて転がるので L1 は 19 % しか残らない。
- 高さ: 四脚の公称姿勢で胴体 0.1932 m・胸 0.1937 m、うつ伏せ（u0 ≥ 0.9）の中央値 0.0858 m・0.0814 m（報酬の ĥ の 0 と 1）。
- h_est と真の高さの差: 平均 0.11 mm、最大 2.4 mm（`experiments/getup/height_est_bank.json`）。
- 本番のバンクで CPU の学習ループ（64 体 × 3 iter）が回ることを確認。1 体の接触点の最大 11（上限 750）。

### GPU の小試験（§4.2-5、2026-10-14、`logs/getup1-gputest/`）

`python -m getup.train_getup1 -e getup1-gputest -B 4096 -I 200 --seed 1`（bank_v1、単独実行、13:16〜13:21）。

- **速さ: 54.7 iter/分**（1 iter 1.09 秒 = 収集 0.90 秒 + 更新 0.18 秒、9 万 step/秒）。1500 iter が約 27 分、3000 iter が約 55 分。
  計画書 §4.7 の見積り（3000 iter で 1.1〜2.1 時間）の約半分だった。ただし段階は L0 のままなので、接触の多い L1・L2 では遅くなりうる。
- **GPU メモリ**: torch の確保は最大 502 MiB。Genesis 自身が確保する分は含まない（`nvidia-smi` がドライバの版の食い違いで使えず、測れなかった）。
- **接触点**: 1 体の最大 24（上限 750）。`max_collision_pairs` 150 は十分。破綻 0。
- **学習の進み**: 平均報酬 0.9 → 35.7、エピソードは最初から最後まで 8 秒（転倒で終わる仕組みはない）。std 0.50 → 0.30。

### 見つかった問題: 学習中の成功率が 0 のまま

200 iter のあいだ、TensorBoard の成功率は一度も 0 を超えなかった。成功の報酬（その瞬間の条件）は 0.003 → 0.90 と増えていたので、
判定の作りが壊れているのか、条件は満たすが 1 秒続かないのかを、`tools/check_success.py` で切り分けた
（L0 の初期状態、1024 体、2〜8 秒、`experiments/getup/check_success_getup1-gputest_199_L0.json`）。

| 行動 | 1 秒続けて成功 | 全条件を満たした時間 | 角速度 < 0.5 rad/s の時間 | 続けて満たした最長（中央値） |
|---|---|---|---|---|
| 方策の平均（決定的） | 33 % | 68 % | 82 % | 23 歩 |
| 平均 + 探索のゆらぎ（std 0.30、学習中と同じ） | **0 %** | 47 % | **57 %** | 10 歩 |
| 行動 0（公称姿勢へ） | 79 % | 79 % | 100 % | 389 歩 |

- **判定は正しく動いている**（行動 0 で 79 % 成功。残りの約 2 割は、近傍の姿勢から落としたときに倒れた状態（近傍 N の u0 の 5 % 点は −0.22）で、
  行動 0 では起き上がれない）。
- **学習中の成功率が 0 なのは、探索のゆらぎのせい。** 行動に毎歩 std 0.3 のゆらぎが乗ると、胴体の角速度が 0.5 rad/s を超える時間が増え、
  「全条件を 1 秒（50 歩）続けて満たす」に届かない。
- **影響: カリキュラムが昇格しない。** 昇格（§4.5）は「直近 2000 エピソードの学習中の成功率 ≥ 0.75」で判定しているので、
  std がかなり小さくなるまで L0 から上がれない。1500 iter の本番の前に直す必要がある。
- 200 iter の時点の方策（決定的に 33 %）は、まだ行動 0（79 %）より悪い。学習はまだ始まったばかりで、これ自体は問題ではない。

直し方の候補（どちらにするかは未決定）:

1. **昇格の判定だけ、ゆらぎに左右されない条件にする**: 例えば「エピソードの最後の 1 秒で、u・高さ・関節角・端以外の接地なしを満たしている」
   （角速度を外す）。§3.2 の成功の定義（評価と実機）は変えない。実装が簡単で、学習の時間も増えない。
2. **昇格の判定を、決定的な行動での評価で行う**: 数十 iter ごとに学習を止め、方策の平均で 1 エピソード動かして成功率を測る。
   判定が §3.2 の定義そのものになるが、評価のぶん学習が遅くなる（100 iter ごとなら約 15 %）。

## getup-v1 の本番（seed 1、1500 iter、2026-10-14、`logs/getup1-s1/`）

### 昇格の判定の修正（本番の前、ユーザーが案 1 を選んだ）

- `curriculum.promote_on = "end_hold"`（`promote_hold_s` 1.0）: エピソードの**最後の 1 秒、角速度以外の §3.2 の条件**（u・関節角・胴体高・端以外の接地なし）を
  満たし続けて立っていれば、昇格の判定で合格と数える。§3.2 の成功の定義（評価と実機）は変えない。
  既定は旧来の `"success"` のままなので、小試験（getup1-gputest）の `cfgs.pkl` を読むと前と同じに動く。
- TensorBoard に `stand_end_rate`（最後の 1 秒に立っていた割合）と `stand_end_rate_current_level` を足した。昇格の時刻は `run_info.json` の `promotions`。
- CPU での確認: 行動 0・16 体・3 秒のエピソードで、最後に立っていた割合 81 % → L1 へ昇格した。

### 検証の道具（学習のたびに使う。**検証では毎回動画を撮る**、ユーザーの指示）

- `getup/eval_getup.py`: 評価用の状態（学習に使っていない 4,800 個）のうち、段階ごとの**全状態**を決定的な方策で 8 秒ずつ 1 回動かす。
  条件は「個体差・観測ノイズあり（学習と同じ）」と「公称（なし）」。§3.2 の成功率（Wilson の 95 % 区間）・u0 の区間別・累積成功曲線・最後に立っている率・
  トルク（|τ|/τ_max の 99%点・90 % 以上の時間・100 % に達した関節と時刻）・関節速度・破綻を `experiments/getup/eval/<exp>_<ckpt>.json` に、
  状態ごとの結果（版の比較で対応をとる用）を `_per_state.json` に残す。
- 動画: 段階ごとに 6 エピソード（成功 4・失敗 2 を無作為に）を、評価と**同じ初期状態・同じ個体差**で再生し、体 0 を追うカメラで撮って 1 本にする
  （`media/videos/getup/<exp>_<ckpt>_<段階>.mp4`、字幕に状態の番号・u0・評価と再生の結果・時刻）。
  再生は観測ノイズが変わるので結果が評価と食い違うことがある。今回は 18 本中 15 本が一致（L0 5/6・L1 6/6・L2 4/6）。
  ノイズなしでも同じ状態・同じ個体差の再生は完全には一致せず、60 歩で胴体の位置が最大 4.9 mm ずれた（CPU、原因は未確認）。
- 環境に足したもの: 録画用のカメラ（`camera_res`）、`force_reset`（指定の状態・ヨー・個体差でやり直す）、`dr_snapshot`。学習の動きは変わらない。
- `getup/jobs/train_eval.sh <exp> <seed> <iter>`: whisper の解析が走っていない・次の開始までに終わるときだけ、学習 → 検証（動画つき）を続けて行う。
  同じ名前の学習済みのチェックポイントがあれば止まる。`--eval-only` で検証だけやり直せる。

### 分析

1. **ゲート S（11/1、L2 ≥ 70 %）は seed 1 で満たした。§4.8 の「L1 ≥ 90 %」はわずかに届かない**（87.5 %、95 % 区間の上端 89.6 %）。
2. **失敗の 3 分の 2 は「立っているのに揺れが収まらない」。** L1 で最後の 1 秒に立っている体は 95.8 %、成功は 87.5 %。
   最後の 1 秒は角速度以外の条件を満たしているので、この約 8 pt で成功を妨げたのは角速度（0.5 rad/s 未満を 1 秒保てない）。
   残りの約 4 pt は最後まで立てていない（動画では、崩れた姿勢のまま止まる例）。
3. **方策が「全開か全閉か」の動かし方になっている。** 行動の平均が ±1 の外にある時間が 90 %（CPU、L1 の 256 状態）。行動は ±1 で切るので、
   平均を外に出すと探索のゆらぎが効かなくなり、エントロピーの項で std が罰なしに増え続ける（0.30 → 0.92）。
   同じ 256 状態・同じ個体差で、**決定的な方策 89.5 % に対し、ゆらぎつき 96.1 %**。学習中の成功率（0.97〜0.98）は、決定的な評価（実機と同じ）を過大に見せる。
   2 の揺れも、この全開・全閉の動かし方と関係している可能性が高い（未確認）。
4. **トルクは、どのエピソードでも一度は 100 % に達する**（個体差ありの全段階で、エピソードの 99〜100 %）。最初に達するのは開始から中央値 0.08 秒（4 歩目）。

   目標角は 1 歩 0.06 rad の速さで動くので、床に押さえられて動けない関節はすぐにこのずれを超える。
   段階が上がるほど 99%点が上がる（74 → 91 → 97.5 %）。L2 で 100 % に達する関節の上位は右肘ヨー・頭ヨー・左足首ピッチ・右股関節ピッチ・右肘ピッチ
   （それぞれエピソードの約 93 %）。肘ヨーと頭ヨーは起き上がりに要らない関節で、床に押しつけているだけと考えられる。
   **実機ではトルクを 100 % にしない、という決まりに反する**（計画の getup-v3 の条件は 99%点 < 90 %・90 % 以上の時間 ≈ 0）。実機の前に必ず直す。

### 次（getup-v2 の候補。中身はユーザーと決める）

- **行動の平均を ±1 の中に収める**: ±1 を超えた分（サンプルした行動）に罰を入れるか、エントロピーの係数を下げる・std に上限を置く。
  三宅さんの設定（rl_games）はエントロピーの項 0 と、平均の範囲外の 2 乗を損失に足す bound loss（係数 0.001）を使っていた（`experiments/getup/miyake_code_review.md`）。
  3 の決定的とゆらぎつきの差、2 の揺れ、std の増え続けを同時に狙う。
- **トルク**: 送る目標角を「測った角度 ± 0.05 rad」の中に制限する（`khr_common.action_post` で sim と実機の両方。P の項が上限の 91 % を超えなくなる）か、
  速さの制限を下げる。要らない関節（頭ヨー・肘ヨー）を動かす罰。
- v1 の 3 seed は、v2 の候補と比べる対照として後で回す（単一 seed では結論を出さない）。

## getup-v2（2026-10-14、`envs/getup_env2.py`・`train_getup2.py`・`ppo_bound.py`）

### 動機

getup-v1 の本番で見つかった 2 つの問題を直す（ユーザーが候補 1・2 の両方を選んだ）。比べやすいよう、v1 からの変更はこの 2 つだけにした。

1. 行動の平均が 9 割の時間 ±1 の外にあり（全開か全閉か）、探索のゆらぎが効かないので std が増え続け、決定的な方策がゆらぎつきより 7 pt 低い。
2. 目標角が 1 歩 0.06 rad で先に進み、床に押さえられた関節で目標とのずれが 0.055 rad を超えて、どのエピソードでもトルクが 100 % に達する。

### 変更

1. **行動の平均の範囲外の罰（bound loss）**: `getup/ppo_bound.py` の `PPOBound`。損失に
   `0.01 × Σ_関節 (max(μ − 1, 0)² + min(μ + 1, 0)²)` の平均を足す。rsl-rl の `update()` には項を足す口がないので、
   rsl-rl 5.4.0 の `PPO.update` を写して印（`# getup-v2`）の行だけ足した（5.4.0 以外では import で止まる）。
   三宅さんの rl_games の設定（`bounds_loss_coef` 0.001、境界は ±1 付近）と同じ考え方。こちらは境界を切る値そのもの（±1）にし、
   v1 で平均が外に張り付いていたので確実に効くよう 10 倍の 0.01 にした。TensorBoard の `Loss/bound`・`Loss/mu_outside_frac` で効きを見る。
   CPU の確認: 平均を +3 にずらした方策を 5 iter 学習すると、罰あり 3.01 → 2.95・罰なし 3.01 → 2.99（動く速さは学習率で決まる）。
   エントロピーの係数（0.005）は変えていない。
2. **目標角を観測した関節角 ± 0.05 rad に収める**: `khr_common/action_post.py` の `gap`（既定なし＝v1 は前と同じ、自己テストあり）。
   順番は「写像 → 1 歩 0.06 rad の制限 → 可動域 → 観測した関節角 ± gap → 可動域」。P の項は kp × 0.05 = 1.25 N·m（上限の 91 %）まで。
   使う関節角は方策が観測したもの（観測ノイズ ±0.01 rad を含む。実機ではサーボが返す角度）なので、ずれの最大は 0.06 rad になりうる。
   1 歩の遅れのあいだに関節が動くこと、減衰の項（kd × 関節速度）も上限に効くので、100 % が完全になくなるとは限らない。検証で測る。
   同じ処理を実機のデプロイヤでも使える（共通後処理層）。

## 立った後の揺れ・移動と、速さとトルクの関係（2026-10-15、ユーザーの指摘を受けて、v1・v2 の seed 1）

### 立った後の揺れと移動の原因（`getup/tools/hold_analysis.py`、`experiments/getup/eval/hold_getup{1,2}-s1_1499.json`）

L2 の評価用の状態から 64 個（決まった乱数）を 12 秒動かし、8〜12 秒のあいだずっと立っている体（60〜63 個）を調べた（CPU）。
条件: dr（検証の動画と同じ）、ノイズなし、個体差もノイズもなし、freeze（8 秒の時点で 1 秒以上立っている体の送る目標角を固定＝方策を止め、PD と物理だけで保つ）。

|---|---|---|---|---|---|---|

| 関節速度の RMS | 0.59 rad/s | 0.08 | 0.71 | 0.67 | 0.68 | 0.09 |

| 胴体の角速度の RMS | 0.23 rad/s | 0.06 | 0.29 | 0.26 | 0.24 | 0.09 |

1. **揺れの原因は方策の出力**: 立った後も、送る目標角を毎歩ほぼ制限いっぱい（0.06 rad/歩）に行き来させている。v1 は揺れのほぼすべてが
   20〜25 Hz（1 歩ごとに向きが反転する＝制御の 50 Hz の半分）、v2 は 10〜25 Hz。**観測ノイズを切っても、個体差を切っても変わらない**ので、
   ノイズや個体差に反応しているのではなく、方策そのものが行き来を作っている。
2. **目標角を固定すると止まる**: 関節速度は 7〜8 分の 1、付け外しは約 20 分の 1、胴体の移動は 3.5〜5 分の 1、向きの変化は約 10 分の 1。残る揺れは 5 Hz 前後
   （体が PD のばねの上で揺れる固有の揺れ）。
3. **移動の仕組み**: 揺れで手足が床から離れたり着いたりを毎秒 8〜10 回くり返し、そのたびに少しずつ滑る（スティックスリップ）。
   中央値で 4 秒のあいだに、v2 は胴体が 3.4 cm・向きが 5.7°、v1 は 1.5 cm・3.9° ずれる。
4. **揺れはトルクも押し上げる**: 立っているだけで 99%点が 68〜79 %。固定すれば 33〜35 %。
5. **なぜ方策がこうするか**: 学習の目的に、これを止める理由がない。行動の変化の罰は係数 −0.005 だけで（歩行の v31 は −0.02 に加えて、
   v10 で「カクつき」対策に入れた 2 階差分の罰 −0.01 と関節速度の罰がある）、成功の条件（角速度 0.5 rad/s 未満）は揺れていても満たせる
   （RMS 0.23〜0.29）。静かに立つことへの報酬もない。1 歩おきに反転する形になるのは、遅れ 1 歩と「前回の目標」を観測に入れた閉ループで、
   方策の利得が大きいと起きる周期 2 の振動と考えられる（推測、未確認）。
6. 実機では、毎歩の行き来はサーボの発熱・ギアの摩耗・トルクの上昇につながるので、**実機の前に直す**。

比較の動画（同じ状態・同じ個体差、左は方策のまま、右は 6 秒から目標角を固定。後半は 9〜10 秒を 1/5 の速さで）:

### 速さとトルク: 制限の幅を狭める試験（v2 の方策のまま学習し直さない、`dr_factors_getup2-s1_1499_gap*.json`）

|---|---|---|---|---|---|

- いまの方策の起き上がり方は、上限近くのトルクがある前提でできていて、**時間を延ばしても、送る目標角を絞るだけではほとんど立てない**。

### v3 の候補（ユーザーと決める）

- 時間: 学習のエピソードと §3.2 の主評価の時間を 8 秒 → 16 秒前後に延ばす（実機の試行はまだなので、実機の結果を見て基準を変えることにはならない。
  変えた理由と時期は計画書に残す。8 秒以内の値も副次的に併記する）。
- トルクの余裕: 学習のトルクの上限を仕様の 90 % 前後に下げる（三宅さんの学習用 URDF は 93 %）、または gap を 0.03 にする。
  上限を下げる方法なら、シミュの中では方策が仕様の 90 % を超えるトルクを使えない。KHR がその範囲で起き上がれるかは学習してみないと分からない。
- 揺れ: 行動の変化の罰を歩行並み（−0.02）にし、2 階差分の罰（−0.01）を足す。速さの制限を 0.06 → 0.03 rad/歩にする（揺れの振幅とトルクの両方を下げる。動きは遅くなる）。
- std: エントロピーの係数 0（三宅さんの設定と同じ）。

## getup-v3（2026-10-15、`envs/getup_env3.py`・`train_getup3.py`）

### 動機と決定

v2（seed 1）で、①トルクは 99%点 80 % まで下がったが 100 % がまだ一瞬出る（姿勢の負荷が原因で、方策のまま gap を絞ると立てない）、
