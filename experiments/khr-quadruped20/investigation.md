# khr-quadruped20 (v20) 事前調査記録 — 実機で観察された3課題への対策

- 記録日: 2026-08-11
- 発端: v19 の**実機動作（2026-08-10）でユーザが感じた3つの課題**。
  ① 前進を指示しているのに横へ逸れる ② 後退の速度が遅い ③ 旋回する際に中心からずれる
- 方針は [[project_roadmap]] / `ResearchPlan.md`。

## 1. 調査: 3課題それぞれにシミュ側の原因が見つかった

v19 (model_3999) の軌跡を実測（10秒、立ち上がり2秒除く、ノイズ/DR無効）。

| 指令 | 実測 |
|---|---|
| 前進 (+0.30) | 進行 **2.48 m** / 横ずれ **0.126 m（5%）** / 平均 0.248 m/s |
| 後退 (−0.20) | 進行 1.64 m / 横ずれ 0.035 m / 平均 **0.164 m/s** |
| 左旋回 (+0.50) | **中心のずれ 0.033 m**（経路長 0.30 m） |
| 右旋回 (−0.50) | **中心のずれ 0.024 m**（経路長 0.28 m） |

### ① 横へ逸れる — 原因は**未確定**（当初の断定を訂正）

> **【訂正】** 初版では「サーボのトリム誤差が主因」と断定したが、**これは証明されていない**。
> 一般論からの推測であり、この機体で残差を測ってはいなかった。以下に事実と仮説を分けて記す。

**確認できた事実**
1. **この機体には実在する大きなサーボ0点ズレがある**。ファーム `config.h` の
   `IDL_TRIM`/`IDR_TRIM` に実機のトリム値が入っており、ピッチ軸（左右で値が揃うはず）で

   | 関節 | L | R | 左右差 |
   |---|---|---|---|
   | 肩ピッチ | −20.42° | +0.68° | **−21.10°** |
   | 膝ピッチ | −68.54° | −53.68° | **−14.86°** |
   | 股ピッチ | −17.12° | −21.42° | +4.30° |
   | 肘ピッチ | 88.41° | 91.83° | −3.42° |

   EEPROM 付きのトリム機構が実装されていること自体、0点ズレが前提の設計であることを示す。
2. **DR に関節角オフセットのランダム化が無い**（摩擦・質量・COM のみ。kp/kd も無効）。
   ＝ 学習時に個体差を一度も経験していない、というのは事実。

**上記だけでは因果を主張できない理由（反証2点）**
- **トリムは「誤差」ではなく「補正値」**であり、ファームが適用する。問題になるのは**補正後の残差**だが、
  それは未測定。さらに膝ピッチの左右差 14.86° は KONDO サーボのスプライン1歯（約14.4°）にほぼ一致し、
  **ホーンの取付歯が左右で1つずれ、トリムがそれを正しく補正しているだけ**の可能性が高い。
- **シミュ自身が 5% 横へ逸れている**。動画の62秒＝約15m 進むとすると横ずれは 0.77m に達し、
  **実機固有の原因を持ち出さなくても観察された横逸れを説明できる**。当初この説明を過小評価していた。

**決定的な検証（次回の実機セッションで実施可能）**
- 初期姿勢で静止させ、`log.csv` の `qd`(指令角) と `q`(実測角) を関節ごとに比較する。
  系統差が残る → 残差オフセットが実在。差が無い → トリムは効いており原因はシミュ側。
- 実機で vy=0 の前進を一定距離歩かせ、**実測の横ずれ率**をシミュの 5% と比較する。

**したがって v20 の①の位置づけを次のように訂正する**
- ❌「実機の横逸れの主因への対策」 → 根拠不足
- ✅「**個体差に対する頑健性の保険**、およびその効果を測る実験」
- v20 で横ずれが改善しない場合、次の一手は `drift` の **vy 重みを上げる**（シミュ自身の非対称性を
  直接叩く）方が筋が通る。

### ② 後退が遅い — 原因: **指令範囲が前後非対称**
- `lin_vel_x_range = [-0.2, 0.3]`。後退の指令上限が前進より小さいため、
  絶対速度も **0.164 m/s vs 前進 0.248 m/s（34%遅い）** となる。
- 経緯: v9 で後退を −0.2 で開放 → v10 で前進のみ 0.4→0.3 に下げた → 非対称が残った。
- （なお追従率で見ると後退82%・前進81%とほぼ同等。**遅いのは追従の失敗ではなく指令設計の問題**。）

### ③ 旋回で中心がずれる — 原因: **`_reward_drift` に vx が入っていない**

v19 までの実装:
```python
vy_err = loco_lin_vel[:,1] - commands[:,1]
wz_err = loco_ang_vel[:,2] - commands[:,2]
return vy_err**2 + yaw_w * wz_err**2      # ← vx が無い
```
その場旋回の指令は (vx,vy,wz)=(0,0,±0.5) なので、**前後に流れても drift では罰されない**。
`tracking_lin_vel` は exp 形で小さなズレをほぼ罰さないため、抑制が効いていなかった。

## 2. v20 の対策（3点。①②③に1対1で対応）

| 対応 | 変更 |
|---|---|
| **③** | `_reward_drift` に **vx 誤差を追加**: `vx_err² + vy_err² + yaw_w·wz_err²`。旋回時の中心ずれ・横移動時の前後流れを直接罰する |
| **②** | `lin_vel_x_range` **[-0.2, 0.3] → [-0.3, 0.3]**（前後対称化） |
| **①** | **関節角オフセットのDRを新設**: `randomize_joint_offset: True` / `joint_offset_range: [-0.02, 0.02]`（±1.15°）。エピソードごとに各関節へ一定オフセットを与え **PD目標角に加算**（系統誤差として作用）。個体差があっても真っ直ぐ歩ける方策を狙う |

据え置き: v19 の tracking 設定（sigma 0.08 / tracking_lin_vel 5.0）、足裏全面接地
（`feet_orientation` -3.0 ＋着地直前）、`knee_swing_flexion` 1.8、トルク安全策など。

### ①の位置づけ（訂正後）
関節オフセットDR は「個体差への頑健性」を与える DR の王道手法であり、Sim2Real の実験として
価値がある（卒論の主張 `ResearchPlan.md` §3-A/B にも接続する）。ただし**実機の横逸れの主因が
これである証拠は無い**（上記の反証2点を参照）。本版はその効果を測る実験と位置づける。

### 事前スモークテスト（学習前・num_envs=4）
- ② `lin_vel_x_range = [-0.3, 0.3]` を確認。
- ① `joint_offset` は範囲 [-0.0195, 0.0196] に収まり、**env ごとに異なる値**（系統誤差として機能）。
- ③ 旋回指令(vx=0)で前後に流れる状況を作ると drift が **0.0000 → 0.0400** に増加
  （v19 は vx を見ないため同値だった）。
- 全26報酬のメソッド対応 OK、報酬 finite。

## 3. 学習と検証（このあと）
```bash
python khr_train_quad20.py -e khr-quadruped20 -B 4096 -I 4000 --seed 1
python khr_quad_report.py -e khr-quadruped20
```
### v20 の合否指標（v19比）
- **① 横ずれの減少**: 前進2.5m あたり 0.126m（5%）→ 縮小。
  さらに **関節オフセットを与えた条件でも横ずれが増えないこと**（＝個体差への頑健性）を確認する。
- **② 後退速度の向上**: 0.164 → 0.24 m/s 前後（前進と同等）へ。
- **③ 旋回時の中心ずれの縮小**: 0.033/0.024 m → 縮小。経路長 0.30m も短くなること。
- **トルクのピーク（必須）**: v19 の 81% を維持し **90%を超えないこと**。
- 足裏傾き 8.4°・膝ROM 26〜30°・前進追従81% が大きく崩れないこと。

> 注意: 関節オフセットDRは学習を難しくする方向に働く（同じ指令でも結果が個体ごとに変わる）。
> ±0.02rad は控えめな設定だが、追従が大きく落ちる場合は範囲を縮める。
