# getup-v6（L3: 横向き ＋ 歩行中の転倒）— 計画と判定の基準（学習の前に固定、2026-10-30）

## 0. きっかけ

- 10/30、ユーザーが教授の言葉を伝えた:「できる人にはなるべくいろいろやってほしいから、４脚歩行がいい感じに進んでるなら起き上がりもやっちゃおう」。
  ユーザーの受け止めは「教授的には起き上がりまで卒論に含めてほしそう」。
- ユーザーの指示は「転び方を数えるのと、L3 の作成まではやろう」。10/23 からの保留を解いた。L4（仰向け）と実機（R0〜R1）は、ユーザーが言うまで始めない。
- 元の計画（`docs/GetUpSim2RealPlan.md` §4.5）では、L3 は「u0 ≥ 0（横向き）＋ 歩行中の転倒 F（SHOULD）」、判定は「各段階 ≥ 80 %」だった。

## 1. 転び方の数え上げ（学習の前の確かめ）

道具は `getup/tools/fall_survey.py`。結果は `experiments/getup/falls/` に置き、§1 の数値は `falls.md` にまとめる。

- 起き上がり用のシーン（別名 URDF）で、v31 の歩行の方策を walk_session と同じ観測の作り方で動かす。
- 3 s ごとに、水平のランダムな向きへ胴体の速度を Δv 足す（Δv は 0.5〜2.0 m/s）。
- 転倒の判定は walk_session と同じで、判定したら全関節を脱力させ、止まった向き u0 を数える。
- v31 のシード 1〜3 で 512 体ずつ回す。参考に、シード 2 で押しを 1.0〜1.3 m/s に絞った条件も回す。
- 押さなければ 64 体とも 20 s 転ばないことを先に確かめた。

結果（10/30 23:16、`falls.md`）: **転んで止まった状態の 97.6〜99.0 % が L4 の範囲（u0 < 0、胸が上を向く）で、L3 の範囲（横向き）は 0.3〜2.1 % だった**（シード 1〜3）。

| 条件 | 転んだ体 | L2 % | L3 % | L4 % |
|---|---|---|---|---|
| シード 1、脱力 | 312 | 0.6 | 0.3 | 99.0 |
| シード 2、脱力 | 422 | 0.2 | 2.1 | 97.6 |
| シード 3、脱力 | 412 | 0.7 | 0.7 | 98.5 |
| シード 2、押しを 1.0〜1.3 m/s に | 272 | 0.0 | 0.7 | 99.3 |
| シード 2、転倒後も目標角を保持 | 422 | 0.0 | 0.0 | 99.8 |

- 転ばせた押しの 9 割は左右からで、横に倒れてから、さらに胸が上を向くまで転がって止まる。
- 押しを弱めても、転倒後に脱力させず関節を保持しても、変わらない。シミュレーションの脱力には関節の摩擦がないので両端を比べたが、どちらも L4 だった。
- 止まった向きは、左右どちらが下かがほぼ半々だった。頭が下を向いたものは 0。
- **L3 は、歩行中の転倒の 1〜2 % しか覆わない。** 歩行中に転んでから起き上がるには L4（仰向けからの寝返り）が要る。
- それでも L3 を作るのは、ユーザーの指示の範囲だからである。また、元の計画どおり、L4 の前の段階（横向きから胸を床へ向ける）にもなる。
- 限界: 転ばせ方は胴体の速度の押しだけである。段差・滑り・サーボの力の不足（10/28 の実機）による転倒は数えていない。

## 2. 構成（3 試行）

`python -m getup.train_getup6 -e getup6-L3-s{1,2,3} -B 4096 -I 3000 --seed {1,2,3}`（キュー `getup/jobs/queue_v6.txt`、`run_queue.sh` → `train_eval.sh`）。

| 項目 | v5 dcthr（採用版） | v6 |
|---|---|---|
| 初期状態バンク | bank_v1 | bank_v2（bank_v1 の 24,000 状態はそのまま。後ろに歩行中の転倒 F を足す、`getup/tools/make_bank_v2.py`） |
| 段階 | L0 → L1 → L2 | L0 → L1 → L2 → **L3** |
| L3 の中身 | — | 主のバンクで u0 ≥ 0 ＋ F で u0 ≥ 0（学習用 8,685 状態のうち F は 14、評価用 2,157 のうち F は 5） |
| イテレーション | 1500 | 3000 |
| 報酬・行動の後処理・個体差・PPO・段階が上がる条件 | dcthr | 同じ |

- **F のうち u0 < 0（仰向け寄り）は L3 に入れない。** 段階は u0 で切る決まりなので、仰向けの F は L4 の範囲になる。
  そのかわり、評価で F の全部（u0 によらない）の成功を参考に出す（`eval_getup` の `falls_all`）。L4 に進むかを決める材料にする。
- **観測の中の段階の値が変わる。** 段階の番号を（段階の数 − 1）で割って観測に入れているので、L2 の値は v5 の 1.0 から v6 では 2/3 になる。
  評価と実機では、いちばん上の段階（v6 は L3 = 1.0）を使う。
- 環境 `getup_env3` は、段階の中身を `getup/levels.py` で決めるように直した。
  `curriculum["extra"]` が無ければ前と同じになることを、bank_v1 と v5 の設定で確かめた（6 つの段階の状態の番号がすべて一致）。

## 3. 判定の基準（学習の前に固定）

主な評価は `eval_getup` で、評価用バンクの各段階の全状態を、個体差ありで 8 秒動かす。成功の定義は v1〜v5 と同じ（1.2 節の 5 条件を 1 秒続ける）。

| 判定 | 条件 |
|---|---|
| **合格** | 次の 3 つをすべて満たす。(1) L3 の成功が 3 シードの平均で 80 % 以上（元の計画の「各段階 ≥ 80 %」）。(2) L2 の成功が 3 シードの平均で 85 % 以上（dcthr は 91.5 %。L3 を足して L2 を大きく落とさない）。(3) トルクが上限（仕様の 90 %）に張り付く時間が、L3 で 3 シードとも 1 % 未満（dcthr は 0.07 %） |
| 不合格 | どれか 1 つでも満たさない。L3 に上がれなかったシードも、そのまま L3 の成功を数える |

- 3 シードがそろうまで判定しない。1 シードの値で何も言わない。
- 参考（判定には使わない）:
  - L3 の中の内訳（主のバンクの横向き kind 0 と F kind 2、u0 の区間別）
  - F の全部の成功（仰向けを含む）
  - L0・L1 の成功
  - 立った後の揺れ（`hold_analysis`、L2 の 256 状態）
  - L3 に上がったイテレーション
- 動画: 検証のたびに、段階ごとに 6 エピソードを撮る（`media/videos/getup/getup6-L3-s*_2999_L{0,1,2,3}.mp4`）。ユーザーの決まり「検証では毎回動画」による。

## 4. 事前の見立て（外れたらそれも記録する）

- L2 に上がるのは v5 と同じく 700〜900 イテレーション目、L3 は 1,100〜1,600 イテレーション目。
- L3 の成功は 70〜85 %。横向き（u0 が 0〜0.3）がいちばん難しい。まず胸を床へ向ける（upright の項）動きを覚える必要がある。
- L2 の成功は dcthr と同じくらい（87〜95 %）。L3 の状態の約 74 % は u0 ≥ 0.5（L2 の範囲）なので、L3 の段階でもリセットの約 56 % は L2 の範囲の状態になる
  （70 % × 0.74 ＋ 合格済みの段階からの 5 %）。L2 の範囲の練習は大きくは減らない。

## 5. GPU と自動実行

- 起き上がりの学習は whisper と重ねない（`gpu_gate.sh` の gpu_check、3000 イテレーションで 95 分の空きが要る）。
