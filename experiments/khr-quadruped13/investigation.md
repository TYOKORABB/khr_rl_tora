# khr-quadruped13 (v13) 事前調査記録 — すり足の原因（クリアランス報酬の設計欠陥）と対策

- 記録日: 2026-07-30
- 位置づけ: v12 の足回り品質を実測して判明した「すり足」への対策。方針は [[project_roadmap]]。
  学習後の結果は同ディレクトリ `report.md`/`results.md`・DevelopmentDiary に追記。

## 1. 課題: 歩容が「すり足・引きずり」だった（v12 実測, 前進0.3・8秒）

幾何オフセットを補正した**真のクリアランス**（各足の接地時基準高さからの持ち上げ量）で測定:

| 脚 | 接地率 | 歩容一致率 | 真のクリアランス | 接地中の滑り |
|---|---|---|---|---|
| 前左(腕) | 40% | 84% | **0.011 m** | 0.126 m/s |
| 前右(腕) | 45% | 89% | **0.014 m** | 0.146 m/s |
| 後左(足) | 41% | 85% | **0.000 m** | 0.049 m/s |
| 後右(足) | 53% | 89% | **0.005 m** | 0.058 m/s |

- 目標 `feet_height_target` は 0.06 m。実際は **0〜14 mm**。後左足は一度も地面から離れていない。
- 前脚は接地中に 0.126〜0.146 m/s で滑る。前進速度 0.213 m/s の **6〜7割** ＝ 引きずり。
- v10 でも同様（クリアランス 0.004〜0.012 m）で、**v9 以降ずっと見落とされていた**。
  トルク飽和の解消に注目するあまり、足上げを測っていなかった。

## 2. 根本原因: クリアランス報酬の設計欠陥（絶対高さを4脚一律に適用）

`_reward_feet_clearance` は `feet_height_target = 0.06` を **世界座標の絶対高さ** として
4本の足リンクへ一律に適用し、`error = |0.06 − feet_pos_z|` を指数で報酬化していた。

しかし各足リンクの**立位での原点高さ**を実測すると（v13スモーク時の `foot_ref_z`）:

```
foot_ref_z = [0.101, 0.101, 0.027, 0.027]   # [前左, 前右, 後左, 後右]
```

- **前脚(腕リンク)は立位で既に 0.101 m** ＝ 目標 0.06 を大きく超えている。
  → 足を上げるほど誤差が増え報酬が減る。**クリアランス報酬が足上げを罰していた。**
- **後脚は 0.027 m** で目標まで 3.3 cm。到達には大きな動きが要る一方、
  v9 以降で積み増した罰（`torque_limits −5.0`, `dof_pos_error`, `action_smoothness2`,
  `acceleration`）がすべて「脚を大きく動かすとコスト」として働き、割に合わなかった。
- 加えて v10 で前進上限を 0.4→0.3 に下げ、大きな歩幅を出す必要も減っていた。

結果、**「足を上げずに擦って進む」のが報酬的に最適**になっていた。scale を上げるだけでは
前脚の符号問題は直らないため、目標の定義自体を修正する必要がある。

## 3. v13 の対策（環境 khr_quad_env10 / 学習 khr_train_quad13）

姿勢・トロット・トルク安全策は v12 のまま。足回りに関する3点のみ変更。

| 変更 | 内容 |
|---|---|
| **クリアランスの相対化（主対策）** | `_reward_feet_clearance` を **各足の接地時基準 `foot_ref_z` からの相対高さ**で評価。`foot_clearance_target = 0.03`（4脚とも到達可能で意味のある目標）。scale 0.2→**1.0** |
| **滞空時間報酬の新設** | `_reward_feet_air_time`（scale **1.0**）。接地の瞬間に「それまでの滞空時間 − 0.2s」を加点し、「上げて・運んで・置く」歩容を促す（legged_gym 定番）。状態更新は `step` 側で行い報酬関数は純粋に保つ |
| **引きずりの抑制** | `contact_no_vel` −0.2 → **−1.0**。接地中の滑り（前脚0.13〜0.15 m/s）を強く罰す |

実装の要点:
- `foot_ref_z` は最初の step（初期姿勢＝4脚接地）で各足リンクのz高さを記録。env毎に保持。
- `feet_air_time` / `last_contacts` は `feet_num` 確定後に確保し、reset時にゼロ化。
- 旧 `feet_height_target` は互換のため cfg に残置（env10 では未使用）。

**トルク余裕について**: v12 のピークは定格の 66%（34%の余裕）。足上げにトルクを払う余地は
物理的にある。ただし飽和が再発しないか学習後に必ず確認する（実機の焼損リスクが最優先）。

### 事前スモークテスト（学習前・num_envs=4）
- `foot_clearance_target=0.03` / `air_time_target=0.2`、scales（clearance 1.0 / air_time 1.0 /
  contact_no_vel −1.0）反映。全25報酬のメソッド対応 OK。
- `foot_ref_z = [0.101, 0.101, 0.027, 0.027]` を取得（**上記の原因診断を数値で裏付け**）。
- clearance / air_time 報酬とも有限値を返し、step報酬 finite。→ 正常動作。

## 4. 学習と検証（このあと）
```bash
python khr_train_quad13.py -e khr-quadruped13 -B 4096 -I 4000 --seed 1
python khr_quad_report.py -e khr-quadruped13
```
### v13 の合否指標（v12比）
- **真のクリアランスの増加（主目的）**: 0〜14mm → 目標30mm に近づくこと。特に後脚が地面から離れること。
- **接地中の滑りの低下**: 前脚 0.13〜0.15 m/s が下がること（引きずり解消）。
- **歩容一致率の向上**: 84〜89% → より高く。
- **トルク安全性の維持（必須）**: 飽和 0/22 を維持し、ピークが定格の80%程度を超えないこと。
- 追従・直進性（前進68%・yaw 16°/10秒）が大きく崩れないこと。

> 足上げが増えれば接地衝撃・トルクが増える方向なので、**安全性とのトレードオフを必ず確認**する。
> 飽和が出たら clearance/air_time を弱めるか torque_limits を強める。
