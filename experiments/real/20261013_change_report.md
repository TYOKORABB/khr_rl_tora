### 1.1 前提: khr-getup.1 の中身（16:23、`66962ae`）

- 重力ベクトル（BNO055 の VECTOR_GRAVITY）を Meridim[8..10]、状態語を [11]（印 0x6B・通信監視の状態・キャリブレーション状態）。
- 通信監視: 正しいパケットが 200 ms 途絶えたら保持（HOLD）、1200 ms で全サーボ脱力（LIMP、ラッチ）。Power OFF のパケットで解除。起動直後も Power OFF を受けるまで脱力（DISARMED）。
- 純粋な C++ の部分は `khr_core.h`（ホストで単体テスト）、Arduino に依存する部分は `khr_ext.h`。

### 1.2 khr-getup.2 — 重力ベクトルを「読み取り途中」に読んでいた問題（`144725c`）

**分かったこと**: .1 では、重力の新しい値が届いたフレームが 3.8 %（約 4 Hz、最大 0.72 秒の空白）。
IMU スレッド（コア 0）が読み取り中のグローバル変数を、メインループ（コア 1）が最大 3 ms 待っただけで読んでおり、読み取り途中の 0 を見ていた。
梶田版の Euler 角の「全部 0 なら前回の値を使う」も同じ症状への対処だった。

| 場所 | 変更 |
|---|---|
| `mrd_wire0.h` L207–217（グローバル） | `imu::Vector<3> gravity_v` をやめ、`khr_imu_mux`（portMUX）、`khr_grav_shared[3]`、通し番号 `khr_grav_seq`、読み取り時間 `khr_imu_read_us` を追加 |
| `mrd_wire0.h` 個別読み取りの経路（L472 付近） | 重力をいったん手元の変数 `g` に読み、全部 0 でなければ排他制御の中で共有変数に書いて通し番号を進める（0 なら渡さない） |
| `mrd_wire0.h` L220 `khr_read_calib_sometimes()` | キャリブレーション状態の読み取りを毎周 → **32 周に 1 回**（.3 で関数に切り出した） |
| `khr_ext.h` L135–151 `khr_meriput90_ext()` | 排他制御の中で読み、「前のフレームから通し番号が進んだか」を状態語の bit 2 にする（L144）。診断に [84] 通し番号・[85] 読み取り時間（µs） |
| `main.cpp` L4 | `VERSION` を `+khr-getup.2` |

**選んだ方法と理由**
- 「全部 0 なら前回値」（梶田版の方式）にしなかった: 症状は消えるが、値が古いことが外から分からない。**通し番号**を送れば PC で更新の頻度と抜けを数えられる。
- 排他制御は portMUX（短い区間だけ割り込みを止める）を選んだ: 渡すのは float 3 個と整数 2 個だけで、二重バッファより単純。
- 状態語 bit 2 の意味を「このフレームに 0 でない値を読めた」→「前のフレームから新しい値が届いた」に変えた（PC 側の読み方は同じ）。
- キャリブレーション状態はゆっくりしか変わらないので、32 周に 1 回でも困らない。スレッドの 1 周を短くして、読み取り途中に当たる確率を下げた。

**結果**: 20.6 % のフレームで新しい値（約 21 Hz）。スレッドの 1 周は中央値 6.0 ms・最大 8.3 ms。
起動時刻 [83] から、スレッドは毎フレーム動いていることも分かった。残りの約 8 割は、読み取りそのものが 0 を返していた（→ §1.3）。

### 1.3 khr-getup.3 — IMU を 1 回の I2C 読み取りでまとめて取る（`3a465d8`）

| `mrd_wire0.h` L290, L449–457 | スレッドの頭で、一括読み取りの経路へ分岐。**10 回続けて失敗したら 1 周だけ梶田版の読み方**をはさむ |
| `main.cpp` L476–478 | 梶田版の `imu2ahrs()` を排他制御で囲む（書き込み途中の値を読まない） |
| `main.cpp` L401、`khr_ext.h` L58 `khr_pc_options()` | PC が [87] に `0x6B4C` を送っている間だけ梶田版の読み方にする（比較用） |
| `khr_ext.h` L151 | [87] に IMU の診断語（失敗の累計 下位 8 bit・最後の理由・読み取り方） |
| `khr_ext.h` L88 | 起動表示に読み取り方 |
| `config.h` L146–149 | `KHR_IMU_BURST 1`、`KHR_BNO055_I2C_ADDR 0x28` |

**選んだ方法と理由**
- 0 が返る原因（Arduino-ESP32 1.0.6 の I2C・BusIO・BNO055 のクロックストレッチなど）は追わず、**I2C の回数を 4 回から 1 回に減らす**ことにした。
  原因の特定には何度も書き込み（BOOT ボタン）が要る。一括読み取りなら、加速度・ジャイロ・Euler 角・重力が同じ融合周期の値でそろう利点もある。
- **同じ書き込みのまま比べられる切り替え**（[87] の印）を入れた: 書き込みを増やさずに、同じ回の中で一括と個別を比べられる。
  印の上位 8 bit を 0x6B にしたのは、ESP32 が [87] に返す診断語の上位 8 bit は最大 0x3F なので、取り違えようがないため（単体テストで全組み合わせを確認）。コンソールはこの印を送らない。
- **10 回続けて失敗したら梶田版の読み方をはさむ**: 一括読み取りが壊れても、歩行のデプロイヤが使う Euler 角が止まったままにならないようにする。
- 梶田版の読み方は消さずに残した（`KHR_IMU_BURST 0` で戻せる）: v8・v19 の実機歩行と厳密に同じ条件で比べる必要が出たとき用。

**結果**（同じ回に静止したまま 5 秒ずつ切り替え、`fw_check imu-ab`）: 一括 99.8 / 100.0 Hz・失敗 0 / 0.4 回/秒、個別 11.4 Hz・失敗 88.5 回/秒。
静止中の平均値は 2 つの読み方で一致（加速度の差は最大 0.002 m/s²、重力・Euler 角は差 0）。

### 1.4 khr-getup.4 — 受信バッファの古い通常パケットを読み捨てる（`e0b30c3`）

**分かったこと**: ESP32 は毎フレーム、受信バッファの**一番古い** 1 パケットだけを読む（梶田版の元からの作り）。
いったん溜まった 4〜5 パケットが減らないので、PC の指令は約 50 ms 遅れて効いていた（往復の中央値 52〜61 ms、p99 382 ms）。
ユーザーの了承「古いパケットは不要なら捨てていいよ」を得て変更した。

| 場所 | 変更 |
|---|---|
| `khr_core.h` L150–188 | `khr_cksm_ok()`（Meridian のチェックサムと同じ計算）、`khr_udp_drain()`（テンプレート、上限 `KHR_DRAIN_MAX = 16`） |
| `khr_ext.h` L51 `khr_udp_drain_rx()` | 上の方針を実機の受信関数 `mrd_wifi_udp_receive()` につなぐ |
| `main.cpp` L276–285（受信 [2-1] の直後） | 受けたフレームで読み捨てを行い、読み捨てたら `mrdsq.r_expect` を「最後に残したパケットの 1 つ前の番号」にする |
| `config.h` L150–152 | `KHR_UDP_DRAIN 1` |
| `khr_ext.h` L86 | 起動表示に受信の方式 |

**方針の中身と理由**
- **通常パケット（マスターコマンド 90）だけを読み捨てる**。今持っているのが特殊コマンド（全サーボ脱力・トリム設定など）なら読み捨てず、
  読み捨ての途中で特殊コマンドが来たらそれを使って止める（後ろは次のフレーム）: 一度しか送られない特殊コマンドを失わないため。
- **読み捨てた分をシーケンス番号の飛び（スキップ）として数えない**: 梶田版はスキップを検出すると、そのフレームのマスターコマンドを実行しない（`flg.meridim_rcvd`）。
  読み捨てのたびにそれが起きると特殊コマンドが無視されるので、予想番号を合わせる。チェックサムの合わないパケットの分は飛びとして残す（本当の欠落なので）。
- 選ばなかった案: PC 側で送る時刻を ESP32 に合わせる（コンソールの方式。PC 側の作りに依存して制御できない）、受信の待ち時間を延ばす（その分だけ遅れる）。

**結果**（`fw_check latency`、脱力パケットだけ）: 往復 中央値 61 → 14.8 ms（100 Hz で送り続け）、52 → 19.9 ms（受けたら返す）、p99 382 → 38 ms。
副作用: PC のパケットが受信の待ち（3 ms）に間に合わないフレームが約 18 %（前の指令を使い、新しいパケットは次のフレームで使う）。
梶田版のスキップ検出は**このフレームでだけ**立つ（返り番号で確認: 読み捨てたフレーム 74 回ではスキップ 0、新しいパケットが無いフレーム 90 回で 90）。

## 2. ESP32 への書き込みと、実機の状態

### 2.1 書き込みの道具 `real/firmware_patches/flash_with_backup.py`（新規、`144725c`）

**分かったこと**: この機体の ESP32 は、PC から書き込みモードに入れない（リセットは効くが GPIO0 が下がらず、起動モードがいつも `boot:0x13`）。
PlatformIO の書き込み（`build_fw.sh --upload`）は自動で書き込みモードに入る前提なので使えない。

| 機能 | 内容 | 理由 |
|---|---|---|
| BOOT ボタンを待つ | 接続を繰り返し試す（既定 30 回、実際は `--attempts 40` で実行） | ユーザーが押すまで待つ |
| 書き込む前に全体をバックアップ | 4 MB を 921600 bps で読み、ESP32 側の md5 と照合してから保存（`_work/backup/flash_<時刻>.bin`、権限 600） | 書き戻せることを保証する。Wi-Fi の設定が入っているので gitignore の場所に置き、権限も絞る |
| 書き込むのは otadata（0xE000）と app0（0x10000）だけ | ブートローダ・パーティション表・NVS（EEPROM のトリム値）は書かない | 変える必要のない領域に触らない。トリム値を守る |
| パーティション表の照合 | 今の表がビルドの表と違えば書かずに止まる | アプリだけ書いて起動しない事態を防ぐ |
| 1 回の接続でバックアップと書き込み | 読み出しのあと同じ接続で書く | BOOT ボタンを 1 回で済ませる（別々だと 2 回） |
| `--restore` | バックアップをフラッシュ全体に書き戻す | 元の状態へ完全に戻す手段 |
| 記録 | `_work/backup/flash_log.txt` に経過を追記 | いつ何を書いたかを残す |

### 3.3 `real/servo_jog.py`（新規、`144725c`）— サーボ 1 個だけで指令の経路を確かめる

- 頭ヨー（L0）だけ電源を入れ、今の角度から ±5° をなめらかに 1 往復。ほかの 21 個はずっと脱力（送る前にパケットを検査）。
- 中止: 指令と実測の差 **2° を 0.3 s**（最初 4° にしたが、偽の ESP32 で「ぶつかって 3° ずれた」場合に止まらなかったので下げた）。振幅の上限 10°。
- 評価は「ESP32 が実際に電源を入れていたフレーム」だけ（返ってくる電源フラグで判定）。脱力後の動き（このときはユーザーが手で動かした）を混ぜないため。`--reanalyze` で記録から出し直せる。
- **選んだ理由**: 動かすのが目的ではなく経路の確認なので、負荷のない首を、小さく、ゆっくり。寝かせた機体でも何かに当たりにくい。
- 結果: 追従の誤差 最大 0.64°・RMS 0.19°、指令から実測が戻るまで 112 ms（.1 の受信の溜まりを含む）。

### 3.4 `real/pose_session.py`（新規、`e0b30c3`、`1df82e2` で `--home` 追加）— 姿勢を保ったまま IMU の 6 姿勢を記録

- **全 22 サーボに電源を入れて保持**: ユーザーの「パワーを入れてくれないと姿勢を維持するのは無理かも」による。脱力では手足が崩れて胴体の向きが決まらない。
- 裏で動かし続ける `serve` と、`record <姿勢>`・`status`・`stop` を、`real/data/raw/pose_session/` のファイルでやりとりする。
  理由: 姿勢を置き換えるたびにユーザーに確認を取る（会話を挟む）間も、100 Hz で保持の指令を送り続ける必要がある。
- `--home`（2 回目で追加）: ユーザーの提案「コンソールの HOME ボタン（全関節 0°）を使えない？」による。
  コンソールの HOME は一瞬で 0° へ動くが、ここでは **4 秒かけてなめらかに**動かす（動作中に指令とのずれを監視できる。最大 1.71° だった）。
  コンソールそのものは、同じ受信ポートを使うので同時には動かせない。
- 中止: どれかの関節の指令とのずれが **5° を 0.3 s**、受信の途絶 0.3 s、`--max-minutes`（既定 12 分、実機では 20 分で起動）。止めるときは必ず脱力パケットを 1 秒送る。
- 1 回目に落ちた原因（番号の桁あふれ）と、往復遅れの集計の誤り（返り番号の一巡）は §7。

### 3.5 `real/walk_session.py`（新規、`5ee640d`）— 四脚歩行の方策を画面なしで実機に動かす

ユーザーの「代わりに実行することってできる？」による。コンソールは画面のボタン操作が前提なので、同じことをボタンなしで行う道具を作った。

| 項目 | 決めたこと | 理由・選ばなかった案 |
|---|---|---|
| 方策 | 既定 `khr-quadruped31-s2`（CPU で推論） | 3 seed のうち、全 5 方向でトルクのピークが 95.7 % 以下と最もバランスがよい。GPU は再学習・whisper と共有なので使わない |
| 読み込み | 最小のスタブ `_PolicyStub`（観測の次元と行動の数だけ）で `OnPolicyRunner` を組む。critic は v25 以降 81 次元 | 研究室の手元だけのスタブ（`khr_quad_env_no_gs.py`）に頼らない |
| 観測の作り方 `ObsBuilder` | 学習時の `khr_quad_env21.step()` と同じ並び・同じ作り方。**関節速度は方策の周期（20 ms）の差分**、「今の行動」と「1 つ前の行動」を分ける、累積ヘディング誤差 `heading ← heading·(1−0.002) + (loco_wz − 指令wz)·0.02`（`loco_wz = −ω_x`） | コンソールは関節速度が半分（10 ms の差を 0.02 で割る）、1 つ前の行動が今の行動と同じ（100 Hz で上書き）だった |

| 行動の当て方 | すぐ当てる（1 ステップ遅らせない） | 学習時は 1 ステップ（20 ms）遅らせていたが、実機には通信と処理の遅れが約 20 ms ある |
| **行動の制限** | **学習時と同じ（`clip_actions = 100`、実質なし）。代わりに目標角を URDF（`khr3hv_symhip.urdf`）の可動域の内側 0.03 rad に収める** | 学習環境で測ると v31 の行動は膝で最大 8・足首 5.4（初期姿勢から最大 69°）で、コンソールの ±2 では方策ステップの **98 %** で頭打ちになる。可動域で収めても閉ループで歩けることを学習環境で確認（前進 0.3 で 26 % のステップが端で止まるが、10 秒で 2.20 m）。0.03 rad は計画書の可動域の余裕と同じ値 |

| 記録 | 方策の周期ごとの関節角・目標・角速度・重力・指令・行動・ヘディング誤差・傾き（`real/data/raw/walk_<時刻>.npz`）と要約 JSON | 論文用の分析と、学習環境との比較のため |

### 3.6 `real/walk_analyze.py`（新規、`3bb698e`）— 歩行の記録を分析し、学習環境と比べる

- 指令ごとの区間（最初の 0.5 秒は除く）で、旋回の速さ（`−ω_x`）、横・前後の傾き（重力の y・z 成分）、関節の追従、歩容の周期（膝の角度を直線で傾きを除いてから FFT）、可動域の端に当たった割合を出す。
- `--sim`: 同じ指令の列を、同じ観測の作り方・同じ可動域の制限で学習環境でも動かし、同じ指標と並進の速さ（学習環境だけ）を出す。図も作る。

### 3.7 `real/imu_tests.py`（新規、`9488956`）— IMU の残りの確かめ（斜め・360°・落下）

- `static`: 静止中の融合の重力と加速度センサの向きの差（合格 < 3°）。**手で置く角度ではなく加速度センサを基準にした**: 狙った角度に 3° 以内で置くのが難しく、静止していれば加速度センサは重力そのものを測るため。
- `rotate`: 1 フレームで 5° を超え、かつジャイロが示す回転と食い違う「跳び」を数える（実際に速く回した場合は跳びとしない）。
- `drop`: 着地の衝撃から、重力が最終値の 3° 以内に落ち着くまでの時間。
- `--npz`: 記録済みの生データも分析できる（歩行の記録で試し、四脚の保持中の差 0.45°・跳び 0 回）。実機での 3 つの試験はまだ（§8）。
- サーボには何も送らない（受信だけ）。

## 7. 作業中に見つけて直した不具合（道具・手順）

| 見つけたこと | 影響 | 直し方 | 場所 |
|---|---|---|---|
| シリアルポートを開くと ESP32 がリセットされる | 起動表示を読むたびに再起動（サーボは脱力のまま） | 仕様として受け入れ、脱力していることを確かめてから開く | 手順 |
| 通信監視の試験が「最後に送った時刻」起点で、受信の溜まり（約 50 ms）の分ずれて不合格に見えた | 判定の誤り | 返り番号で「ESP32 が処理した時刻」を起点に | `fw_check` §3.2 |
| `servo_jog` の評価が脱力後の動きを含めていた | 誤判定（最大誤差 34.8°） | ESP32 が電源を入れていたフレームだけで評価 | §3.3 |
| `servo_jog` の中止の基準 4° では、ぶつかって 3° ずれても止まらない | 安全 | 2° に下げ、偽の ESP32 で確認 | §3.3 |
| **シーケンス番号（0〜59999）を int16 にそのまま入れていた** | 保持を始めて約 5.5 分（32768 個目）で道具が落ち、**ユーザーが逆さに持っている最中に全サーボが脱力**（通信監視が設計どおり働いた） | 3 つの道具で uint16 として入れる。32767〜123456 の回帰試験を `fw_check selftest` に。想定外の例外でも必ず脱力を送ってから終える | `fw_check`・`servo_jog`・`pose_session` |
| 往復遅れの集計で、返り番号（30000 で一巡）を一巡前の送信と組んでいた | 集計が「300 秒」になる（制御には影響なし） | 時刻順にたどり、その番号を最後に送った時刻とだけ組む。送信側の記録も一巡後の番号で残す | `pose_session.echo_rtt_ms()`、`servo_jog` |
| 「左側面を下に」が向かい合った人から見た左と取られた | 6 姿勢の解が「符号が逆」という誤った解に | 1 回目と比べて気づき、ロボット自身の左右にラベルを入れ替え。指示とコメントは「ロボット自身の」と書く | `real/calib/imu_poses.json`、§3.1 |
| 1 回目の 6 姿勢: 左右は背中のケースで 20〜30° 転がり、寝かせた姿勢は頭の側が約 6° 高い | 不合格 | 全関節 0° で保持（`--home`）＋水準器で置く。逆さとうつ伏せは取り直し | §3.4 |

| 観測を比べる位置（スライス）の誤り、オプション名 `--cmd` がサブコマンドの変数と衝突、方策の周期の数え方に関数属性を使っていた | 道具の誤動作 | それぞれ修正（コミット前） | `walk_session` |
| Genesis は 1 プロセスで 1 回しか初期化できない | 分析が落ちる | 1 回だけ初期化し、同じ指令の列は 1 回だけ動かす | `walk_analyze` |
| 歩容の周期が 0.29 Hz と出る区間 | 区間の初めの膝のゆっくりした変化を拾っていた | 直線で傾きを除いてから周波数を見る | `walk_analyze` |
| 360° 回しの回転の総量で、すでに °/s のジャイロをさらに度に変換していた | 表示の誤り | 変換を外す（コミット前） | `imu_tests` |
