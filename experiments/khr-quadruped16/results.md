# khr-quadruped16 (v16) 検証結果 — ❌ 報酬ハック。膝を「曲げっぱなし」にして報酬だけ回収した

- 記録日: 2026-07-31（学習: 4096env × 4000iter, seed=1, 所要 1h06m, 最終 model_3999。完走）
- 対策の意図は同ディレクトリ `investigation.md` を参照。
- 評価はノイズ/DR無効・loco座標系。前進は在範囲0.3。

## 1. 結論: 報酬設計の失敗（reward hacking）

学習ログでは `rew_knee_flexion = 1.4803` と**高い報酬を獲得**しているのに、
**膝の可動域はむしろ縮小した**（v15 7.2/7.8° → v16 **2.7/2.8°**）。

原因を特定するため、膝角度の分布を測った（前進0.3, 10秒）:

| 膝 | 平均角度 | swing 平均 | stance 平均 | **swing−stance 差** | 指令ROM | 実測ROM |
|---|---|---|---|---|---|---|
| l_knee | 0.685 rad | 0.700 | 0.673 | **+1.5°** | — | 2.7° |
| r_knee | **0.700 rad** | 0.703 | 0.697 | **+0.3°** | — | 2.8° |

（default = 0.40 rad、報酬の目標 = default + 0.30 = **0.70 rad**）

**膝は常時 0.70 rad（＝報酬の目標角度）で固定されていた。** 遊脚期と接地期の差はわずか
0.3〜1.5° しかなく、「曲げて・伸ばす」動作は一切していない。

### なぜこうなったか（設計の欠陥）

`_reward_knee_flexion` は **膝の「位置（絶対的な屈曲量）」を報酬にしていた**。

```python
flex = dof_pos[knee] - default_dof_pos[knee]     # 絶対的な屈曲量
rew  = exp(-k * |target - flex|) * is_swing      # 目標角度に近いほど加点
```

この定義だと **「常に目標角度で固定する」だけで満点**が取れる。関節を動かす必要がない。
むしろ動かすと目標から外れて損をするうえ、`dof_vel`/`action_rate` 等のコストもかかるため、
**固定するのが最適解**になった。

**「膝を曲げる」ことは報酬にしたが、「膝を曲げ伸ばしする（動かす）」ことは報酬にしていなかった。**
狙った犬・馬の遊脚短縮（曲げて→伸ばす周期運動）とは別物である。

## 2. 副作用: 接地の質と左右対称性が悪化

| 指標 | v15 | v16 |
|---|---|---|
| 後脚 足裏傾き（接地時平均） | 13.5° | **16.1°（悪化）** |
| 足裏傾き 左/右 | 11.0 / 13.9° | 12.1 / **17.1°** |
| 後脚 接地率 左右差 | **1.0 pt** | **10.8 pt（悪化）** |
| 後脚 歩容一致率 | 92/93% | 99/88%（左右で乖離） |

膝を曲げた姿勢で固定した結果、脚のリンク姿勢が変わり **接地時の足裏の傾きが更に悪化**した
（v14 11.0° → v15 13.5° → v16 16.1°）。左右対称性も v15 の最良値から大きく後退。

## 3. 安全性・追従は維持

| 指標 | v15 | v16 |
|---|---|---|
| 飽和関節数（全方向） | 0/22 | **0/22（維持）** |
| ピーク \|τ\|（前進） | 0.846 Nm (62%) | 0.869 Nm (63%) |
| 平均 \|τ\|/limit（前進） | 16% | 15% |
| \|Δaction\|RMS（前進） | 0.0899 | 0.0920 |
| 追従 前進/後退/左横/右横/旋回 | 75/61/90/69/105-96% | 75/**69**/62/65/99/100% |

トルク安全性は維持。後退は 61→69% と改善したが、横移動は 90/69 → 62/65% と低下。
後脚クリアランスは横ばい（膝を固定したままなので当然）。

## 4. 総合評価

| 項目 | 判定 |
|---|---|
| **膝 ROM の回復（主目的）** | ❌ **失敗**（7.2/7.8° → 2.7/2.8° と悪化） |
| 報酬の獲得 | ⚠️ 高い（1.48）が**ハックによるもの** |
| トルク安全性 | ✅ 維持（0/22、ピーク63%） |
| 接地の質 | ❌ 悪化（足裏傾き 13.5 → 16.1°） |
| 左右対称性 | ❌ 悪化（接地率差 1.0 → 10.8pt） |

**v16 は失敗。ただし「報酬の書き方を誤ると容易にハックされる」ことを実証した価値ある失敗である。**
実機に載せるなら v15（追従・対称性・滑らかさが最良）または v13。

## 5. 学び（卒論に記載する価値がある）

**「望む状態」ではなく「望む変化」を報酬にすべきだった。**
位置（絶対角度）を報酬にすると、その位置で静止するのが最適解になる。
周期運動を促したいなら、**位相間の差分**や**速度**、あるいは**基準からの相対量**を報酬にする必要がある。

これは v13 で `feet_clearance` を「絶対高さ」から「接地基準からの相対高さ」に直したときと
**同じ構造の誤り**であり、報酬設計における一般的な教訓といえる。

## 6. 次（v17 候補）: 「差分」を報酬にする

1. **膝の swing−stance 差を報酬にする（本命）**。接地時の膝角度の移動平均（EMA）を基準にし、
   **遊脚中にそこから追加で曲がった分**だけを加点する。定角度で固定しても差がゼロになるので
   ハックできない。v13 の `foot_ref_z`（接地基準）と同じ発想。
2. 膝の角速度（|ω|）を遊脚期に加点する。動きそのものを報酬化するが、暴れるリスクがある。
3. 併せて、悪化した接地の質（足裏傾き16.1°）への対処が必要。
   `feet_orientation` を「接地時＋着地直前」に広げる案を検討する。
