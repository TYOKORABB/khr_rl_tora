# URDF 可動域是正後の全バージョン再学習

**2026-10-06 開始 / 全 88 本 / 自動実行**

## 1. なぜやるのか

`r_hip_pitch` の可動域が左右で鏡像になっているバグ（→ [`../urdf_hip_pitch_bug.md`](../urdf_hip_pitch_bug.md)）が
**v1 から v29 までのすべてに影響していた**。

| | 左 `l_hip_pitch` | 右 `r_hip_pitch` |
|---|---|---|
| URDF の値 | −110.0° / +100.0° | **−100.0° / +110.0°**（鏡像） |
| 軸・rpy | `axis="0 1 0"`, `rpy="0 0 0"` | **同一**（＝鏡像にすべき理由がない） |

実測された影響:

- **v7: 右股関節が全時間の 100% で可動域に張り付き**（動いた範囲 0.3°）
- **v8: 左右とも 100% 張り付き**（1.4° / 0.6°）＝歩容は膝と足首だけで作られていた
- v30（是正後）で左右非対称が **8.62° → 4.21°**、足裏傾きが **4.71° → 3.91°**（過去最良）

つまり **これまでの 29 版すべての比較が、片脚を縛った状態での比較だった。**
是正後の条件で引き直さないと、「どの報酬が効いたか」「どの設計変更が効いたか」の
判断がそのまま使えるとは言えない。

## 2. 何を触らず、何を実行時に包むか

| 対象 | 方針 | 理由 |
|---|---|---|
| `../../assets/khr3hv/urdf/*.urdf` | **変更しない** | 他プロジェクトと共有。上流（s-kajita/khr3hv）の成果物 |
| 旧環境 `khr_quad_env*.py` 全 21 本 | **変更しない** | 書き換えると「当時の実装」が分からなくなる |
| `khr_quad_eval_metrics.py` | **変更しない（凍結）** | 指標を足すだけで GPU の演算順が変わり、接触物理のカオス性で<br>既存の測定値まで動く（[`../ablation/measurement_caveats.md`](../ablation/measurement_caveats.md) §2）。<br>これまでの全 ablation 結果との比較可能性を守る |
| 実行時のクラス | **`quad_compat.py` が包む** | 上記すべてを触らずに条件を揃える唯一の方法 |

### `quad_compat.py` が補うもの

1. **可動域の是正** — `scene.rigid_solver.set_dofs_limit()` で build 直後に上書き（`fix_joint_limits.py`）。
   どの URDF を読んでいる環境でも効く。
2. **旧環境に無い測定用属性** — `foot_ref_z` / `knee_idx` / `local_up` /
   `rear_feet_indices` / `rear_leg_phase_idx`。これらは開発途中で追加されたため
   v1〜v15 の環境には存在せず、評価がそこで落ちる。
   **定義はすべて `khr_quad_env19.py` からそのまま写しており**、新旧で同じ量を測ることを担保する。

```
                      ┌─ train_with_urdf_fix.py ─→ 可動域の是正のみ
quad_compat.py ───────┤
                      └─ eval_with_urdf_fix.py ──→ 可動域の是正 ＋ 測定属性の補完
                                                   （測定ツール本体は無改変で呼ぶ）
```

## 3. 実行順序 — 途中で止まっても価値が最大になるように

88 本すべてで約 3 週間かかるため、「全部終わるまで何も分からない」順序にはしない。

| | 内容 | 本数 | 累積日数* | その時点で言えること |
|---|---|---|---|---|
| **Tier A** | v23 × 4 seed | 4 | 1 日 | **ノイズ床の再構築。** 本プロジェクトの 2σ 判定すべてが<br>v23×4seed のノイズ床に依存しており、それがバグ入り機体で作られている |
| **Tier B** | v19 / v25 / v27 / v28 × 3 seed | 12 | 4 日 | 現在の結論（報酬の必要/不要、5 つの設計則）が是正後も成り立つか |
| **Tier C** | 残り 24 版 × 1 seed | 24 | 10 日 | 全バージョンに最低 1 点。通史を是正後の条件で引き直せる |
| **Tier D** | 残り 24 版 × seed 2,3 | 48 | 22 日 | 統計を 3 seed に揃える（単一 seed の誤判定を 4 回やった反省） |

\* 枠 12:00–18:00、1 本 ≒ 72 分（学習）+ 3 分（評価）→ 1 日 4 本。

**最優先が Tier A である理由**: ノイズ床は「同じ設定・違う seed でどれだけ測定値がばらつくか」の
基準で、`RewardReference.md` の「削除可／削除不可」判定も、v24〜v31 の改善判定もすべてこれを基準に
2σ 検定している。土台がバグ入り機体のままでは、是正後の数値をそこに当てても意味がない。

## 4. 使い方

```bash
./run_retrain_fixurdf.sh --status     # 進捗（完了数・残り日数・次の5本）
./run_retrain_fixurdf.sh --dry-run    # 残っている全本数を一覧
./run_retrain_fixurdf.sh              # 手動実行（枠内・GPU空きのときだけ進む）
```

自動実行（crontab に登録済み）:

```
10 12-17 * * * /home/tora/gsw4/khr_rl_tora/run_retrain_fixurdf.sh >> .../logs/retrain_fixurdf/cron.log
```

毎時起動なのは、12 時台に他プロセスが GPU を使っていても後の枠で拾えるようにするため。
二重起動はロックで防いでいるので、重なっても安全。**停止したいときはこの cron 行をコメントアウトする。**

出力:

- チェックポイント: `logs/fixurdf-vNN-sS/`
- 測定結果: `experiments/results_json_fixurdf/fixurdf-vNN-sS.json`
- 新しいノイズ床: `experiments/noise_floor_fixurdf.json`
  （Tier A の 4 本が揃った時点で `build_noise_floor.py` が**自動生成**する）
- 進捗の記録: `queue.done`（学習成功を記録）/ `queue.evalfail`（評価のみ失敗）

### 測定プロトコルの変更（意図的）

| | 旧（v1〜v29 の判定に使用） | 新（`fixurdf-*`） |
|---|---|---|
| 体数 | 8 体 | **128 体** |
| 指令・時間 | `[0.3,0,0]`・12 秒（先頭 2 秒を捨てる） | 同じ |
| 繰り返し | 3 回平均 | 同じ |
| ノイズ床 | `experiments/noise_floor.json` | `experiments/noise_floor_fixurdf.json` |

**体数を上げた理由**: 横ずれ率は 8 体では信用できない（8 体 2.25 ± **0.63** →
128 体 1.93 ± **0.06** で σ が 10 分の 1。[`../ablation/measurement_caveats.md`](../ablation/measurement_caveats.md) §2）。
ノイズ床をゼロから作り直すこの機会なら互換性の代償がなく、しかも実測で
**128 体 29.8 秒 vs 8 体 28.1 秒** とほぼ無償だった（GPU が体数方向を並列化するため）。

**旧ノイズ床は上書きせず残す。** 過去の判定を再現できるようにするため。
旧と新を同じ表に並べてはいけない（機体もプロトコルも違う）。

`exp` 名を `fixurdf-` 接頭辞にし、結果 JSON も別ディレクトリに置いているのは、
`update_reward_reference.py` の自動集計（`^khr-quadruped\d+...` にマッチ）に
混ざらないようにするため。**是正前の判定表と是正後の数値を同じ表に並べない。**

## 5. 設計上の注意（過去の事故から）

- **二重起動を mkdir ロック＋PID 生存確認で防ぐ。**
  v29 の学習時、キュー実行側がまだ評価中で `.done` を書く前に別インスタンスが起動し、
  「未実行」と判断して同じ exp を再開 → `logs/` を消して 58 分の学習を破壊した。
  学習プロセスの有無を見るだけでは評価フェーズを取りこぼすため、ロックで排他する。
  （動作確認済み: 生きた PID のロック → 中止 / 死んだ PID の残留ロック → 除去して続行）
- **`.done` は学習が成功した時点で記録する。** 評価が失敗しても再学習はしない。
  ckpt が残っているので評価だけ後からやり直せる。72 分を捨てる方が損。
- **学習が失敗したらキューを止める。** 同じ失敗を 88 本繰り返さないため。
- **開始した学習は枠を越えても最後まで走らせる。** 途中で殺すと ckpt が残らない。
- **GPU が他プロセスに使われていたら何も開始しない。** 相手が誰であっても競合は避ける。
- **このリポジトリの学習/評価が進行中なら何も開始しない。**
  nvidia-smi のメモリ監視だけでは、学習が終わって評価が始まる「数秒の隙間」に
  滑り込める。そこで新規学習を始めると進行中の測定と競合し、接触物理のカオス性で
  **測定値そのものが動く**（[`../ablation/measurement_caveats.md`](../ablation/measurement_caveats.md) §2）。
  そのため「学習中か」ではなく「このリポジトリの作業が進行中か」で判定する。
