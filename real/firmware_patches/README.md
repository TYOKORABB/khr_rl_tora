# ESP32 ファームの改造パッチ（khr-getup.3）

起き上がり実験の前提整備（`GetUpSim2RealPlan.md` §5.2 の **P0-1 IMU** と **P0-2 安全系**）のための、
梶田研の Meridian_LITE への最小限の改造。2026-10-13 のユーザ回答（Q-A「自分で実行可能なら改造を許可」）で実施。

- **元のリポジトリは一切書き換えない。** `build_fw.sh` が固定コミットの写しを `_work/`（gitignore）に取り出し、
  そこにパッチを当ててビルドする。`s-kajita/Meridian_LITE` へのコミット・プッシュはしない。
- 土台: `s-kajita/Meridian_LITE@85a62d1`（2026-04-21 "IMU eular angle bug fixed"、起動時の表示は
  `Meridian_LITE_v1.1.1_2025_08.22(kajita)`）。上流は `Ninagawa123/Meridian_LITE`（MIT License, © 2021 Ninagawa123 and Project Meridian Team）。
- Wi-Fi の設定 `keys.h` は元のリポジトリの作業ツリーから毎回コピーする。どこにもコミットしない。
- **実機に書き込み済み（2026-10-13 18:40、khr-getup.3）**。記録は `experiments/real/20261013_hw_check/`。

## 何を変えたか

| | 既定 | 改造前との違い | 切り方（`config.h`） |
|---|---|---|---|
| **IMU の重力ベクトル** | ON | BNO055 の融合推定の重力ベクトルを **Meridim[8..10]**（100 倍値、m/s²）に入れる。改造前はこのスロット（地磁気）に常に 0 を送っていた | `KHR_SEND_GRAVITY 0` |
| **状態語** | 常に | **Meridim[11]**（改造前は温度として常に 0）に通信監視の状態・キャリブレーション状態・改造版の印を入れる | — |
| **IMU の読み取り方**（.3 から） | 一括 | 加速度・ジャイロ・Euler 角・重力を **1 回の I2C 読み取り**でまとめて取る。改造前は 3 回（.2 は重力を足して 4 回）に分けて読んでおり、Euler 角などは読み取り途中の 0 を「前回の値」で埋めていた。**値そのもの（換算）は同じ**で、静止中の平均は個別の読み取りと一致（最大差 0.002 m/s²）。PC が [87] に `0x6B4C` を送っている間だけ個別の読み取りに戻る（比較用。コンソールは送らない） | `KHR_IMU_BURST 0` |
| **診断**（.2 から） | `KHR_SEND_GRAVITY` と同じ | **Meridim[84]** 重力ベクトルの通し番号（下位 16 bit。PC で更新頻度と抜けを数える）、**[85]** IMU スレッド 1 周の読み取り時間 [us]、**[87]**（.3 から）IMU の診断語（bit 0–7 読み取りの失敗の累計、8–11 最後の失敗の理由、12–13 読み取り方）。**[86] は使わない**（PC が番号を入れ、ESP32 がそのまま返すので往復遅れを測れる） | — |
| **通信監視（ウォッチドッグ）** | ON | PC からの正しいパケットが **200 ms** 途絶えたら HOLD（最後の目標角を保持 = 改造前と同じ）、**1200 ms** で LIMP（全サーボ脱力）。LIMP はラッチし、コンソールの **Power を切ったパケット**で解ける | `KHR_WDG_ENABLE 0` |
| **起動直後** | ON（通信監視の一部） | Power OFF のパケットを一度受けるまで全サーボ脱力（改造前は、最初のパケットが Power ON ならその目標角へすぐ動いた） | `KHR_WDG_ENABLE 0` |
| BNO055 の融合モード | NDOF（改造前と同じ） | 変更なし。`OPERATION_MODE_IMUPLUS`（地磁気なし）に切り替えられるようにしただけ | `KHR_BNO055_MODE` |

**変えていないもの**: Euler 角 [12..14]・加速度 [2..4]・ジャイロ [5..7]・サーボの指令と読み出し・通信周期・
[80..83] の時刻情報。既存のコンソールとデプロイヤ（`Meridian_consoleS*.py`）は [8..11] を使っていないので、そのまま動く。

### Meridim[11] の状態語

| bit | 内容 |
|---|---|
| 0–1 | 通信監視の状態（0: DISARMED, 1: OK, 2: HOLD, 3: LIMP） |
| 2 | 前のフレームから新しい重力ベクトルが届いた（届いていなければ [8..10] は前回と同じ値）。.1 では「このフレームに 0 でない値を読めた」 |
| 3 | 通信監視が有効 |
| 4–5 | BNO055 の加速度センサのキャリブレーション状態（0–3） |
| 6–7 | BNO055 の融合（システム）のキャリブレーション状態（0–3） |
| 8–15 | `0x6B`（改造版の印。改造前は [11] が常に 0） |

PC 側の読み取りは `khr_common/gravity.py`（`decode_status()`・`gravity_base()`・`solve_mount()`）。
ファーム側の `khr_pack_status()` と PC 側の `decode_status()` は、同じ値（`0x6BEF`, `0x6B09`）を両方の単体テストで確かめて、ずれないようにしている。

### 通信監視の状態遷移

```
            Power OFF のパケット
 DISARMED ───────────────────────┐
 （起動直後・脱力）                  ▼
                       ┌────────► OK ◄──────────┐
                       │  パケット   │ 200 ms 途絶   │ Power OFF のパケット
                       │           ▼             │
                       └──────── HOLD            │
                              （最後の目標角を保持）  │
                                   │ さらに 1000 ms │
                                   ▼             │
                                  LIMP ──────────┘
                           （全サーボ脱力・ラッチ。Power ON のパケットが来ても解けない）
```

LIMP を解いたあと再び Power を入れるのはコンソールの通常の手順に任せる（コンソールは Power ON の瞬間に
受け取った実測角を目標にする）ので、脱力して崩れた姿勢から古い目標角へ跳ぶことはない。

**守れないもの**: ESP32 自体の停止（ハング・電源断）。ICS サーボは指令が来なくなると最後の目標角を保持し続けるので、
**物理的な KILL スイッチ（サーボ電源）は別に必要**（計画書 P0-2）。

## P0-0 の監査で分かったこと（3° 補正）

計画書 F3 の「指令と実測の差が 3° を超えると目標を実測側へずらす補正（`tgt_gap_max`）」は、上流
（Ninagawa123 版、`v1.1.1_2026_04.26`）には**ある**が、梶田版では `e0a37b0` で入れて `a9f0cd4` で**取り消し済み**で、
土台の `85a62d1` には**無い**。研究室の実機がこの版なら補正の無効化は不要（起動時の VERSION 表示で確認する）。

## 使い方

**この機体の ESP32 は PC から自動で書き込みモードに入れない**（GPIO0 が下がらない。2026-10-13 に確認）。
書き込みは `flash_with_backup.py` で行い、**始まったら ESP32 の BOOT ボタンを 5 秒ほど押し続ける**。
書き込む前にフラッシュ全体（4 MB）を `_work/backup/` に読み出して照合し、otadata とアプリだけを書き込む
（ブートローダ・パーティション表・サーボのトリム値が入った NVS は書き換えない。パーティション表が違えば書き込まずに止まる）。

```bash
cd real/firmware_patches
./build_fw.sh                                        # パッチ版をビルド（単体テストも実行）
~/.platformio/penv/bin/python flash_with_backup.py   # バックアップ → 書き込み（BOOT ボタンを押す）
~/.platformio/penv/bin/python flash_with_backup.py --restore _work/backup/flash_20261013_174412.bin   # 元の梶田版にそのまま戻す
```

`build_fw.sh --upload`（PlatformIO の書き込み）は、自動で書き込みモードに入れる ESP32 向け。

```bash
cd real/firmware_patches
./build_fw.sh                    # パッチ版をビルド（単体テストも実行）→ _work/patched/BUILD_INFO.txt
./build_fw.sh --test             # 単体テストだけ
./build_fw.sh --upload           # ESP32 を USB でつないで書き込む（確認あり。ポートは自動検出か --upload /dev/ttyUSB0）
./build_fw.sh --base --upload    # 改造前（梶田版そのまま）に書き戻す
```

PlatformIO（`~/.platformio/penv/bin/pio`）が必要。ライブラリは `platformio.ini` の指定（`^` つき）で解決されるので、
**実機に今入っているファームとはライブラリの版が違う可能性がある**（2026-10-13 のビルド: Adafruit BNO055 1.6.4、
Adafruit BusIO 1.17.4、Meridian 0.1.0、MPU6050 0.5.0）。書き戻し（`--base`）も同じ版で作り直したものになる。

## 実機セッションでの確認手順

ロボットは寝かせるか吊った状態で。コンソールを閉じ、コンソールと同じ PC で行う。

1. **書き込む前に**、今のファームの起動表示（シリアルモニタ 115200 bps）を記録する。
   `Meridian_LITE_v1.1.1_2025_08.22(kajita)` 以外なら土台が違うので書き込まずに相談する（計画書 Q-B）。
2. `flash_with_backup.py` で書き込み（BOOT ボタン）、起動表示に `+khr-getup.3`、`[khr] IMU read: burst 0x08-0x33 (44 bytes, 1 transaction)`、`[khr] watchdog: ON (hold after 200 ms, limp after 1200 ms)`、
   `BNO055 mounted.` が出ることを確かめる。
3. `python -m real.fw_check listen` — 改造版と認識し、`|g|` が約 9.8、キャリブレーション状態が上がっていくこと。
   [80..83] の時刻情報（`plot_esp32_time.py`）で、フレーム周期が改造前より悪化していないこと
   （IMU のスレッドが I2C を 2 回多く読むようになった。400 kHz で 0.5 ms 程度の見込み）。
4. `python -m real.fw_check wdg-test` — **サーボに電源を入れずに**状態遷移（OK → 200 ms で HOLD → 1200 ms で LIMP → Power OFF で解除）を確かめる。
   このツールが送るのは全サーボ脱力のパケットだけ。結果は `experiments/real/<日付>_fw_check/wdg_test_<時刻>.json`。
5. **電源を入れた確認（ハーネスつき）**: コンソールで Power ON → コンソールを強制終了 → 約 0.2 s 保持のあと約 1.2 s で脱力することを
   動画で確認（LIMP に入ってから脱力まで < 50 ms が合格条件）。シリアルモニタに `[khr] watchdog OK -> HOLD`、`HOLD -> LIMP` が出る。
   コンソールを起動し直すと Power OFF で始まるのでラッチが解け、Power ON で通常どおり動く。
6. **IMU の 6 姿勢**: `python -m real.fw_check pose <姿勢>` を upright / head_down / prone / supine / left_down / right_down で記録し、
   `python -m real.fw_check solve` で取り付け回転を求める（合格: 全姿勢で誤差 < 3°）。
   そのあと `listen` を見ながらゆっくり 360° 回し、5° を超える跳びがないこと。結果は `real/calib/`。
7. **既存の歩行が変わらないこと**: v31 の四脚歩行を改造ファームで短く動かす（Euler 角の経路は変えていない）。

問題があれば `./build_fw.sh --base --upload` で改造前に戻す。

## まだやっていないこと

- **個別の読み取りで重力が 0 を返す原因**は特定していない（.3 の一括読み取りで回避した。個別に読むと、重力の読み取りの約 9 割が
  「I2C は成功したように見えて値が全部 0」になる）。
- **一括読み取りへの切り替えは、歩行のデプロイヤが使う Euler 角の鮮度も変える**（値は同じだが、読み取り途中の 0 による取りこぼしが無くなる）。
  v8・v19 の実機歩行と厳密に同じ条件で比べたいときは `KHR_IMU_BURST 0` でビルドするか、khr-getup.2（コミット `144725c` のパッチ）に戻す。
- **指令が約 50 ms 遅れて効く**（梶田版の元からの挙動。受信バッファから毎フレーム一番古いパケットを 1 つだけ読むため）。
  読み捨てて最新だけ使う変更は、既存の歩行の条件が変わるので入れていない（ユーザーと相談）。

- **サーボ温度・電流の読み出し**（計画書 FW-T、P1）: ICS の `getTmp`/`getCur` をサーボの通信に挟む必要があり、
  フレーム周期への影響を実機で測りながらでないと入れられない。当面は赤外線温度計で代替する。
- クォータニオンの送信: 方策が使うのは重力ベクトルだけなので見送った（必要なら Meridim[84..87] が空いている）。
