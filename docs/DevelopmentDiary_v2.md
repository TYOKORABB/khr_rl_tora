## 2. 現行のしくみ（v31）

`quad/khr_train_quad31.py`（設定はこのファイルの `get_cfgs()` / `get_train_cfg()` に直書き）＋ `quad/khr_quad_env21.py`。
版ごとに足したものは付録 B。

### 2.1 四脚の形

- **腕 = 前脚、脚 = 後脚**。腕が固定の `khr3hv_12dof.urdf` ではなく、腕が動く URDF を使う（今は右股関節の可動域を直した `khr3hv_symhip.urdf`）。
- **胴体を y 軸まわりに +90° 傾けた**前のめりの四脚姿勢（最初の試作は −90° の後ろ倒れで、見た目から前倒れに変えた、§10.3）。
- 制御するのは**全 22 関節**（腕 8・脚 12・胸と頭のヨー 2）。接地は前腕 2 つと足 2 つの 4 点。
- 歩容は**対角の 2 本ずつのトロット**（周期 0.5 s、位相 [前左, 前右, 後左, 後右] = [0, 0.5, 0.5, 0]）。
- 初期姿勢は v8 で作り直したもの（付録 C）。足裏が水平になる条件 `hip_pitch + knee_pitch + ankle_pitch = −1.5708` を満たす。

### 2.2 座標系の補正（loco frame）

胴体を 90° 倒しているので、胴体の座標軸が世界とずれる（胴体の z = 世界の前、胴体の x = 世界の下）。
速度の追従や姿勢の報酬を胴体の座標のまま計算すると「前進を罰する」ようなことが起きる。
そこで**報酬の計算は、初期姿勢の回転で世界にそろえた loco frame で行い、観測（角速度・重力）は胴体の座標のまま**にする。
実機の IMU は胴体の座標で測るので、観測をそろえるためにこの非対称が要る。評価で速度を測るときも loco frame を使う（胴体の座標では旋回が −4 % と誤って出た、§10.3）。

### 2.3 観測（actor 122 次元・critic 81 次元の特権観測）

| 位置 | 内容 | 次元 |
|---|---|---|
| [0:3] | 胴体の角速度 × 0.25 | 3 |
| [3:6] | 重力の向き（胴体の座標） | 3 |
| [6:9] | 指令（vx, vy, wz）× スケール | 3 |
| [9:31] | 関節角 − 初期姿勢 | 22 |
| [31:53] | 関節速度 × 0.05 | 22 |
| [53:75] | 今の行動 | 22 |
| [75], [76] | 歩容の位相 cos・sin | 2 |
| [77:99] | 1 つ前の行動 | 22 |
| [99:121] | 1 つ前の関節速度 × 0.05 | 22 |
| **[121]** | **累積ヘディング誤差 × 5**（v25 で追加、§4.7） | 1 |

観測のノイズ（スケールを掛けた後の値に一様乱数で足す）: 角速度 0.1（実の角速度で ±0.4 rad/s）・重力 0.05・関節角 0.05・関節速度 0.1・ヘディング 0.25（±0.05 rad）。行動にはノイズなし。
critic には、ノイズなしの同じ量（並進速度を含む）に、ランダム化の値（追加質量・摩擦・重心のずれ）とヘディング誤差を足した 81 次元を渡す（非対称 actor-critic）。

### 2.4 制御

- PD 位置制御 kp = 25、kd = 0.5、行動のスケール 0.15（目標角 = 初期姿勢 + 0.15 × 行動）。行動の上限は ±100（実質なし）。
- 行動は 1 ステップ遅れて効く（実機の遅れの模擬）。
- 終了条件: ロール・ピッチ 50° 超、胴体の高さ 0.10 m 未満。エピソード 20 秒、指令は 4 秒ごとに引き直す。
- 指令の範囲: 前後 ±0.3 m/s、横 ±0.15 m/s、旋回 ±0.5 rad/s。

| 報酬 | 重み | 役割（入れた版） |

### 2.7 物理の制約

- **サーボの定格トルク 1.373 Nm** を URDF の上限にしている。Genesis はこれを強制するので、飽和するとシミュでも指令どおりに動けない（実機では発熱・脱調）。
- **膝は片方向にしか曲がらない**（可動域 0.000〜2.793 rad）。v8 まで膝が下限に張り付いていた原因（§4.2）。
- **右股関節の可動域のバグ**: 元の `khr3hv.urdf` は `r_hip_pitch` の可動域が左と鏡像（左 −110°/+100°、右 −100°/+110°、軸は同じ）。
  v30 から直した `khr3hv_symhip.urdf` を使う（§4.8）。

### 2.8 PPO の設定（全版で共通）

ネットワーク [128, 64, 32]・ELU、`init_std` 0.5、entropy 0.01、lr 1e-3（適応）、γ 0.99、λ 0.95、clip 0.2、max_grad_norm 1.0、
5 epoch × 4 minibatch、4096 体 × 24 step/iter、4000 iter（約 50 分）。seed は `gs.init(seed=…)` の 1 か所だけで決まる（§5.3）。

## 3. 使い方

いつもリポジトリのルート（`khr_rl_tora/`）から実行する（URDF を `../assets/...` と作業ディレクトリ基準で読むため）。地図はルートの `README.md`。

```bash
source /home/tora/gsw4/bin/activate
cd /home/tora/gsw4/khr_rl_tora

python quad/khr_train_quad31.py -e khr-quadruped31-s1 -B 4096 -I 4000 --seed 1          # 学習（logs/<exp>/ を消して作り直す）
python quad/khr_quad_eval_metrics.py -e khr-quadruped31-s1 --env khr_quad_env21 -n 128  # 測定（測り方を固定、凍結）
python quad/khr_quad_eval.py -e khr-quadruped31-s2 --ckpt 3999 --env khr_quad_env21     # ビューアで再生（--env は付録 B）
DISPLAY=:1 python quad/khr_quad_record21.py -e khr-quadruped31-s2 --ckpt 3999 --vx 0.3 -o media/videos/walk.mp4   # 録画
python -m real.walk_session --help                                                     # 実機（real/README.md）
python -m getup.train_getup1 --help                                                    # 起き上がり（getup/README.md）
tensorboard --logdir logs
```

- 録画は `DISPLAY=:1` が要る（指定しないと "No display" で失敗する）。
- 旧日誌や `experiments/` の古い記録のコマンドは、2026-10-14 の整理の前の場所で書かれている（`python khr_train_quad23.py` → 今は `python quad/khr_train_quad23.py`）。
- v1〜v15 は `quad/archive_v1_v15/` にあり、直接は起動できない。`python quad/train_with_urdf_fix.py khr_train_quad8 khr_quad_env5 ...`（URDF の是正つき）か `khr_quad_eval.py --env` で使う。

### 4.1 第 1 期: 歩けるようにする（v1〜v4、7/21〜7/22）

**v1 — 初めての四脚歩行（`khr-quadruped`、3000 iter）**
- 二足の環境を四脚にした `khr_quad_env.py` を新しく作った（22 関節・トロット・loco frame・121 次元の観測・非対称 actor-critic）。指令は前進 0〜0.2 m/s だけ。
- 最初はエピソード長 12.5 のまま伸びず完全に失敗。探索の std が早く潰れていたので、`init_std` 1.0 → 0.5、行動のスケール → 0.15、entropy → 0.01 にして回避（§10.3）。
- 転ばずに立てる（エピソード長 1001）が、**実速 0.036 m/s（指令 0.15）のすり足**。

**v2 — 「速く・自然に」を設定だけで狙って、かえって遅くなった**
- `tracking_sigma` 0.25 → 0.15（追従を厳しく）、前進 0〜0.4、遊脚の目標の高さ 0.035 → 0.06。前進の追従報酬 1.45 → 1.12 に下がった。
- 報酬の内訳を調べると、**止まっていても前進の追従報酬の約 94 % がもらえ**、動くと罰（加速度・初期姿勢からのずれ・行動の変化）が増える。
  「歩く報酬 < 歩く罰」で、止まるのが最適解になっていた（探索は潰れていない＝報酬の設計の問題）。

**v3 — 報酬のバランスを直して、初めて速く歩いた**
- `tracking_lin_vel` 1.5 → 4.0、`similar_to_default` −0.1 → −0.02、`action_rate` −0.05 → −0.02、`acceleration` −1e-4 → −2e-5。
- 指令 0.3 に実速 0.257 m/s（追従 86 %）。legged_gym（Rudin ら 2021）で速度の追従報酬が最重要とされたことと合う。

**v4 — 全方向へ**
- 指令の範囲だけ広げた（横 ±0.15、旋回 ±0.5）。前進 ≈86 %・横 ≈77 %。足裏の傾き 12.4°、定格の 95 % を超えて張り付く関節 2/22。以後の比較の基準になった。

**是正後（§6）**: v1・v2 はほとんど進まない（0.04・0.10 m/s）。v3・v4 は速い（0.28 m/s）が、**3 seed とも 99%点が 100 %（常にどこかが飽和）で、膝がほとんど動かない**（1〜2°）。
当時「歩けた」としたのは速さと転倒だけを見ていたためで、トルクと関節の使い方を見れば実機に載せられる歩き方ではなかった。

### 4.2 第 2 期: 頑健さと足裏、膝の解放（v5〜v8、7/22〜7/23）と最初の実機

**v5 — 押しの外乱（`khr_quad_env2`）**: 3 秒ごとに最大 1.0 m/s の押し。押しへの耐性は上がったが、**追従が大きく落ちた**（前進 93 → 69 %、横 78 → 35 %）。
最初から強く押したので、方策が守りに入った（頑健さと性能のトレードオフ）。

**v6 — 押しのカリキュラム（`env3`）**: 押しを 50,000 ステップかけて強める。追従を保ったまま耐性を回復した。
ただし v4 → v6 で足裏の傾きが 12.4 → 24.3°、`ankle_roll` −30°・`hip_yaw` +20° と**脚がねじれて開いた踏ん張り姿勢**に流れ、定格のトルクを連続して使っていた。

**v7 — 足裏の水平（`env4`、`feet_orientation` −1.0）**: 足裏の傾き ≈11°。代わりに**定格の 95 % を超えて張り付く関節が 7/22** に増え、膝がほとんど動いていないことが分かった。

**v8 — 膝の解放と脚の横開きの抑制（`env5`）**
- 原因は 2 つ。(1) **膝の初期値 0.10 rad が機械的な下限 0.0 のわずか 5.7° 上**で、片方向にしか曲がらない膝が下限に押し付けられていた（可動幅 6.4° なのにトルク張り付き 100 %）。
  (2) `hip_yaw`・`ankle_roll` が開いたまま、時間の 98〜99 % で定格の 95 % を超えていた。
- 初期姿勢を作り直した（膝 0.10 → 0.40 rad、股関節 −1.671 → −1.770、足首 0 → −0.201、肩 −1.571 → −1.771、肘 0 → 0.20。付録 C）。`hip_pos` の罰に `hip_yaw`・`ankle_roll` を足した。
- 膝の可動幅 6.4 → 22.3°、膝の張り付き 100 → 3 %、張り付く関節 7/22 → 2/22、足裏の傾き 7.5°（当時の最良）。横の押しへの耐性は 1.5 → 1.2 m/s に下がった（踏ん張り姿勢をやめた代償）。
- 6 方向の録画: 前進 87 %・左右の横 63 / 92 %・旋回 91 / 101 %。**後退は 7 %**（学習の指令が前進 0〜0.4 だけで、負の速度を一度も経験していない）。

**v8 の実機確認と教授の指摘（7 月下旬）**: 研究の方向は良いとの評価。一方で **① 動きがぎこちない、② トルクが最大になっている可能性、③ 後退できない** の 3 点を指摘された。
- 調べると、**後脚の股関節ピッチが全方向で常に 100 % 飽和**し、PD の目標から 50〜66° ずれ続けていた（届かない指令を出し続ける bang-bang の動き）。ほかの 20 関節は 1〜4° で追従。
  ハードが弱いのではなく、**方策が飽和を利用する歩き方を覚えていた**（報酬が飽和をほとんど罰していなかった）。
- 当時「静止して同じ姿勢を保つなら 43 % のトルク」と書いたが、**これは別の測り方の値で誤り**。起き上がりの事前検証で測り直すと 8.2 %（9.9 V、§8.2）。
- **URDF のバグの影響（§4.8）**: 当時の v8 の方策は、股関節が時間の 100 % で可動域の端に張り付いていた（左右とも。動いた範囲は 1.4° と 0.6°）。歩容は膝と足首だけで作られていた。

### 4.3 第 3 期: トルクの安全（v9〜v12、7/29〜7/30）

**v9 — 飽和対策と後退（`env6`）**
- `torque_limits`（−2.0、定格の 85 % 超を罰する）、`dof_pos_error`（−1.0、PD の目標と実際の角度の差＝届かない指令を罰する。主対策）、`acceleration` 強化、前進を −0.2〜0.4 に。
- 股関節の追従誤差 47〜60 → 2.6〜8.0°、張り付く関節 2/22 → 1/22（右股関節だけ）、平均の負荷 36 → 28 %、**後退 7 → 74 %**。
- **是正後**: トルク平均 32.8 → 19.5 %（−48.8σ）、99%点 100 → 72 %（−32.7σ）。**トルクが下がる方向では全版でいちばん大きな段差**で、トルクを罰する報酬の効果は是正後も明確（上がる方向では v4 → v5 の押しの導入が +72σ）。

**v10 — 左右対称と低負荷（`env7`）**
- 実機の安全についての指摘「**トルク 100 % はモーターが焼けるので絶対に不可**」「前進なのに横へ逸れる」「カクッとする」。
  前進時に右股関節だけ平均 100 %・左 56 % の非対称な歩き方で、右の飽和と横への逸れは同じ原因だった。
- `leg_load_balance`（左右の後脚の平均負荷の差）、`drift`（指令からの横・旋回のずれ）、`action_smoothness2`（行動の 2 階差分）を追加。`torque_limits` を 0.65・−5.0 に強化、前進の上限 0.4 → 0.3。
- **張り付く関節 0/22（全方向）**、平均の負荷 11〜17 %、右股関節 100 → 23 %、横の速度のずれ +0.032 → −0.004。前進の追従は 71 % に下がった（安全を優先した意図的なトレードオフ）。前進中のヨーのずれ（+0.053 rad/s）は残った。
- **是正後**: 99%点 72 → 55 %（−20σ）。以後の版は 52〜66 %（崩れた v11 を除く）に収まる。

**v11 — ❌ 瞬間のヨーを罰して、並進が崩れた（`env8`）**
- `drift` のヨー成分を横の 5 倍にした。前進 28 %・後退と横 0 %（旋回だけ残る）。トロットは前進中に**もともとヨーが周期的に揺れる**ので、それを強く罰すると「並進すると罰される → 動かない方が得」になった。
- 学び: 直進性は**瞬間のヨー**ではなく、**時間で平均した向きのずれ**で罰する。是正後も速度 0.001 m/s で、同じ失敗が再現した（横ずれの率は前進がほぼ 0 なので発散し、意味をなさない）。

**v12 — ヨーのずれを EMA で（`env9`）**: ヨーの誤差の EMA（約 1 秒の平均）の二乗を罰した（`heading_drift`）。周期的な揺れは平均で消え、じわじわ曲がる成分だけを叩く。
前進 68 %・10 秒の向きのずれ +27 → +16°・張り付く関節 0/22 を保った。ここでシミュの改善を一区切りにし、実機へ移る方針にした。

### 4.4 第 4 期: 足回りの質（v13〜v19、7/30〜8/1）と 2 回目の実機

**v13 — すり足の原因はクリアランスの報酬の欠陥だった（`env10`）**
- 指導教員と本人の「足回りが不安」から、初めて足上げを実測した。接地の高さからの**本当の持ち上げ量が前脚 11〜14 mm・後脚 0〜5 mm**（目標 60 mm）。後ろ左足は 8 秒間一度も離れなかった。
- 原因: `feet_clearance` が目標 0.06 m を**世界座標の絶対の高さ**として 4 本に一律で当てていた。**前脚（腕のリンク）は立っているだけで 0.101 m** あり、上げるほど目標から遠ざかって報酬が減る＝**足上げを罰していた**。
- 各足の接地時の高さ `foot_ref_z` からの**相対量**で測るように直し、`feet_air_time` を追加、`contact_no_vel` を強化。前脚の持ち上げ 3 倍（31〜32 mm）、横の追従 +14〜23 pt。後脚は 5〜6 mm のまま。
- この欠陥が本物だったことは、8/21 の ablation で確かめた（§4.6、前脚だけが 22 % 下がる、4.8σ）。

**v14 — ❌ 仮説が反証された（`env11`）**: 後脚の「変な力の入れ方」（膝が曲がらず、足首が膝より大きいトルク）の原因を「胴体の高さの罰で胴体が固まっている」と考え、`base_height` −10 → −3。
胴体の上下動は 2.0 → 1.8 mm でほぼ変わらず、仮説は棄却。前脚の目標を脚ごとに分けて v12 の水準に戻したのは成功。

**v15 — 膝が動かない本当の原因を特定（`env12`）**
- `feet_orientation` を接地中だけにした（遊脚中も足裏の水平を強いて膝の屈曲を抑えていた、という仮説）。足首の負荷 32 → 24 % と仮説の一部は当たったが、膝は動かないまま。
- PD の**指令の**可動域と実測の可動域を比べると、膝の指令の可動域そのものが 7° しかなかった（実測はそれ以上）。**トルク不足ではなく、方策が膝を動かす指令を出していない**。
  膝を曲げる利益がなく、動かすコスト（関節速度・行動の変化など）だけがあるので、膝を固めて股関節だけで振る歩き方に収束していた。

**v16 — ❌ 報酬ハック: 膝を「曲げっぱなし」にされた（`env13`）**: 遊脚中に膝が曲がっているほど加点（**膝の角度という位置**を報酬にした）。
学習の報酬は高いのに膝の可動幅は 7 → 2.7° に縮み、膝は報酬の目標角度 0.70 rad で固定されていた。**位置を報酬にすると、その位置で止まるのが最適解**になる。
v13（絶対の高さ → 相対量）と同じ構造の誤り。

**v17 — 膝の「遊脚 − 接地」の差を報酬に（`env14`）**
- `knee_swing_flexion`: 基準を**その脚自身の接地時の膝角度（EMA）**にとり、遊脚中にそこから追加で曲がった分だけを加点。一定の角度で固定すると差が 0 になるのでハックできない（学習前に確かめた）。
- 膝の可動幅 7 → **55°**、膝が足首を上回る主動力に戻った。代わりに、トルクのピーク 63 → 91 %、追従の低下、足裏の傾き 21.4°。差分で動きを促すと、絶対量（膝の平均角度）は拘束されずに流れる。
- **是正後**: 膝 ROM 48.9 ± 12.7°（過剰）、足裏 17.9° と、当時の診断どおり。

**v18 — 足裏全面での接地（`env15`）**: `knee_swing_flexion` 3.0 → 1.8、`feet_orientation` −1 → −3 にして**着地の直前（遊脚の終盤）からも水平を求める**。
足裏の傾き 21.4 → **6.1°**、膝の可動幅 38〜48°、ピーク 81 %。前進の追従は 57 % で戻らず。**是正後**: 足裏 17.9 → 4.8°（−26.5σ）と大きく改善したことは 3 seed でも保たれた。

**v19 — 前進の追従の回復（`env15` のまま）**
- 診断: 指令 0.3 に実速 0.171（43 % 足りない）でも `exp(−誤差²/σ)` は最大の 89.5 % がもらえ、**遅いままが最適**になっていた（v2 と同じ構造）。
- `tracking_sigma` 0.15 → 0.08、`tracking_lin_vel` 4.0 → 5.0（速度に対する報酬の傾きが 2.1 倍、学習前に検算）。
- 前進 57 → **81 %（0.244 m/s）**、後退 82 %、ピーク 81 % で据え置き、膝 26〜30°。当時の**総合的に最良**の版。
- **2 回目の実機（8/10）**: v19 で **62 秒間、転倒なしで四脚歩行**。足裏全面の接地も実機で再現し、教授の評価は「良い感じですね」。
  一方で、ユーザーが感じた課題 ① 前進なのに横へ逸れる ② 後退が遅い ③ 旋回の中心がずれる、が次の版の動機になった。
  （当時の実機はコンソール `Meridian_consoleS_quad.py`、改造前のファーム、行動の制限 ±2。v31 の実機とは条件が違う、§7.1）

### 4.5 第 5 期: 実機で見つかった課題（v20〜v23、8/11〜8/12）— そして「多くはノイズだった」

**v20 — 実機の 3 課題への対策（`env16`）**
- ② 後退が遅いのは、**指令の範囲が前後で非対称**（−0.2〜0.3）だったため。③ 旋回の中心がずれるのは、`drift` が前後のずれを見ていなかったため。① 横への逸れは原因が確定しなかった。
- `drift` に前後を追加、前後の範囲を ±0.3 に、**関節の 0 点のずれのランダム化（±1.15°）を新設**（個体差への頑健さ）。
- 後退 0.164 → **0.269 m/s**（前進とほぼ同じ）、個体差ありの横ずれ 12.3 → 8.3 %。代わりに足裏 8.4 → 13.3°、接地の左右差 3.0 → 9.5 pt、個体差ありのピーク 100 %。
- 訂正: 当時「実機のサーボのトリムの誤差が横への逸れの主因」と書いたが、**証明されていなかった**。トリムはファームが当てる補正値で残差は未測定、しかもシミュ自体が 5 % 横へ逸れていた。
- 測り方の誤り: トルクの図の道具が関節の 0 点のずれを切っておらず、v20 だけ個体差ありで測っていた（見かけのピーク 100 %）。既定で切るように直した。
- **是正後**: 足裏 3.9 → 6.1°（+4.3σ）の悪化は 3 seed でも出た。

**v21 — トルクと足裏を取り戻す（`env16` のまま）**: `torque_limits` 0.65・−5 → 0.60・−8、`feet_orientation` −3 → −4.5、`leg_load_balance` −1 → −2。
個体差ありのピーク 100 → 82 %、足裏 13.3 → 7.8°。代わりに前進 0.223 m/s、接地の左右差 9.5 → 14.0 pt（悪化）。
`leg_load_balance` は**トルクの左右差**を罰していて、直したい**接地時間の左右差**とは別の量だった（測る量を誤った 3 例目、§10.1）。
**是正後**: 99%点 −4.9σ・足裏 −5.3σ の改善は 3 seed でも出た。

**v22 — 接地時間の左右差を直接罰する（`env17`、`contact_duty_balance` −10）**: 接地の左右差 14.0 → **2.2 pt** と見えた。`tracking_lin_vel` 5 → 6 は速度を上げず、ピークだけ 82 → 93 % に上げた。
**しかしこの改善はノイズだった**: 直後の seed study（§4.6）で、同じ設定でも接地の左右差は seed だけで 0.9〜11.8 pt 動くと分かり、
`contact_duty_balance` を外す ablation でも差は出なかった。是正後の 3 seed でも v21 4.8 pt・v22 4.1 pt で差はない。**設計則の事例からは外す**。

**v23 — `tracking_lin_vel` を 5 に戻す（`env17` のまま）**: v22 との違いはこの 1 点だけなのに、接地の左右差 2.2 → 12.5 pt、横ずれ 13.9 → 6.1 % と大きく入れ替わった。
これがきっかけで、**版を重ねる前にノイズ床を測る**ことにした。v23 は以後の基準（ベースライン）になった。

### 4.6 統計を入れる（8/11〜8/21）: seed study・ablation・測り方の分解

**seed study — 同じ設定を seed だけ変えて 4 本（v23 × seed 1〜4、8/11〜8/12）**

| 横ずれ | 6.1 / 10.9 / 7.7 / 6.5 % | 1.89 | 3.78 |
| 前進速度 | 0.228 / 0.227 / 0.214 / 0.238 m/s | 0.009 | 0.017 |
| 膝 ROM | 26.9 / 41.7 / 21.6 / 45.3° | 9.87 | **19.74** |
| トルク平均 / 99%点 | 18.0 % / 59.7 %（σ 0.33 / 1.13） | | |
| 90%超の時間 | 全 seed 0.00 % | 0 | 0 |

- **v20 以降に下した「この版は良い／悪い」の多くは根拠がなかった**: 膝 ROM の「過大／理想」（差 18° < 2σ 19.7°）、ピークの「危険／安全」（差 16 pt ≈ 2σ）、接地の左右差の「大成功／悪化」（差 10 pt ≈ 2σ 8.5）。
- 一方で、**トルクを平均・99%点・90%超の時間で見れば極めて安定**（どの版も実機に問題のない水準）。ピーク（最大値）は主指標にしない。
- 以後の決まり: **版の差は 2σ を超えたときだけ主張する**、ピークは使わない、ablation も複数 seed で行う。

**ablation — 報酬を 1 つ外して 3 seed ずつ（v23 基準、8/19〜8/20）**

| 外した報酬 | 何が起きたか | 判定 |
|---|---|---|
| `torque_limits`（v9〜） | 90%超の時間 0.00 → **11.2 %**、99%点 59.7 → **100 %**、平均 18 → 32 %、足裏 7.6 → 12.7° | ✅ 必須（主張 A の決定的な証拠） |
| `knee_swing_flexion`（v17） | 膝 ROM 33.9 → **6.6°**（v15 の棒脚に戻る）。トルクは下がる＝膝を使わない方が楽 | ✅ 必須（主張 C） |
| `contact_duty_balance`（v22） | 接地の左右差 5.0 → 4.7 pt。どの指標も差なし | ❌ 効果なし（v22 の改善はノイズ） |

## 5. 測り方と統計

### 5.1 測定のやり方（`quad/khr_quad_eval_metrics.py`、凍結）

- 1 つのチェックポイントを、**128 体・12 秒（最初の 2 秒は捨てる）・指令を固定**して動かす。ランダム化と観測ノイズは切り、
  **個体差（関節の 0 点のずれ ±1.15°）なし／あり**の 2 条件で測る。論文の主な条件は「個体差あり・前進 0.3 m/s」。
- 測定の乱数（どんな個体を引くか）を 0・1・2 で 3 回測り、平均する（`--repeats 3`）。乱数は torch・cuda・numpy・random のすべてを明示する（v24 の誤報の再発防止）。
- **このファイルは凍結**している。読み取りを 2 行足しただけで GPU の演算の順が変わり、接触のカオスで横ずれが 263 % 動いたことがある（§5.4）。旧版を測るときは `quad/eval_with_urdf_fix.py`・`quad_compat.py` で外から包む。

| 指標 | 定義 |
|---|---|
| トルク平均・99%点 | 22 関節のトルク ÷ 定格 1.373 Nm の平均と 99 パーセンタイル |
| 90%超の時間 | 定格の 90 % を超えていた時間の割合 |
| 前進速度 | loco frame の前進速度 |
| 横ずれ | 指令の向きに垂直な最終変位 ÷ 進んだ距離（%）。**ほとんど前進しない版では発散して意味をなさない**（v1・v11） |
| 膝 ROM | 後脚の膝の最大 − 最小（°） |
| 着地の足裏傾き | 後脚の足が着地した瞬間の足裏の傾き（°）。接地平均・蹴り出しも別に出る |
| 接地の左右差 | 後脚の左右の接地時間の割合の差（pt） |
| 歩容の一致 | 4 脚とも「立脚の位相（< 0.55）で接地・遊脚で離地」の時間の割合 |
| 転倒 | エピソードの終了（倒れた）回数。全版の再学習の測定は押しなし（`--push` で 1.0 m/s の押しを即座に掛けられる） |
| 股関節の左右差 | 左右の股関節ピッチの平均角度の差（°、`quad/khr_quad_eval_symmetry.py`）。ノイズ床に入っていないので版の比較には使わない |

方向別（後退・左横・旋回）は `--cmd` で指令を変えて同じように測る。

### 5.3 seed（学習 seed と測定 seed）

- **学習 seed** は `khr_train_quad*.py --seed` → `gs.init(seed=…)` の 1 か所だけで決まり、random・numpy・torch・torch.cuda をまとめて初期化する（rsl-rl は独自の seed を持たない）。
  決まるのは、ネットワークの初期の重み、行動のサンプリング、エピソードの開始の位相、指令の引き直し、ランダム化、観測ノイズの 6 つ。
  **URDF・報酬・ネットワーク・PPO の設定・PD・歩容・初期姿勢は変わらない**＝同じ問題を別の乱数の引き方で解き直す。
- それでも方策が変わるのは、PPO が非凸な最適化で、**四脚歩行には対称性の破れ（どちらの脚が先か、どちらへ曲がる癖か）が本質的にあり、報酬がそれを指定していない**から。seed がその破れ方を選ぶ。
- 同じ設定でも、v23 の膝 ROM は seed で 21.6〜45.1°、v24 の横ずれは 7.7〜19.0 % と 2.5 倍。**1 seed では正反対の結論が書けてしまう**。
  逆に、**良い設計は seed のばらつきも小さい**（v25 の横ずれの幅 1.5 pt、v27 の着地の傾きの幅 0.7°、v31 の股関節の左右差 0.3〜1.2°）。
- **測定 seed**（`--repeats`）は方策を変えず、試す条件（引く個体・指令・位相）だけを変える。個体差なしではばらつきの大半が学習 seed 由来、個体差ありでは大半が測定由来（§4.6）。
- **中間発表・審査での答え方**: 4 seed の σ の推定自体に約 35 % の不確かさがあることは自覚している。ただし主張している効果（4.8σ・30σ など）に対しては十分。
  境界の事例は「有意とは言えない」と書く。実機に載せる 1 本を選ぶのは実装上の選択で、結論の根拠には全 seed の平均 ± σ を使う。
- seed を並べた動画 `quad/khr_quad_record_seeds.py`（同じシーンに複数の seed の方策を並べ、軌跡を合成。軸の範囲は版をまたいで固定）。
  v24 は 3 seed が同じ向きに 0.23〜1.07 m 逸れ、v27 は −0.25〜+0.30 m でほぼまっすぐ。

### 5.4 判定の決まり（失敗から作ったもの）

1. **2σ を超えたときだけ差を主張する**。それ未満は「区別できない」と書く。1 seed で傾向を語らない（§10.2 の 4 回の誤り）。
2. **安全（トルク 100 % は絶対に不可）は 2σ 検定ではなく、seed ごとの最悪値で見る**（v26）。
3. **ピーク（最大値）は使わない**。最大値は体数を増やすほど上がる（同じ方策で 8 体 85 % → 32 体 92 % → 128 体 95 %）。99%点と 90%超の時間は体数にほぼ依存しない。
4. **指標ごとに必要な体数が違う**。横ずれは 8 体では信用できない（σ 8 体 0.63 → 128 体 0.06）。今は 128 体。
5. **測っていない軸では何も言えない**。報酬の総点検は前進だけで測っていた。評価の 600 ステップでは押しのカリキュラム（50,000 ステップ）が効かず、押しは実質なかった。
6. **比較の条件をそろえる**。個体差の有無（v20 の誤測定）、ランダム化・観測ノイズ、座標系（v8）を測定器の側で固定する。

### 8.4 GPU の小試験と、カリキュラムが進まない問題（10/14）

| 項目 | 実測（4096 体 × 200 iter、`logs/getup1-gputest/`） |
|---|---|
| 速さ | **54.7 iter/分**（1500 iter 約 27 分、3000 iter 約 55 分）。計画の見積もりの約半分。日中の空き 440 分で 3000 iter を 1 日 約 8 本 |
| GPU メモリ | torch の確保 最大 502 MiB（Genesis 自身の分は `nvidia-smi` が動かず測れなかった） |
| 接触点 | 1 体の最大 24（上限 750）、破綻 0 |

段階は L0 のままなので、接触の多い L1・L2 では遅くなりうる。

**問題: 学習中の成功率が 200 iter とも 0。** `getup/tools/check_success.py` で切り分けた（L0、1024 体）。

| 行動 | 1 秒続けて成功 | 角速度 < 0.5 rad/s の時間 |
|---|---|---|
| 方策の平均（決定的） | 33 % | 82 % |
| 平均 + 探索のゆらぎ（std 0.30、学習中と同じ） | **0 %** | 57 % |
| 行動 0（公称姿勢へ） | 79 % | 100 % |

判定は正しく動いている。学習中は行動に毎歩ゆらぎが乗って胴体の角速度が 0.5 rad/s を超え、「1 秒続けて」に届かない。
**カリキュラムの昇格（学習中の成功率 ≥ 0.75）はこのままでは起きない**。本番の 1500 iter の前に、昇格の判定を直す（判断待ち）:
1. **昇格の判定だけ、ゆらぎに左右されない条件にする**（例: エピソードの最後の 1 秒で、上向き・高さ・関節角・手足の先以外の接地なしを満たす。角速度は外す）。評価の成功の定義は変えない。手間が少なく、学習も遅くならない（おすすめ）。
2. **ときどき学習を止めて決定的な行動で評価する**。判定は成功の定義そのものになるが、学習が約 15 % 遅くなる。

次: 判定を直す → 本番 1500 iter（seed 1）→ 評価のデータで L1 ≥ 90 %・L2 ≥ 70 % → 3 seed。**ゲート S（11/1）**: getup-v1/v2 が L2 で 70 % に届かなければ代わりの案に切り替え、範囲を L1（平らなうつ伏せ）に絞る。

### 8.5 判定の修正と getup-v1 の本番（10/14、詳細は `getup/DIARY.md`）

- **判定**: ユーザーが案 1 を選んだ。昇格の合格を「エピソードの最後の 1 秒、角速度以外の条件で立っている」にした（評価と実機の成功の定義は変えない）。
- **検証の道具**: `getup/eval_getup.py`（評価用の全状態を決定的な方策で。個体差あり・公称、トルク、u0 別、累積成功曲線）。
  **ユーザーの指示で、検証では毎回、段階ごとに 6 エピソードの動画を撮る**（評価と同じ状態・同じ個体差の再生、字幕つき、`media/videos/getup/`）。
  学習 → 検証を続けて回すジョブは `getup/jobs/train_eval.sh`（whisper の解析を避ける）。
- **学習**（seed 1、1500 iter、26.6 分）: iter 200 で L1、400 で L2 へ昇格。L1・L2 でも 56.3 iter/分。

| 段階 | 成功（個体差あり、決定的） | 最後に立つ | 成功までの時間（中央） | トルク 99%点 | 判定 |
|---|---|---|---|---|---|
| L1（平らなうつ伏せ、758 状態） | **87.5 %**（84.9〜89.6） | 95.8 % | 2.1 秒 | 91.1 % | 基準 90 % に届かず |

- **見つかった問題**:
  1. 失敗の 3 分の 2 は、立っているのに揺れ（角速度 0.5 rad/s 以上）が 1 秒収まらない。
  2. **行動が全開か全閉か**: 行動の平均が 9 割の時間 ±1 の外にあり、±1 で切るので探索のゆらぎが効かず、std が 0.30 → 0.92 と増え続けた。
     同じ状態で決定的 89.5 % 対 ゆらぎつき 96.1 %。学習中の成功率（0.97〜0.98）は実機と同じ決定的な評価を過大に見せる。
  3. **トルクがどのエピソードでも 100 % に達する**（開始から中央値 0.08 秒）。行動 0（公称姿勢へ戻すだけ）でも起きる。

- **三宅さんの学習コードを受け取った（10/14 夜、`experiments/getup/miyake_code_review.md`）**: 初期状態は 1 つ・個体差なし・観測に関節角なし・剛性 85 でトルク上限 1.2753 N·m。

|---|---|---|---|---|---|---|---|---|---|
| L1 | 86.0 %（83.4〜88.3） | 87.5 % | **95.1 %** | 89.2 % | 4.2 秒 | **79.7 %** | 91.1 % | 0.12 % | 0.69 % |

  v1 で 100 % の常連だった頭ヨー・肘ヨー（起き上がりに要らない関節）が上位から消えた。
- **残った問題**（診断の道具 `getup/tools/sat_breakdown.py`・`dr_factor_eval.py`）:
  1. 100 % には 98 % のエピソードで一度は達する。上限に達した瞬間のずれ 0.063 rad の内訳は、制限の部分 0.037・**1 歩の遅れのあいだに荷重で押し戻された分 0.028**・ノイズ 0.001。
