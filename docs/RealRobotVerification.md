## 0. はじめに読む — 安全上の最重要事項

実機は**サーボを破損させる／指を挟む危険**がある。以下は毎回必ず守る。

1. **最初はロボットを吊るす／スタンドに載せる**（足が地面に着かない状態）。
   「load policy」で初期姿勢に動く瞬間と、最初の「Go action」は必ず浮かせた状態で。
2. **緊急停止を常に押せる位置に**。コンソールの「Emer. stop」ボタン、または
   最悪サーボ電源（POWER チェックを外す／電源ケーブルを抜く）で止められるようにする。
3. **短時間から**。シミュ計測では多くの関節が定格トルク（1.373 Nm）を連続使用している。
   長時間の連続動作は**発熱・脱調**を招く。数秒〜十数秒ずつ、サーボの発熱を触って確認。
4. **符号キャリブレーション（§5）を飛ばさない**。`genesis2khr_dir` は現在すべて +1＝未検証。
   URDF と逆向きの関節が 1 つでもあると、初期姿勢移行の瞬間に暴れる。
5. **腕（前脚）の荷重確認（§6.3）**。四足では腕サーボが体重を支える。二足では
   していない使い方なので、地面に降ろす前に静的に耐えられるか確かめる。

> **未完了の前提ブロッカー（このうち A・B は実機を歩かせる前に必須）**
> - [A] 符号キャリブレーション（§5）… 現状 `genesis2khr_dir` 全 +1 で未検証
> - [B] 腕の荷重負担検証（§6.3）
> - [C] PC の IP を 192.168.11.16 に固定（§3）… ずれると UDP が通らない

## 1. 全体像（データの流れ）

```
[PC] Meridian_consoleS_quad.py  ──UDP:22224 送信──▶  [ESP32] Meridian_LITE  ──▶ 22 サーボ
  ├ 学習済み policy を 50Hz で推論                          ▲
  └ IMU/サーボ角を観測に変換                       UDP:22222 受信（PC 側）
                              ◀──ESP32→PC 100Hz(10ms)──┘  (IMU/現在角を Meridim90 で返す)
```

- **Meridim90**: PC ⇔ ESP32 を循環する 90 要素配列。サーボ値は奇数インデックスに入る
  （L 系統 = 21 + ID×2、R 系統 = 51 + ID×2）。
- ESP32 は 100Hz（`FRAME_DURATION = 10ms`）で通信、ポリシー推論は 50Hz（`dt = 0.02`）。
- 22 関節すべて（腕 8＝前脚 + 脚 12＝後脚 + 胴/頭 yaw 2）をポリシーが制御する。

## 3. ネットワーク設定（過去の UDP タイムアウトの原因はここ）

**症状**: リモートデスクトップ接続時に「UDP がタイムアウト」して通信できない。
**原因は 2 つ**あり、両方つぶす必要がある。

### 3.1 原因① PC の IP がずれている（最重要）

ESP32 のファーム `keys.h` は**送信先 PC の IP を 192.168.11.16 に固定**している
（`Meridian_LITE/.../src/keys.h:7  WIFI_SEND_IP "192.168.11.16"`）。
一方 PC は DHCP なので、割り当てが 192.168.11.16 以外になると
**ESP32 の返信パケットが PC に届かず**、コンソールは受信タイムアウトになる。

対策（どちらか）:
- **推奨: PC の IP を 192.168.11.16 に固定**する（ルータの DHCP 予約、または OS 側で静的 IP）。
  以後 keys.h を触らずに済む。
- または PC の実 IP に合わせて `keys.h` の `WIFI_SEND_IP` を書き換えて ESP32 を再書き込み。

対応する設定（整合していることを確認）:

| 項目 | 値 | 定義場所 |
|---|---|---|
| SSID | `Buffalo-2G-F080` | `keys.h:5` |
| ESP32 → PC 送信先 | `192.168.11.16`（= PC の IP） | `keys.h:7` |
| PC → ESP32 送信先 | `192.168.11.17`（= ESP32 の IP） | `board_ip.txt` DHCP_SEND |
| PC の受信 IP | `192.168.11.16` | `board_ip.txt` DHCP_RECV |
| ネットワークモード | `0`（DHCP/WiFi） | `board_ip.txt` NETWORK_MODE |
| 受信ポート / 送信ポート | 22222 / 22224 | `Meridian_consoleS_quad.py:205-206` |

> つまり **PC=192.168.11.16、ESP32=192.168.11.17** が正しい対。

### 3.2 原因② リモートデスクトップで受信インターフェースが変わる

Chrome リモートデスクトップ／VPN は仮想 NIC を足すため、「特定 IP に bind」する実装だと
そのインターフェースで受けられなくなる。四足版デプロイヤは対策済み:

- 受信ソケットを **`0.0.0.0`（全インターフェース）に bind** + `SO_REUSEADDR`
  （`Meridian_consoleS_quad.py:1720-1721`）。全 IF で受けるので RDP でも取りこぼさない。

> なお ufw は無関係（過去に誤診）。`sudo ufw status` が「非アクティブ」＝遮断していない。
> 通信不良の主因は 3.1 の IP 不一致。

### 3.3 疎通確認
1. PC と ESP32 を同じ WiFi（Buffalo-2G-F080）に接続。
2. ESP32 を起動し、シリアルモニタで自身の IP（192.168.11.17 か）と WIFI_SEND_IP を確認。
3. PC の IP を確認: `ip addr | grep 192.168.11`（**192.168.11.16 であること**）。
4. `ping 192.168.11.17`（ESP32）が通ること。

## 5. サーボ単体の符号キャリブレーション（★必須・初回のみ）

`genesis2khr_dir` は全関節 +1＝**URDF とサーボの回転方向が一致している保証が無い**状態。
逆符号の関節が 1 つでもあると初期姿勢移行で暴れるため、**歩かせる前に必ず**行う。

手順（ロボットは吊るした状態で）:
1. コンソールを起動（§7.1）し **POWER をオンにしてから一旦オフ**、または各サーボを
   脱力状態にする。**Axis Monitor** でサーボを 1 つずつ手動スライダで少しだけ動かす。
2. その関節が **URDF（Genesis）で正方向に回すのと同じ向き**に動くか確認。
   - 同じ向き → その関節は `+1` のまま。
   - 逆向き → その関節を `-1` にする。
3. 22 関節すべてを確認し、逆だった関節の符号を
   `Meridian_consoleS_quad.py:500` 付近の `genesis2khr_dir` に反映する
   （関節順は §付録の joint_names 順）。
4. 反映後、もう一度「load policy」で初期姿勢に静かに移行するか確認（暴れないこと）。

> 判断基準の作り方: `khr_quad_eval.py` で該当関節を正方向に少し動かした時の見た目を
> 事前に確認しておくと、実機との突き合わせがしやすい。

## 6. 動作確認の本番手順（吊るした状態から）

### 6.1 コンソール起動
```bash
source /home/tora/gsw4/bin/activate
cd /home/tora/gsw4/Meridian_consoleS
python Meridian_consoleS_quad.py 192.168.11.17      # 引数は ESP32 の IP（省略時 board_ip.txt）
```
- 起動後、**Message ウィンドウ**でエラー率・フレーム数・動作周波数を確認。
  受信できていれば周波数が約 100Hz 前後で回る。0 のままなら §3・§9 を確認。

### 6.2 サーボ電源オン
- [ ] **Command ウィンドウの「POWER」チェックをオン** → 全サーボ通電。
- [ ] この時点でロボットは**現在角を保持**するだけ（まだポリシーは動かない）。異音・過電流が
      ないか確認。

### 6.3 初期姿勢への移行（load policy）＋腕の荷重確認
- [ ] **sim2real ウィンドウの「load policy」ボタン**を押す。
      → ポリシーがロードされ、**四足の初期姿勢（`default_joint_angles`）へ移行**する。
      22 関節すべてに指令が入る（腕＝前脚を含む）。
- [ ] 移行が**ゆっくり静か**であること。暴れる／片側だけ逆に動く場合は即 POWER オフ →
      §5 の符号を見直す。
- [ ] **[B] 腕の荷重確認**: 吊るしたまま、前脚（肩・肘）に体重相当の荷重を軽く手で
      かけてみて、サーボが保持できるか（脱調しないか）確認。支えられなければ歩行に進まない。

### 6.4 ポリシー実行（Go action）— まず速度ゼロで
- [ ] sim2real ウィンドウの中央「**O**」ボタンで速度指令をゼロにする（`cmd = 0,0,0`）。
- [ ] **「Go action」ボタン**を押す → 50Hz でポリシー推論開始。
      速度ゼロなので、その場でトロット位相の**足踏み（定常歩容）**をするはず。
- [ ] 挙動が安定していることを確認。おかしければ即「**Emer. stop**」。

### 6.5 段階的に速度を与える（まだ吊るした状態）
矢印ボタン（またはジョイスティック）で指令を少しずつ与える。上限は
`lin_x ±0.3 / lin_y ±0.3 / ang_vel ±0.5`（`Meridian_consoleS_quad.py:378-382`）。

- [ ] **前進**（↑ / go_straight）: 小さい値から。前脚・後脚が対角で動くか。
- [ ] **横**（← → / go_left,right）: 左右差に注意（シミュでも左横が弱い＝左右非対称）。
- [ ] **旋回**（Yaw の↑↓ / turn_left,right）: その場旋回になるか。
- [ ] 各方向で数秒ずつ。**サーボの発熱を触って確認**しながら。
- ※ **後退（↓）は v4〜v8 では未学習**（`lin_vel_x_range=[0,0.4]`）。動かないのが正常、
     無理に指令しない。

### 6.6 接地させて確認（最後・慎重に）
- [ ] 吊るした状態で 6.4〜6.5 が安定して初めて、**低い位置からそっと接地**させる。
- [ ] まず**速度ゼロで自重を支えて立てるか**（腕＝前脚が荷重に耐えるか）。
- [ ] 立てたら**ごく小さい前進**から。転倒に備えて必ず手を添える。
- [ ] 転倒・暴れ・過電流・発熱いずれかで即「Emer. stop」→ POWER オフ。

### 6.7 観測ログの取得（任意・研究記録用）
- [ ] sim2real ウィンドウの「**obs2csv**」で観測データを CSV 保存できる。
      実機とシミュの観測差（sim2real ギャップ）の分析資料になる。

## 7. 終了手順
1. 「Emer. stop」でポリシー停止。
2. 速度指令をゼロ（O）にしてあることを確認。
3. **POWER チェックを外す**（サーボ脱力）。ロボットを支えてから外すこと。
4. コンソールを閉じ、サーボ電源・ESP32 の給電を切る。

## 9. トラブルシューティング

| 症状 | 確認・対処 |
|---|---|
| **UDP タイムアウト／受信 0Hz** | ① PC の IP が **192.168.11.16** か（§3.1、最頻原因）。② ESP32 が同じ WiFi に居て IP 192.168.11.17 か（シリアルモニタ）。③ ping が通るか。④ RDP 経由なら 0.0.0.0 bind 済みなので IF 問題は出ないはず。 |
| **load policy で暴れる／片側逆** | 符号未検証（§5）。`genesis2khr_dir` を 1 関節ずつ直す。即 POWER オフ。 |

| **立てない／前脚が潰れる** | 腕の荷重不足（§6.3）。歩行前に静的荷重で要確認。 |
| **cfgs.pkl / model が無い** | `exp_name`/`ckpt` を実在値に（`ls logs/<exp>/`）。デプロイヤは不在時にエラーで安全に中断する。 |
| **動きが学習時と別物** | `action_scale`/`gait_period`/`def_pos` は cfg から自動取得のはずだが、`exp_name` が意図と違う版を指していないか確認。 |
| **後退で動かない** | 仕様（未学習域）。異常ではない。 |
