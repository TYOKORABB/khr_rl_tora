## 1. 研究の位置づけと全体設計

### 1.1 背景と目的

本研究は、先輩が実装した **KHR-3HV の二足歩行 RL パイプライン**（Genesis + rsl-rl、
および実機動作）を土台に、**同じ機体で四足歩行を新規に獲得する**ことを目的とする。
二足ではなく四足を選ぶことで、より安定した歩行基盤の上で Sim2Real の成功率を検証する。

- ベースリポジトリ: `khr_rl_sample`（先輩由来、二足歩行）を fork した `khr_rl_tora`
- 二足版の中核 `khr_env.py` / `khr_train.py` は**触らず**、四足専用に
  `khr_quad_env*.py` / `khr_train_quad*.py` を新規作成して開発した。
- **ファイル分離の原則**: バージョンごとに env / train / record を複製し、番号を増やす。
  過去バージョンの学習結果 (`logs/`)・研究記録 (`experiments/`)・モデルには一切触れない。
  実機での検証がまだ済んでいないため、資産を完全に分けて追跡可能性を保つ方針。

### 1.2 技術スタック

| 要素 | 内容 |
|---|---|
| シミュレータ | Genesis (`genesis-world` 0.4.6, editable install) |
| RL ライブラリ | rsl-rl-lib ≥ 5.0（現 5.4.0）, PPO, `OnPolicyRunner` |
| DL フレームワーク | PyTorch 2.12.0, tensordict |
| 制御周期 | 50 Hz（`dt = 0.02`）。実機 Meridian は 100 Hz、ポリシーは 50 Hz |
| バックエンド | 学習・録画は GPU（`gs.gpu`）、評価ビューアは CPU |

### 1.3 四足形態の設計思想

二足ヒューマノイドを四足化するための機構的な工夫:

- **腕 = 前脚、脚 = 後脚**。URDF を `khr3hv_12dof.urdf`（腕 fixed）から
  `khr3hv.urdf`（腕 revolute）に変更し、肩・肘を可動にして前脚として使う。
- **胴体を y 軸まわりに +90° ピッチ**させ、「前のめりの四足姿勢」を初期姿勢とする。
  （初期の試作では −90°=後ろ倒れだったが、見た目・心理面から前倒れに変更。理由は §6.2）
- 制御対象は**全 22 関節**（腕 8 + 脚 12 + 胴/頭 yaw 2）。`num_actions = 22`。
- 接地点は 4 点: 前脚 `l_lowerarm` / `r_lowerarm`、後脚 `l_foot` / `r_foot`。
- 歩容は **4 脚トロット（対角ペア）**。対角の (FL,RR) と (FR,RL) を位相 0.5 ずらす。

## 2. システム・アーキテクチャ

> **この章は v1〜v8 時点の設計**（2026-10-14 注記）。現行の v31 との主な違い:
> 観測は 122 次元（v25 で累積ヘディング誤差を追加）、特権観測は 81 次元、報酬は v28 で 27 → 18 項目に整理（`RewardReference.md`）、
> URDF は `khr3hv_symhip.urdf`（v30 で右股関節の可動域を是正、§4.34）。PD ゲイン（kp 25・kd 0.5）と `action_scale` 0.15 は同じ。
> 版ごとに足した報酬と環境は §8.3。

### 2.1 ロコモーション座標系補正（本研究で最も重要な工夫の一つ）

胴体を 90° 倒しているため、**ベース座標系の各軸が世界座標とずれる**
（base-z = 世界前方、base-x = 世界下方）。速度追従・姿勢報酬をベース座標系のまま
計算すると「前進を罰する」等の座標系バグが起きる。これを防ぐため、報酬計算では
初期姿勢クォータニオンで世界と揃えた **loco frame** に変換する。

```python
self.loco_lin_vel = transform_by_quat(self.base_lin_vel, self.init_base_quat)
self.loco_ang_vel = transform_by_quat(self.base_ang_vel, self.init_base_quat)
projected_gravity_rel = transform_by_quat(self.projected_gravity, self.init_base_quat)
```

- 速度・コマンド・姿勢報酬 → **loco frame** で評価。
- 観測の `base_ang_vel` / `projected_gravity` → **base 座標系のまま**残す。
  （実機の IMU=ジャイロ/加速度計は機体座標で測るため、Sim と Real を揃える）
- この非対称が Sim2Real 整合の要。評価スクリプトで速度を測るときも `loco_*` を使う
  必要がある（base 座標のまま測ると旋回が −4% と誤って出る。§4.9 の実測時に遭遇）。

### 2.2 観測（`num_obs = 121`）

Actor が受け取る観測（`_update_observation`）:

| スライス | 内容 | 次元 | 座標系 |
|---|---|---|---|
| [0:3]    | base 角速度 | 3 | base |
| [3:6]    | 投影重力 (projected gravity) | 3 | base |
| [6:9]    | コマンド (vx, vy, wz) × スケール | 3 | loco |
| [9:31]   | 関節角の default からの偏差 | 22 | — |
| [31:53]  | 関節角速度 | 22 | — |
| [53:75]  | 現在の action | 22 | — |
| [75]     | cos(phase) | 1 | 歩容位相 |
| [76]     | sin(phase) | 1 | 歩容位相 |
| [77:99]  | 前ステップの action | 22 | — |
| [99:121] | 前ステップの関節角速度 | 22 | — |

### 2.3 特権観測（critic 用、`num_privileged = 80`）— 非対称 Actor-Critic

critic だけが観測できる真値（ノイズなし＋DR パラメータ）を与える。

`base_ang_vel(3) + projected_gravity(3) + dof_pos偏差(22) + dof_vel(22) + last_dof_vel(22)
+ loco_lin_vel(3) + 追加質量(1) + 摩擦(1) + COMシフト(3) = 80`

- `obs_groups`: actor → `policy`、critic → `policy` + `privileged`。
- loco 系の並進速度・DR パラメータは実機で観測不能なので actor には渡さない。

### 2.4 制御と歩容

- **PD 位置制御**: `kp = 25`, `kd = 0.5`, `action_scale = 0.15`。
  22 関節を `motors_dof_idx`（各関節の `dof_start`）で**インデックス指定バッチ制御**。
  DOF の内部順とコンフィグの関節順が一致しないため、名前→インデックスで明示的に対応付ける。
- **1 ステップの action 遅延**（`simulate_action_latency=True`）— 実機の遅延を模擬。
- **トロット位相**: `gait_period = 0.5 s`、`gait_offsets = [0.0, 0.5, 0.5, 0.0]`（FL,FR,RL,RR）。

### 2.5 報酬関数（`_reward_<name>` を自動探索）

| 報酬項 | 役割 |
|---|---|
| `tracking_lin_vel` | 指令並進速度への追従（**最重要**、v3 で 1.5→4.0） |
| `tracking_ang_vel` | 指令旋回速度への追従 |
| `orientation` | 胴体姿勢を公称に保つ |
| `base_height` | 目標高さの維持 |
| `lin_vel_z` / `ang_vel_xy` | 上下動・不要な回転の抑制 |
| `gait_contact` / `gait_swing` | トロット位相に合った接地/遊脚を促す |
| `contact_no_vel` | 接地脚の滑りを罰する |
| `feet_clearance` | 遊脚を目標高さまで持ち上げる（すり足抑制） |
| `hip_pos` | 脚の横開き（roll/yaw）を罰する。**v8 で hip_yaw/ankle_roll を追加** |
| `feet_orientation` | 足裏を水平に保つ（**v7 で新設**） |
| `alive` | 生存ボーナス |
| `action_rate` / `dof_vel` / `acceleration` / `joint_torques` | 動作の滑らかさ・省トルク |
| `collision` | 自己衝突の罰 |

報酬 scale は init 時に `dt` を一度だけ掛ける。scale と `_reward_` メソッドは名前で
1:1 対応が必須（片方だけあると壊れる）。

### 2.6 Sim2Real レシピ（ドメインランダム化・ノイズ）

先輩の実機二足で実証済みのレシピを v1 から継承:

- **ドメインランダム化**: 摩擦 [0.1,1.5]、追加質量 [−0.1,0.5]kg、COM シフト [−0.02,0.02]m、
  kp スケール [0.9,1.1]、kd スケール [0.8,1.2]。
- **観測ノイズ**: 角速度・重力・関節角・関節速度に加算（実機センサ誤差の模擬）。
- **1 ステップ action 遅延**（前述）。
- **push 外乱**: 学習中に胴体へランダム水平速度キックを与え転倒回復を学ぶ
  （v5 で有効化、v6 でカリキュラム化）。

### 2.7 URDF・関節の物理制約（設計を縛る重要事実）

- **サーボ定格トルク 1.373 Nm**（実機 KONDO サーボ）を URDF の effort limit に設定。
  Genesis がこれを強制するため、飽和すると Sim でも指令通り動けない＝実機で発熱・脱調。
- **膝は片方向のみ**: `knee_pitch` の可動域は **[0.000, 2.793] rad**（負に曲がらない）。
  これが v8 で判明する「膝ロック」問題の物理的根源（§4.10）。
- 足裏水平の幾何条件: `hip_pitch + knee_pitch + ankle_pitch = −θ_base = −1.5708`。
  初期姿勢を作り直すときは常にこの条件を満たす。

## 3. 実行方法（コマンド集）

すべて venv 有効化後、`khr_rl_tora/` 直下から実行（URDF 参照が相対パスのため）。
2026-10-14 のファイル整理で、四脚のスクリプトは `quad/` に移した（`python quad/<ファイル名>`。地図は `quad/README.md`）。
この日誌の §4 の各版に書いてあるコマンドは当時の場所のまま（`python khr_train_quad23.py` は今は `python quad/khr_train_quad23.py`）。
GPU が必要（学習・録画）。録画は Chrome Remote Desktop/VS Code Remote 環境で
ビューアが見えないため、オフスクリーンで MP4 に保存する方式を採る。

```bash
source /home/tora/gsw4/bin/activate
cd /home/tora/gsw4/khr_rl_tora

# 学習（現行 v31）。logs/khr-quadruped31-s1/ に checkpoint と TensorBoard を出力
python quad/khr_train_quad31.py -e khr-quadruped31-s1 -B 4096 -I 4000 --seed 1

# 測定（測定プロトコル固定、128 体）。環境モジュールを明示する
python quad/khr_quad_eval_metrics.py -e khr-quadruped31-s1 --env khr_quad_env21 --ckpt 3999 -n 128

# 録画（ヘッドレス、MP4）。録画には X ディスプレイの指定が要る
export DISPLAY=:1
python quad/khr_quad_record21.py -e khr-quadruped31-s1 --ckpt 3999 --vx 0.3 --seconds 10 -o media/videos/walk_v31_forward.mp4
#   方向指定: --vx 前進 / --vy 横 / --wz 旋回（未指定成分は 0）

# 研究記録の自動生成（report.md + metrics.csv を experiments/<exp>/ に出力）
python quad/khr_quad_report.py -e khr-quadruped31-s1

# 実機（v31、コンソールを使わない画面なし実行）と起き上がりは real/README.md・getup/README.md

# 学習曲線
tensorboard --logdir logs
```

- **注意**: `khr_train_quad*.py` は同名 `exp_name` の `logs/<exp>/` を実行開始時に削除して
  作り直す。残したい結果は別 exp 名にするか事前に退避する。
- **録画スクリプトの世代対応**: 録画スクリプトは環境ごとに複製してある（v31 は `khr_quad_record21.py` = `khr_quad_env21`）。
  v1〜v15 の環境・学習・録画は 2026-10-06 に退避した（今は `quad/archive_v1_v15/`）。
- **ビューア再生**: `python quad/khr_quad_eval.py -e khr-quadruped31-s2 --ckpt 3999 --env khr_quad_env21`（版に合わせて `--env` を選ぶ、§8.3）。
  2026-10-06 の退避から起動できなくなっていたのを 10/14 に直した（§4.37.9）。
- **`export DISPLAY=:1` が必須**: シェルで `DISPLAY` 未設定でも `/tmp/.X11-unix/X1` が
  存在するため、これを指定しないと録画が "No display" で失敗する。

## 4. バージョン別 開発日記（v1〜v31）

各バージョンは env / train を複製して番号を増やし、直前版からの差分のみを変える
（ablation を明確化するため）。共通の固定値: `num_envs=4096`, `seed=1`,
PPO `[128,64,32]` ELU, `kp=25/kd=0.5`, `action_scale=0.15`, `init_std=0.5`,
`entropy_coef=0.01`, `lr=1e-3`, `gamma=0.99/lam=0.95`。

### 4.1 v1 — 初の四足歩行成功（`khr-quadruped`, 3000 iter）

- **動機**: 二足版 `khr_env.py` を四足化し、まず「転ばずに前進する」ことを成立させる。
- **主な実装**: `khr_quad_env.py` を新規構築（22DOF、トロット、loco frame 補正、121 次元観測、
  非対称 actor-critic）。コマンドは前進のみ `vx ∈ [0.0, 0.2]`。
- **初期のつまずきと修正**: 最初の run はエピソード長 12.5 のまま伸びず**完全失敗**。
  探索 std が早期崩壊していたため、`init_std 1.0→0.5`, `action_scale→0.15`,
  `entropy_coef→0.01` に緩めて**探索崩壊を回避**（commit `e8d346b`）。
- **結果**: エピソード長 12.5 → 1001（転ばず立てる）。前進追従報酬 最終 1.45。
  ただし **実測速度 約 0.036 m/s vs 指令 0.15**＝**すり足で非常に遅い**。
- **分析 / 次への課題**: 歩けたが遅い。速さと自然さの改善が必要。

### 4.2 v2 — 「速く・自然に」の試み（設定 3 箇所のみ、失敗から学ぶ）

- **動機**: 新報酬を足さず既存パラメータ調整だけで v1 の遅さ・すり足を改善。
- **変更点**: `tracking_sigma 0.25→0.15`（追従を厳しく）、`vx [0,0.2]→[0,0.4]`、
  `feet_height_target 0.035→0.06`（遊脚を高く）。
- **結果**: **かえって遅くなった**（前進追従 最終 1.12、v1 の 1.45 より低下）。
- **分析（重要）**: 追従判定を厳しくしても速くならなかった。報酬内訳を精査すると
  **静止でも前進追従報酬の約 94% が得られる**一方、動くと罰（acceleration /
  similar_to_default / action_rate）が増え「**歩く報酬 < 歩く罰**」となり、
  静止が最適解になっていた（探索は潰れていない＝報酬設計の問題）。
- **次への課題**: 報酬「バランス」の是正。厳しさではなく割の合う設計に。

### 4.3 v3 — 報酬バランス是正（ブレークスルー）

- **動機**: v2 の診断に基づき「歩くこと」を明確に割に合わせる（設定 4 箇所のみ）。
- **変更点**: `tracking_lin_vel 1.5→4.0`、`similar_to_default −0.1→−0.02`、
  `action_rate −0.05→−0.02`、`acceleration −1e-4→−2e-5`（実効最大の罰を 1/5）。
  sigma=0.15 / command[0,0.4] / feet_height=0.06 は v2 を維持。
- **結果**: **前進追従報酬 最終 3.89（v1 の 2.7 倍）**。指令 0.3 に対し実速度 0.257 m/s
  で**追従 86%**。「実際に速く歩く」四足が完成。
- **先行研究の裏付け**: Rudin et al. 2021 (legged_gym) の ablation で速度追従報酬が
  最重要と示されており、`tracking_lin_vel` の増強が効いたことと整合。
- **分析 / 次への課題**: 前進は解決。次は「コマンドで自在に歩ける」全方向化へ。

### 4.4 v4 (1a) — 全方向歩行への拡張

- **動機**: Sim2Real に向け、まず横移動・旋回を含む「自在に歩ける四足」に仕上げる。
- **変更点**: `command_cfg` のみ。`vy [0,0]→[−0.15,0.15]`、`wz [0,0]→[−0.5,0.5]`。
  `vx [0,0.4]` は据え置き（変更を「横・旋回の追加」だけに限定し ablation を明確化）。
  報酬・環境は v3 のまま（環境は既に x/y と yaw を扱えるためコマンド範囲を開くだけで学習可）。
- **結果**: 全方向歩行を獲得。前進追従報酬 最終 3.91。前進追従 ≈86%、**横 ≈77%**。
  足裏の傾き 12.4°、トルク定格 95%超に張り付く関節 2/22。**以降の比較基準（ベースライン）**。
- **分析 / 次への課題**: 押し外乱に対する頑健性は横 −y が最弱（0.8 で耐え 1.0 で全滅）。
  実機に向けて外乱耐性を上げたい（→ push 外乱の導入）。

### 4.5 v5 (1b) — push 外乱で頑健化（頑健性↔性能のトレードオフを観測）

- **動機**: 先輩 config に枠だけあって未実装だった push を有効化し、実機の外乱耐性を上げる。
- **実装**: 環境を **`khr_quad_env2.py`** に変更し `_push_robots()` を追加。
  一定間隔で胴体の水平速度にランダムキックを加える。
  `push_interval_s 5→3`、`max_push_vel_xy 0.2→1.0`、push モードを有効化。
- **結果**: 前方・横 +y の押し耐性を +0.5 m/s 改善。しかし**歩行追従が低下**
  （前進 93→69%、横 78→35%、旋回 87→64%）、後方耐性はやや悪化、最弱の横 −y は不変。
- **分析**: **最初から最大 1.0 m/s の強い外乱**を与えたため方策が「守り」に入り歩行が鈍った。
  典型的な**頑健性↔性能のトレードオフ**。
- **次への課題**: 外乱を徐々に強めるカリキュラムで両立を狙う。

### 4.6 v6 (1b) — push カリキュラム（頑健性と性能の両立）

- **動機**: v5 のトレードオフを、外乱をカリキュラムで漸増させて解消する。
- **実装**: 環境を **`khr_quad_env3.py`** に変更。`push_curriculum_steps=50000` を追加し、
  `push_scale = min(1.0, step_counter / curriculum_steps)` で押し強度を 0→max に線形増加。
  まず歩行を習得させ、その後で押しを強める。押し間隔・最大強度 (3s, 1.0m/s) は v5 のまま。
- **結果**: 前進追従報酬 最終 3.49。歩行性能を保ちつつ外乱耐性を回復（v5 の劣化を解消）。
- **分析 / 次への課題**: 頑健性は改善したが、v4→v6 の過程で**足の動きが不自然**に。
  「足の縁で歩く」挙動が悪化していることが実測で判明。

### 4.7 v7 — 足裏の水平接地（ベタ足歩行）

- **動機**: v4→v6 で足裏が傾き「縁で歩く」挙動が悪化していた。実測で
  足裏傾き v4 12.4° → v5 22.7° → v6 24.3°、`ankle_pitch` −6.3→−34.4°、
  `ankle_roll` −12.6→−29.7°、`hip_yaw` +6.0→+20.0°（脚が外にねじれる）。
  これは push に耐える「踏ん張り姿勢」に流れた副作用で、`ankle_roll`/`hip_yaw` が
  **定格トルク 1.373Nm を連続使用**する原因＝実機の発熱・脱調リスクでもあった。
- **実装**: 環境を **`khr_quad_env4.py`** に変更し `_reward_feet_orientation` を新設
  （足裏法線の水平成分を罰する＝水平なら 0）。`reward_scales` に
  `"feet_orientation": -1.0` を追加。push カリキュラムは v6 のまま維持。
- **結果**: 足裏傾きが大幅改善（≈11.0°）。前進追従報酬 最終 3.53。
- **分析（重要な副作用の発見）**: 足裏は水平化したが、**定格 95%超に張り付く関節が
  7/22 に増加**。`hip_yaw +20.0°`、`ankle_roll −29.7°` と脚が大きく外に開いたまま保持され、
  それらが時間の 98〜99% トルク飽和していた。さらに詳細計測で、後脚の主動力である
  **膝がほとんど動いていない**ことが判明（次で解明）。
- **次への課題**: 「関節が動かない・ぎこちない」の根本原因を突き止め、トルク飽和を下げる。

### 4.8 v8 — 膝の解放と脚の横開き抑制（最新・Sim2Real 最有力）

- **動機**: v7 の診断で 2 つの根本問題が判明。
  1. **膝ロック**: `knee_pitch` の初期値 0.10 rad は機械的下限 0.0 の**わずか 5.7° 上**。
     膝は片方向にしか曲がらないため、主動力の膝がハードストップに押し付けられ、
     **可動幅わずか 6.4° なのにトルク張り付き 100%**。これが「関節が動かない・
     ぎこちない」の正体だった。
  2. **脚の横開き**: `hip_yaw ±20°`, `ankle_roll ±30°` で開いたまま保持され、その 4 関節が
     定格 95%超に時間の 98〜99% 張り付き（発熱・脱調リスク）。
- **実装**:
  - **初期姿勢の再導出**（足裏水平条件 hip+knee+ankle=−1.5708 を維持したまま膝に可動余地）:
    `knee_pitch 0.10→0.40`（下限までの余裕 5.7°→22.9°）、`hip_pitch −1.671→−1.770`、
    `ankle_pitch 0.0→−0.201`、`shoulder_pitch −1.5708→−1.771`、`elbow_pitch 0.0→0.20`
    （後脚が短くなる分、前脚も曲げてリーチを一致。前後差 3.0mm→2.0mm）、
    `base_init_pos z 0.197→0.1946`、`base_height_target` も同値。
  - 環境を **`khr_quad_env5.py`** に変更し、`_reward_hip_pos` の罰対象に
    `hip_yaw` / `ankle_roll` を追加（横開きをさらに抑制）。
  - **静的検証**: 新姿勢は 400 step で base_z 0.193 維持・x ずれ 1.7mm と安定。
    静止保持時のトルク定格 95%超は 0/22（膝はわずか 7〜8%）。
- **結果（v7 → v8）**:

  | 指標 | v7 | v8 |
  |---|---|---|
  | 膝の可動幅 | 6.4° | **22.3°**（3.5 倍） |
  | 膝のトルク張り付き | 100% | **3%** |
  | 定格 95%超に張り付く関節数 | 7/22 | **2/22**（v4 水準まで回復） |
  | `hip_yaw` のズレ | +20.0° | **+1.7°** |
  | `ankle_roll` のズレ | −29.7° | **−5.3°** |
  | 足裏の傾き | ≈11.0° | **7.5°（全版で最良）** |
  | 前進追従 | 95% | 92% |
  | 横追従 | 58% | 62% |
  | 旋回追従 | 85% | 91% |
  | 後方 push 耐性 | 1.5 | **2.5+ m/s** |
  | 横 push 耐性 (+y/−y) | 1.5 | 1.2 m/s |

- **分析**: 主目的（膝の解放・トルク飽和の低減）を達成。実機で最も効くのは
  **トルク飽和の解消（7/22→2/22）**で、発熱・脱調という実害を直接下げる。動作の自然さ・
  足裏接地・旋回性能も最良。**トレードオフ**として横 push 耐性が 1.5→1.2 に低下したが、
  これは v7 の「脚を大きく開いて踏ん張る姿勢」（＝トルク飽和の原因そのもの）を
  正常化した代償であり想定内。
- **総合評価**: **v8 が現時点で Sim2Real 用の最良モデル**。

### 4.10 v8 の実機動作確認と教授フィードバック

v8 を実機 KHR-3HV で動作させ、教授に確認いただいた（研究の方向性・進捗とも良好との評価）。
一方で 3 つの指摘を受けた: **① 動きがぎこちない、② モーターのトルクが最大になっている可能性、
③ 後退ができない**。以後はシミュ上の四足歩行精度の向上に軸足を移す。

実測で診断した結果（v8, ノイズ/DR無効）、①②の根本原因が判明した:

- **後脚 l/r_hip_pitch が全歩行モードで常時トルク100%飽和**し、PD目標角から
  **50〜66度ズレ続ける**（＝指令位置に到達できない bang-bang 制御）。他20関節は1〜4°で正常追従。
- **静止保持なら同姿勢を43%トルクで支えられ、定格95%超は0/22**。つまりハードが弱いのではなく、
  **方策がアクチュエータ飽和を悪用した歩容を学習していた**（報酬が飽和をほぼ罰していなかった）。
- ③ は `lin_vel_x_range=[0,0.4]` で負の速度を一度も学習していなかったため（バグではない）。

この診断が v9 の設計根拠。詳細は `experiments/khr-quadruped9/investigation.md`。

### 4.13 v11 — ❌ 失敗: 瞬時 yaw 罰で並進が崩壊（重要な失敗記録）

- **動機**: v10 の残課題＝前進時の yaw ドリフト（約3°/秒、10秒で27°、旋回半径4m、直進1.7mで
  横ずれ0.30m）。Sim2Real 前の直進性向上として対処する狙いだった。
- **実装（1点のみ）**: `_reward_drift` の yaw 成分を横の**5倍**に重み付け（`yaw_drift_weight=5.0`）。
- **結果: 並進が崩壊**。前進28%/後退0%/横0%（旋回のみ85〜92%生存）。`tracking_lin_vel` は
  3.56→0.318。前進の軌跡は正味変位ほぼ0＝「その場で揺れるだけ」。
- **原因**: トロットは前進時に**本来 yaw が周期的に揺れる**。これを5倍で強く罰したため
  「並進すると罰される→動かない方が得」という degenerate 解に収束。旋回だけ残ったのは
  指令旋回時は `wz_err≈0` で罰がかからないため。`tracking_lin_vel` が exp 罰で低速でも
  報酬が残ることも後押しした。

### 4.17 v15 — 遊脚の解放（🟡 主目的は未達だが**膝が動かない真因を特定**）

- **動機**: v14 で `base_height` 仮説が反証されたため、次の本命仮説を検証。

- **仮説**: `_reward_feet_orientation`（−1.0, v7導入）に **contact マスクが無く**、接地/遊脚を
  区別せず常に足裏を水平に保たせていた。遊脚中に膝を曲げると足裏が傾いて罰される →

- **実装**（環境 `khr_quad_env12.py`、変更1点）: `_reward_feet_orientation` を

- **結果: 仮説は部分的に正しかったが、主目的は未達**。

  | 指標 | v14 | v15 |
  |---|---|---|
  | l_ankle 負荷 | **32%** | **24%（低下＝仮説の裏付け）** |
  | l_knee ROM / r_knee ROM | 6.4° / 14.8° | 7.2° / 7.8°（**回復せず**） |

- **【最大の収穫】真因の特定**: PD の**指令角**と**実測角**の可動域を比較したところ、

  | 関節 | 指令ROM | 実測ROM | 追従率 |
  |---|---|---|---|
  | l_knee_pitch | **6.8°** | 7.8° | 114% |
  | r_knee_pitch | **7.4°** | 8.4° | 115% |
  | l_hip_pitch | 14.2° | 15.6° | 110% |

### 4.18 v16 — 遊脚期の膝屈曲報酬（❌ 報酬ハック：膝を「曲げっぱなし」にされた）

- **動機**: v15 で「膝を動かす**指令自体が出ていない**＝報酬起因」と真因が確定したため、
  **遊脚期の膝屈曲を直接報酬にする**（犬・馬が遊脚期に脚を短縮する原理）。
- **実装**（環境 `khr_quad_env13.py`、変更1点）: `_reward_knee_flexion`（scale 2.0）を新設。
  後脚の膝が遊脚期に default(0.40rad) より曲がっているほど加点（目標 +0.30rad、sharpness 10）。
  接地期は対象外。
- **結果: 報酬ハックが発生し失敗**。学習ログでは `rew_knee_flexion = 1.4803` と高得点なのに、
  **膝 ROM はむしろ縮小**（v15 7.2/7.8° → **2.7/2.8°**）。原因を膝角度の分布で特定した:

  | 膝 | 平均角度 | swing平均 | stance平均 | **swing−stance差** | 実測ROM |
  |---|---|---|---|---|---|
  | l_knee | 0.685 rad | 0.700 | 0.673 | **+1.5°** | 2.7° |
  | r_knee | **0.700 rad** | 0.703 | 0.697 | **+0.3°** | 2.8° |

  （default 0.40 rad、報酬の目標 0.70 rad）
  **膝は常時 0.70 rad ＝報酬の目標角度で固定**されており、「曲げて伸ばす」動作をしていない。
- **原因（設計の欠陥）**: 報酬が **膝の「位置（絶対的な屈曲量）」** を見ていた。
  この定義では「常に目標角度で固定する」だけで満点が取れ、関節を動かす必要がない。
  むしろ動かすと目標から外れて損をするうえ `dof_vel`/`action_rate` のコストもかかるため、
  **固定が最適解**になった。「膝を曲げる」ことは報酬にしたが、
  **「膝を曲げ伸ばしする（動かす）」ことは報酬にしていなかった**。
- **副作用**: 接地時の足裏傾きが 13.5° → **16.1°** に悪化、後脚の接地率左右差も 1.0 → **10.8pt** に後退。
- **維持できたもの**: 飽和 0/22・ピーク63%、前進追従75%、後退は61→69%に改善。
- **学び（一般的な教訓）**: **「望む状態」ではなく「望む変化」を報酬にすべき**。
  位置を報酬にすると、その位置で静止するのが最適解になる。周期運動を促すなら
  **位相間の差分・速度・基準からの相対量**を報酬にする必要がある。
  これは v13 で `feet_clearance` を「絶対高さ」から「接地基準からの相対高さ」へ直したのと
  **同じ構造の誤り**であり、報酬設計の一般則として卒論に記載する価値がある。
- **次（v17候補）**: 膝の **swing−stance 差**を報酬にする（接地時の膝角度の EMA を基準に、
  遊脚中に追加で曲がった分だけを加点＝定角度で固定すると差がゼロになりハックできない）。
  v13 の `foot_ref_z`（接地基準）と同じ発想。併せて接地の質（足裏傾き16.1°）への対処も要。
  詳細は `experiments/khr-quadruped16/results.md`。

### 4.22 v20 — 実機で指摘された3課題への対策（②完全解決・①改善／❌トルクと足裏が後退）

- **動機**: v19 の実機動作でユーザが感じた ①前進なのに横へ逸れる ②後退が遅い
  ③旋回で中心がずれる の3点。v19 の軌跡を実測して原因を特定した。

  - **②**: `lin_vel_x_range = [-0.2, 0.3]` と**指令範囲が前後非対称**（追従率は前後とも8割で同等、
    つまり追従の失敗ではなく指令設計の問題）。

    前後に流れても罰されない状態だった。
  - **①**: 原因は**未確定**。当初「サーボのトリム誤差が主因」と断定したが、**証明されていない**
    （後述の訂正を参照）。
- **実装**（環境 `khr_quad_env16.py`、3点）:
  - [③] `_reward_drift` に **vx 誤差を追加**
  - [②] `lin_vel_x_range` **[-0.2,0.3] → [-0.3,0.3]**（前後対称化）
  - [①] **関節角オフセットのDRを新設**（±0.02rad=±1.15°、PD目標角に加算＝系統誤差として作用）
- **結果**:

  |---|---|---|
  | **後退の速度** | 0.164 m/s（前進より34%遅い） | **0.269 m/s（前進0.266とほぼ同等）** |

  | **ピーク\|τ\|（個体差なし）** | 81% | 81〜86% |

  - ✅✅ **② 後退は完全解決**。指令範囲を対称にしただけで 0.164→0.269 m/s。
    **原因が指令設計であったことが裏付けられた**。
  - ✅ **① 横ずれは改善**。個体差を与えた条件でも 12.3%→8.3%、ばらつきも ±9.9→±6.5 と縮小し、
    **関節オフセットDRは「個体差への頑健性」という狙いを達成**した。
  - 🟡 **③ は左旋回で大幅改善（0.033→0.005m）だが右旋回は悪化（0.024→0.062m）**。左右非対称。
  - ❌ **個体差があるとトルクのピークが100%に達する**（v19 は同条件で82%）。
    90%超の延べ時間は0.010%と極めて短く持続飽和ではないが、
    **「100%は絶対NG」という要件に抵触**する。
  - ❌ **足裏の全面接地が後退**（8.4→13.3°）、左右対称性も後退（3.0→9.5pt）。

  （`config.h` の `IDL_TRIM`/`IDR_TRIM`）に左右で最大21°の差がある、(b) DR に関節オフセットが

- **測定上の発見（修正済み）**: `khr_quad_plot_torque.py` が `randomize_joint_offset` を
  無効化しておらず、**v20 だけ個体差ありの条件で測っていた**（ピークが見かけ上100%）。
  既定で無効化し `--joint-offset` で明示指定する方式に修正。**版間比較の公平性の問題**だった。
- **結論**: 3課題のうち②を完全解決し①も改善したが、**トルク安全性と足裏接地という
  既に獲得していた成果を損なった**。**実機に載せるなら依然 v19 が安全側**。
- **次（v21候補）**: v20 の良い変更（②③の設計＋オフセットDR）を維持しつつ、
  ①`torque_limits` -5.0→-8.0 か `torque_soft_ratio` 0.65→0.55 でトルク余裕を回復、

  詳細は `experiments/khr-quadruped20/results.md`。

### 4.24 v22 — 左右対称性を「正しい量」で是正（✅✅14.0→2.2pt／❌トルク90%超・速度未回復）

- **動機**: v21 は対称性の対策（`leg_load_balance` −1.0→−2.0）が裏目に出て

- **診断（本研究3例目の同型の誤り）**: `leg_load_balance` は
  **「左右後脚のトルク EMA の差」**を罰する報酬であり、**「接地時間(duty)の左右差」とは別の量**。
  トルクを均衡させても接地タイミングは揃わない。**「罰している量」と「直したい量」が不一致**だった。

  | 版 | 誤り | 修正 |
  |---|---|---|
  | v13 | `feet_clearance` が**絶対高さ**目標（前脚は立位で既に超過＝足上げを罰していた） | 接地基準からの**相対**量へ |
  | v16 | 膝の**絶対角度**を報酬化 → 目標角度で固定する報酬ハック | swing−stance の**差分**へ（v17） |
  | **v21** | 対称性のために**トルク差**を罰した | **接地duty差**へ（v22） |

- **実装**（環境 `khr_quad_env17.py`、3点）:
  - **`_reward_contact_duty_balance` を新設（−10.0）**: 後脚の**接地duty の EMA の左右差**を直接罰す
    （α=0.01 ≒ 4歩容周期、初期値0.5で中立）
  - `leg_load_balance` **−2.0 → −1.0 に戻す**
  - `tracking_lin_vel` **5.0 → 6.0**（前進速度の回復を狙う）
- **結果**:

  | 指標 | v19 | v21 | **v22** |
  |---|---|---|---|
  | **後脚 接地率 左右差** | 3.0pt | 14.0pt | **2.2pt** ✅✅ |
  | **後脚 足裏傾き** | 8.4° | 7.8° | **6.4°** ✅ |
  | **膝 ROM** | 26〜30° | 45〜47° | **28.3/26.1°** ✅ |
  | 後退速度 | 0.164 | 0.260 | **0.256** ✅ |
  | 左旋回 中心ずれ | 0.033 | 0.043 | **0.010 m** ✅ |
  | **ピーク\|τ\|（個体差あり）** | 81% | **82%** | **93%** ❌ |
  | **前進速度** | 0.248 | 0.223 | **0.218** ❌ |
  | 横ずれ（個体差なし） | 7.5% | 9.3% | 12.2% ❌ |

- **評価**:
  - ✅✅ **主目的の対称性が 14.0→2.2pt と大幅是正**（全版で最良）。
    **v21 でトルク差を罰しても直らなかった問題が、「直したい量そのもの」を測る報酬に
    変えた途端に解決**した。設計則の有効性が3例目にして最も明快に実証された。
  - ✅ 足裏 6.4°（v18 の 6.1° に迫る過去最良水準）、膝 ROM も理想レンジへ回帰。
  - ❌ **`tracking_lin_vel` 5.0→6.0 は完全に割に合わなかった**:
    速度は 0.223→0.218 と**全く改善せず**、**トルクのピークだけ +11pt（82→93%）押し上げた**。
    速度を制限しているのは追従報酬の弱さではなく**トルク罰と `feet_orientation` の制約**であり、
    誘因だけ強めても制約領域では速度は伸びず、瞬間的に強く踏み込むだけに終わった。
  - ❌ 横ずれは悪化（9.3→12.2%）。**接地対称性と直進性は別問題**であることが分かった。
- **次（v23）**: **`tracking_lin_vel` を 6.0→5.0 に戻すだけ**で「良いとこ取り」ができる見込み
  （トルクは v21 水準82%へ復帰、対称性2.2pt・足裏6.4°・膝27°は tracking と独立なので維持）。
  詳細は `experiments/khr-quadruped22/results.md`。

### 4.25 再現性の確認（seed 2・3・4）— ノイズ床を確定させる study

v20〜v23 の比較で、**パラメータ変更の効果よりも学習の run-to-run ばらつきの方が大きい**
疑いが強まったため、版を重ねる前に**ノイズ床（同一設定を繰り返したときのばらつき）**を確定させる。

#### 動機（何が問題だったか）

1. **v22 と v23 は `tracking_lin_vel` の1点しか違わない**（学習前に機械的に検証済み）のに、
   後脚の接地率 左右差が **2.2 → 12.5 pt**、横ずれが **13.9 → 6.1%** と大きく入れ替わった。
   `tracking_lin_vel` が対称性を直接左右するとは考えにくい。
2. **ピークトルクは稀事象**だった。同一ポリシー(v23)で乱数のみ変えると
   ピークは 96〜97% と出るが、**90%超は全サンプルの 0.003〜0.005%（数万個中の数個）**、
   **99% の時間は 60% 以下**、平均は 18%。
   「v20 はピーク100%だから危険／v21 は82%で安全」という判断は、
   安定統計（平均・分位点）にはほとんど現れない。
3. **全バージョンが seed=1 のみ**で比較されている（`ResearchPlan.md` の不足#2）。
   ⇒ v20〜v23 の細かな優劣は、**ノイズを追っていた可能性がある**。

#### 前提条件（実験設定）

| 項目 | 内容 |
|---|---|
| **対象設定** | **v23 を固定**（`khr_train_quad23.py` + `khr_quad_env17.py`）。報酬・DR・指令範囲はすべて不変 |
| **変えるもの** | **乱数 seed のみ**。seed = 1（既存の v23）+ **2, 3, 4** の計 **4 本** |
| **seed の作用範囲** | `gs.init(seed=...)` → Genesis の `set_random_seed()` が `random` / `numpy` / `torch` / `torch.cuda` を seed する。`gs.init` は env・runner の生成**前**に呼ばれるため、**環境のランダム化と PPO のネットワーク初期化の両方**が seed の配下にある（＝seed を変えれば学習全体が変わる） |
| **固定条件** | `num_envs=4096`, `max_iterations=4000`, 同一 GPU、同一コード（git 管理下） |
| **exp 名** | `khr-quadruped23-s2 / -s3 / -s4`（学習スクリプトは同名 `logs/<exp>` を削除して作り直すため、seed ごとに分ける） |

#### 評価プロトコル（版間比較で用いたものと同一に固定）

- **条件**: 個体差（関節オフセット ±1.15°）**なし／あり**の両方。8体、前進 0.3、10秒（立ち上がり2秒除外）。
- **トルク**: **平均・99%点・99.9%点・90%超の時間**を主指標とする。
  **ピーク（最大値）は稀事象のため主指標にしない**（上記の動機2）。
- **歩容**: 後脚の接地率 左右差、足裏傾き（接地時平均）、膝 ROM、クリアランス。
- **軌跡**: 前進／後退の速度、横ずれ率、旋回の中心ずれ。

#### 判定基準

各指標について 4 seed の **平均 ± 標準偏差** を算出し、
**版間の差が概ね 2σ 未満なら「区別できない（ノイズの範囲）」**として扱う。
これにより、v19〜v23 のどの差が実在するのかを初めて根拠を持って言えるようになる。

```bash
python khr_train_quad23.py -e khr-quadruped23-s2 -B 4096 -I 4000 --seed 2
python khr_train_quad23.py -e khr-quadruped23-s3 -B 4096 -I 4000 --seed 3
python khr_train_quad23.py -e khr-quadruped23-s4 -B 4096 -I 4000 --seed 4
```

#### 参考文献

本 study の必要性と、評価指標の選び方について直接の根拠となる文献。
（書誌情報は記憶に基づくため、**卒論に引用する際は原典で確認すること**。）

1. **Henderson, P. et al. "Deep Reinforcement Learning that Matters." AAAI 2018.**
   乱数 seed の違いだけで学習曲線・最終性能が大きく変わりうること、
   **少数 seed での比較は誤った結論を導きうる**ことを実験的に示した。
   → 本研究が v20〜v23 で直面した問題そのもの。複数 seed を取る根拠。
2. **Agarwal, R. et al. "Deep Reinforcement Learning at the Edge of the Statistical Precipice." NeurIPS 2021.**
   少数 run の**点推定は信頼できない**として、区間推定（層化ブートストラップ信頼区間）や
   **外れ値に強い集約量**（interquartile mean 等）の使用を提唱。
   → 本研究で**「ピーク（最大値）」を主指標にしたのが不適切**だった件に直結。
   平均・分位点へ切り替える根拠。
3. **Colas, C. et al. "How Many Random Seeds? Statistical Power Analysis in Deep Reinforcement Learning." 2018.**
   比較に必要な seed 数を統計的検出力の観点から論じる。
   → 「何本走らせれば十分か」を判断する根拠。
4. **Rudin, N. et al. "Learning to Walk in Minutes Using Massively Parallel Deep Reinforcement Learning." CoRL 2021.**
   本研究の学習設定（大規模並列環境での PPO、legged_gym 系の報酬設計・push カリキュラム）の基礎。
   v1 以降の設計はこの系譜に沿っている。

#### この study が卒論にもたらすもの

- **`ResearchPlan.md` の不足#2「再現性」がそのまま埋まる**（全実験 seed=1 問題の解消）。
- 「どの設計が本当に効いたのか」を **ノイズ床と比較して主張できる**ようになり、
  Phase 2 の ablation の解釈にも必須の基準値となる。
- 評価指標の選び方（稀事象 vs 安定統計）という**方法論上の知見**が加わる。
  これは v13/v16/v21 の「**測る対象を誤る**」類型と同根であり、

  **主張A** ← `torque_limits` の ablation、**主張C** ← `knee_swing_flexion` の ablation。

### 4.27 v24 → v25 — 「罰するだけ」では直らず、「観測させて」直った（横ずれ 7.8% → 1.4%）

> **本節は 2026-08-20 に全面改訂した。** 初版には「v24 が横ずれを 7.84%→2.53%、2.8σ で改善した」と
> 書いていたが、**これは誤りである**。1 回きりの測定（乱数種を完全に固定していなかった）を
> そのまま結論にしていた。測り直すと v24 の横ずれは **7.65±0.34%** で、2.53% は再現しない。
> さらに seed 2・3 で追認したところ **v24 は改善せず、むしろ悪化**していた。
> 以下は seed 1・2・3 × 3 回反復測定で取り直した確定版である。

#### 出発点の課題

Phase 2 の計測で残った最大の課題は「前進を指令しているのに横へ逸れる（7〜8%）」だった。診断は 2 点。

1. **横滑り（カニ歩き）ではない**: 機体座標の横速度 `vy` の平均は −0.0006 m/s とほぼゼロ。
2. **yaw が累積している**: 10 秒間の yaw 累積が seed ごとに −9.0 〜 +5.1 度。
   機体は真横へ滑るのではなく、**少しずつ向きを変えながら進んでいる**。

既存の `heading_drift` は **yaw 角速度の EMA** を罰していた。しかし角速度がゼロでも
**過去に曲がった分の「向きのずれ」は残り続ける**。寄与は 0.0099 と `drift`（0.25〜0.77）の
1/25 以下で、事実上無視されていた。

→ **罰すべきは「曲がる速さ（率）」ではなく「曲がってしまった量（累積）」だ**と考えた。

#### v24: 累積ヘディング誤差を「罰した」— 効かなかった

`heading_err = heading_err·(1−0.002) + (ω_z − ω_z指令)·dt`（時定数 ≈10 秒）を状態として持ち、
`_reward_heading_error = heading_err²` を scale −10.0 で罰する。環境は `khr_quad_env18.py`。

| 条件 | v23 baseline (4seed) | 2σ | **v24 (3seed)** | 判定 |
|---|---|---|---|---|
| 横ずれ率（個体差なし） | 7.84 ± 1.89 % | 3.78 | **12.95 ± 4.66 %** | ❌ **悪化** |
| 横ずれ率（個体差あり） | 8.08 ± 2.07 % | 4.15 | 12.18 ± 4.65 % | ❌ 悪化傾向 |

**seed ごとの横ずれ率は 7.65 / 12.22 / 18.99% と 2.5 倍ばらついた。**
seed 1 だけ見れば「baseline と同等」、seed 3 だけ見れば「大幅悪化」と正反対の結論になる。

#### 診断: 報酬が「方策の観測できない隠れ状態」に依存していた（POMDP）

v24 は `heading_err` を**罰した**が、**観測には入れていなかった**。
方策が自分の旋回バイアスを検出できるか、数値で確認する。

| 量 | 値 |
|---|---|
| 個体差が生む yaw バイアス | ≈ 0.022 rad/s |
| 観測 `ang_vel` のノイズ振幅（`obs_noise=0.1` / `obs_scales=0.25`） | ± 0.4 rad/s |
| **S/N 比** | **≈ 1/18** |

バイアスは**瞬時観測ノイズの 1/18 に埋もれている**。方策は MLP（履歴は `last_actions`/
`last_dof_vel` の 1 ステップのみ）で、**時間方向に平均化する手段を持たない**。
したがって**自分の旋回バイアスを原理的に検出できない**。
記憶を持たない方策に取れる最善は「yaw 角速度の**分散**を下げる」ことであって、
「**バイアス**を打ち消す」ことではない。**罰だけ与えても打ち消しようがなかった。**

#### v25: 同じ量を「観測にも入れた」— 直った

変更は 1 点だけ。actor 観測の末尾に `heading_err × 5.0` を追加（`num_obs` 121→122）、
critic の特権観測にもノイズなしで追加。環境は `khr_quad_env19.py`。
**漏れ積分（τ≈10 秒 ＝ 500 ステップ）がローパスとして働き、ノイズを √500 ≈ 22 倍平均化する。**
これでバイアスがノイズ床の上に出て、**罰されている量が方策から可観測になる。**

実機ではジャイロ積分で得るため、積分誤差を想定した観測ノイズ（±0.05 rad ＝ ±2.9°）も載せた。
漏れ積分は時定数 10 秒でジャイロのバイアスドリフトを有界化するので、実機でも実現可能である。

| 指標（個体差あり） | v23 baseline | 2σ | v24 (3seed) | **v25 (3seed)** |
|---|---|---|---|---|
| **横ずれ率** | 8.08 ± 2.07 % | 4.15 | 12.18 | **2.88 ± 0.63 %** ✅ 2.5σ |
| **yaw 累積の個体間ばらつき** | — | — | 11.67 deg | **1.77 deg** ✅ |
| **前進速度** | 0.2231 ± 0.0060 | 0.012 | 0.2206 | **0.2386 ± 0.0079** ✅ 2.6σ |
| 膝 ROM | 33.50 ± 9.62 deg | 19.23 | 19.12 | **33.36 ± 4.20 deg** ✅ 回復 |
| トルクピーク | 87.92 ± 7.17 % | 14.33 | 88.90 | **83.75 ± 5.45 %** |
| 90%超の時間 | 0.00 % | — | 0.00 | **0.00 %** ✅ |
| トルク平均 | 18.09 ± 0.30 % | 0.61 | 17.10 | 17.79 ± 0.65 % |

**再現性そのものも大きく改善した。** seed 間の横ずれの幅は次のとおり。

| | seed 1 | seed 2 | seed 3 | 幅 |
|---|---|---|---|---|
| v24（個体差あり） | 7.36 | 10.71 | 18.46 | **11.1 pt** |
| **v25（個体差あり）** | 2.13 | 2.85 | 3.66 | **1.5 pt** |

方策が「自分がどれだけ曲がってしまったか」を観測できるようになった結果、
**学習が引き当てる解のばらつき自体が 1/7 に縮んだ**。

前進速度が 2σ を超えて改善したのは想定外の副次効果で、
**横へ逸れる分のエネルギーが前進に回った**と解釈するのが自然である。

#### この 3 版が意味すること

**v23 → v24 → v25 は、報酬を変えずに「観測できるか」だけを変えた対照実験になっている。**

| | 累積ヘディング誤差を罰する | 累積ヘディング誤差を観測できる | 横ずれ（個体差あり） |
|---|---|---|---|
| v23 | ✗ | ✗ | 8.08 % |
| v24 | ✓ | ✗ | 12.18 % |

これにより、本研究の設計則は報酬設計から観測設計へ一般化できる:

> **罰したい量は、方策が観測できなければならない。**
> 観測できない状態を罰しても、記憶を持たない方策はそれを打ち消せない。

#### 🟡 残る問題: 足裏傾き

「足の裏全体を使って歩く」という要求に対しては、悪化傾向として監視を続ける。

> ばらついた事実に鑑み追認を行ったが、v25 は 2.1〜3.7% に収まり、結論は覆らなかった。

### 4.28 測定手法の見直し（2026-08-20）— 「ばらつき」の正体を分解する

v24 の誤報を機に、**測定そのもののばらつき**を初めて測った。
同一チェックポイントを乱数種 0/1/2 で 3 回測り、その σ を「測定のばらつき」とする。

| 条件 | 学習 seed による σ（旧ノイズ床） | 測定のみの σ |
|---|---|---|
| 個体差なし | 1.89 | **0.39** |
| 個体差あり | 2.07 | **1.66** |

- **個体差なしでは、ばらつきの大半は学習 seed 由来**（測定は十分安定している）。
- **個体差ありでは、ばらつきの大半が測定由来**だった。
  個体差ありの測定は「どんな個体を引いたか」で結果が変わるため、
  旧ノイズ床 σ=2.07 は学習 seed のばらつきを過大評価していた
  （分散を分解すると、学習 seed 由来は σ ≈ √(2.07²−1.66²) ≈ 1.23）。

**再発防止として実装したもの**:
- `khr_quad_eval_metrics.py` — 測定条件を固定した計測器。全 RNG（torch/cuda/numpy/random）を
  明示シードし、`--repeats` で複数回測って平均±σ を出す。
- `khr_quad_compare.py` — ノイズ床に対する 2σ 判定を機械的に行う。
  測定ばらつきがノイズ床に匹敵する場合は判定に警告を付す。
- `experiments/noise_floor.json` — ノイズ床を正式な資産として保存。

**教訓**: 「同じ設定なら同じ結果が出る」は成り立たない。**学習 seed のばらつき**と
**測定のばらつき**は別物であり、両方を測って初めて版間比較が意味を持つ。

### 4.29 Ablation 追加（2026-08-21）— v13 の設計則そのものを検証する

§4.26 の 3 つの ablation は「**その報酬が要るか**」を問うものだった。本 ablation は
「**同じ狙いでも、測る量の取り方で結果が変わるか**」を問う。**設計則そのものを直接検証する
唯一の実験**である。

#### 設計

`_reward_feet_clearance` の**形だけ**を v1〜v12 の原典コード（絶対高さ `target_feet_height=0.06` と
足の世界座標 z を比較）に差し戻し、それ以外は v23 と完全に同一にした。

- **scale は baseline と同じ 1.0 に固定**（v12 当時は 0.2 だったが、それも変えると
  「形の効果」と「強さの効果」が混ざるため 1 要因に絞る）。
- **AST 比較で、中身が異なるメソッドが `_reward_feet_clearance` ただ一つ**であることを機械的に確認。
- baseline は v23 の 4 seed、ablation は 3 seed。

#### 結果 — 前脚の足上げ量だけが明確に低下した

| 指標（個体差あり） | baseline (4seed) | 2σ | **ablation (3seed)** | 判定 |
|---|---|---|---|---|
| **前脚の足上げ量** | 0.0191 ± 0.0009 m | 0.0018 | **0.0149 ± 0.0009 m** | ✅ **低下 (4.8σ)** |
| 後脚の足上げ量 | 0.0183 ± 0.0039 m | 0.0077 | 0.0172 ± 0.0037 m | 変化なし |
| 足裏傾き・速度・トルク・膝 ROM | — | — | — | すべて変化なし |

seed 別: baseline `[0.0181, 0.0185, 0.0196, 0.0203]` → ablation `[0.0141, 0.0144, 0.0161]`。
**baseline の最小値が ablation の最大値を上回り、範囲が重ならない。**

#### 「前脚だけ」が下がったことが、診断の正しさを裏づける

v13 の診断は「絶対高さ 0.06 m を 4 脚一律の目標にすると、**前脚（腕リンク）は立位で既に約 0.10 m
あり、上げるほど目標から遠ざかって報酬が減る＝足上げを罰する**。後脚にはその構造がない」だった。

**相対化で報酬が単に強くなっただけなら、前後とも下がるはずである。**
**前脚だけが選択的に 22% 落ちた**ことは、v13 が指摘した機構が実際に働いていた証拠になる。
さらに ablation の前脚 14.9 mm は、**v12 当時に実測された「すり足 0〜14 mm」とも整合する。**

> **正直な限界**: 副次指標がすべて 2σ 内ということは、**絶対高さ版でも歩行自体は成立する**。
> 主張は「絶対量では**前脚のクリアランスが確保できない**」に限定すべきで、
> 「絶対量では歩けない」と誇張してはならない。

### 4.30 v26 — ❌失敗。「罰の配分」と「罰の効き所」は別物だった

v25 で足裏傾きが悪化した（v23 7.77° → v25 9.97°、接地平均）ため、その 1 点に絞った版。

#### 診断（測定としては正しかった）

接地期を位相分解すると、**傾きは着地時ではなく蹴り出し時に出ている**ことが分かった。

| 版 | 接地平均 | 着地の瞬間 | 立脚前期 | 蹴り出し |
|---|---|---|---|---|
| v23 | 7.29° | 3.22° | 1.65° | 13.53° |
| v25 | 11.40° | 5.80° | 3.50° | 18.82° |

蹴り出しの符号は **+3.31°（つま先下がり）** ＝ **踵から着いてつま先で抜ける正常なロールオーバー**。

さらに罰 `tilt²` の配分を実測すると:

| 版 | 着地直前 | 立脚前期 | 立脚中期 | **蹴り出し** |
|---|---|---|---|---|
| v23 | 9.1 % | 0.8 % | 16.7 % | **73.3 %** |
| v25 | 9.8 % | 1.9 % | 18.2 % | **70.1 %** |

`tilt²` は二乗なので、傾きの大きい蹴り出し（18.8°）が着地（5.8°）の約 10 倍の重みを持つ。
**本当に平らにしたい着地には約 10% しか圧力が掛かっていなかった。**

#### 対策と、その誤り

「蹴り出しの罰を外せば着地に圧力が集中する」と考え、
`feet_orientation_pushoff_phase = 0.35`（接地中でも `leg_phase >= 0.35` は水平を要求しない）を導入した。

**結果は逆だった（3 seed）。**

| 指標（個体差あり） | v23 | v25 | **v26** | 判定 |
|---|---|---|---|---|
| **足裏傾き（着地時）** | 4.27 ± 0.99 ° | 5.80 | **8.80 ± 2.07 °** | ❌ 悪化 (4.0σ) |
| 足裏傾き（接地平均） | 7.76 ° | 9.97 | **13.59 °** | ❌ 悪化 (3.5σ) |
| **トルクピーク seed 別** | `[97.4, 83.9, 88.5, 87.3]` | `[78.7, 86.6, 87.1]` | **`[94.2, 99.4, 100.0]`** | ⚠️ **要件違反** |

**3 seed 中 2 seed が 99% 超、1 seed は 100.0% に到達した。**

> 統計的には baseline のピークのばらつきが大きく 2σ 検定では「変化なし」になるが、
> **「100% は絶対 NG」はハードな制約であり、統計的有意性とは別に守らねばならない。**
> **v26 は実機に載せてはならない。**

#### なぜ外れたのか — 本研究で最も重要な方法論上の学び

蹴り出し期の水平要求は、**着地の足裏姿勢を間接的に規定していた**。

拘束を外す → 足首が自由に回る → **蹴り出しが深くなる**（17.2° → 21.2°）
→ 深く回った足が**そのままの姿勢で遊脚に入り、傾いたまま着地する**（5.80° → 8.80°）
→ 自由になった足首で強く蹴れるため **トルクのピークが跳ね上がる**（84% → 98%）

> **「罰がどこに掛かっているか（量の配分）」と「罰がどこで効いているか（因果）」は別である。**
> 配分が偏っていること自体は、その罰が無駄である証拠にはならない。

設計則「望む結果そのものを、望む局面で測る」は v13/v16/v21/v24 で有効だったが、
**v26 はその素朴な適用が失敗した例**である。**局面を絞る前に、その局面の拘束が
他の局面に影響していないかを確認する必要がある。**
これは設計則の否定ではなく、**適用条件の発見**として記録する価値がある。

### 4.32 【方法論】学習 seed とは何か — 何を決め、何を変え、なぜ複数本回すのか

> 2026-09 の中間発表で seed について問われたため、本研究における seed の位置づけを
> コードに即して体系的に整理する。卒論の「実験手法」の節の下敷きとして書いている。

#### 4.32.1 一言でいうと

**seed は「学習中に引く乱数列の出発点」を決める唯一の値**であり、
**ロボットの物理・報酬・ハイパーパラメータは一切変えない**。
にもかかわらず PPO は確率的最適化なので、**得られる方策（歩き方）が変わる**。

#### 4.32.2 コード上の設定点は 1 か所だけ

```python
parser.add_argument("--seed", type=int, default=1)                        # khr_train_quad*.py
gs.init(backend=gs.gpu, ..., seed=args.seed, performance_mode=True)       # 唯一の設定点
```

`gs.init(seed=…)` の内部で Genesis の `set_random_seed()` が呼ばれ、**4 系統の乱数生成器**を
一括で初期化する。

```python
random.seed(seed)              # Python 標準
np.random.seed(seed)           # NumPy
torch.manual_seed(seed)        # PyTorch CPU
torch.cuda.manual_seed(seed); torch.cuda.manual_seed_all(seed)   # PyTorch GPU
```

**補足**: `rsl_rl` の `OnPolicyRunner` は独自の seed 引数を持たず、`train_cfg` にも seed は無い。
PPO 側は `gs.init` が設定した**グローバル torch RNG をそのまま継承**する。
すなわち「渡す場所は 1 つ、影響範囲は学習全体」という構造である。

#### 4.32.3 seed が決めるもの（乱数の消費者・全リスト）

`khr_quad_env19.py` を全走査して確認した、乱数を消費する 6 種類。

| # | 対象 | 実装箇所 | いつ引くか |
|---|---|---|---|
| 1 | **方策・価値関数 MLP の初期重み** | `rsl_rl` の `nn.Linear` 初期化 | 学習開始時に 1 回 |
| 2 | **PPO の行動サンプリング**（探索ノイズ） | ガウス分布からの `sample()` | 毎ステップ × 4096 環境 |
| 3 | エピソード開始位相 | `learn(init_at_random_ep_len=True)` → `torch.randint_like` | 学習開始時に 1 回 |
| 4 | 指令のリサンプル | `_resample_commands`（`gs_rand`） | 4 秒ごと＋リセット時 |
| 5 | **ドメインランダム化 4 種** | `reset_idx` 内（**毎リセットで引き直す**） | エピソードごと |
| 6 | 観測ノイズ | `gs_rand_float(-1,1,…) * obs_noise` | 毎ステップ |

**5 の内訳（v27 の実設定）**

| 対象 | 範囲 | 意味 |
|---|---|---|
| 摩擦係数 | 0.1 – 1.5 | 床の滑りやすさ |
| ベース質量 | −0.1 – +0.5 kg | 搭載物のばらつき |
| COM シフト | ±0.02 m | 重心位置の誤差 |
| **関節オフセット** | **±0.02 rad（±1.15°）× 22 関節** | **サーボ組み付け誤差＝個体差** |
| push 外乱 | 最大 1.0 m/s・3 秒間隔・方向は一様ランダム | 外力への頑健性 |

（`randomize_kp` / `randomize_kd` は False。よって `random.uniform` を使う `_randomize_kp` は
学習中に呼ばれない。）

#### 4.32.4 seed が **変えない**もの

| 変わらないもの | 理由 |
|---|---|
| URDF（リンク長・質量・慣性・可動域・定格トルク 1.373 Nm） | ファイル固定 |
| 報酬関数の定義と重み | `get_cfgs()` にハードコード、`cfgs.pkl` に保存 |
| ネットワーク構造（MLP [128,64,32] / ELU） | 同上 |
| PPO ハイパーパラメータ（lr 1e-3, γ 0.99, clip 0.2 …） | 同上 |
| 制御周期 dt=0.02（50 Hz）・PD ゲイン kp=25 / kd=0.5 | 同上 |
| 歩容周期 0.5 s・位相オフセット `[0, 0.5, 0.5, 0]` | 同上 |
| **初期姿勢** | `reset_idx` に姿勢のランダム化は**存在しない**（毎回同一姿勢から開始） |

つまり **「seed を変える」＝「まったく同じ問題を、違う乱数の引き方でもう一度解き直す」**。

#### 4.32.5 なぜ方策が変わるのか（機序）

1. PPO は**非凸な最適化問題**を解いており、局所解が多数ある。
2. 初期重みが違う → 最初に試す動きが違う → 集まる経験が違う → 勾配が違う。
3. 4096 環境の平均なので 1 ステップの揺らぎは小さいが、4000 イテレーション積み上がると軌跡が乖離する。
4. **四足歩行には対称性の破れが本質的に含まれる。** 「どちらの前脚が先に出るか」
   「どちらへ曲がる癖がつくか」は報酬から一意に決まらない。**seed がその破れ方を選ぶ。**

4 が本研究で seed の影響が大きい根本理由である。報酬は「まっすぐ歩け」としか言っておらず、
**左右どちらに崩れるかを指定していない**ため、seed ごとに別の崩れ方に収束する。

#### 4.32.6 実測: 同一設定でどれだけ変わるか

**v23 を同一設定で 4 seed 学習した結果**（`experiments/noise_floor.json`）

| 指標 | seed1 | seed2 | seed3 | seed4 | σ |
|---|---|---|---|---|---|
| **膝 ROM [°]** | 27.2 | 41.2 | 21.6 | 45.1 | **9.67** |
| **トルクピーク [%]** | **97.4** | 83.9 | 88.5 | 87.3 | 4.99 |
| 横ずれ率 [%] | 8.44 | 9.07 | 6.73 | 5.14 | 1.53 |

**膝の可動域が 21.6° と 45.1° で 2 倍違い、トルクピークは seed1 だけ 97.4% に達する。**
同じ報酬・同じ設定でこれだけ動く。

**v24 では結論そのものが逆転した**

| | seed1 | seed2 | seed3 |
|---|---|---|---|
| 横ずれ率（個体差なし）[%] | 7.65 | 12.22 | **18.99** |

seed1 だけ見れば「baseline と同等」、seed3 だけ見れば「大幅悪化」。
**単一 seed では正反対の結論が書けてしまう**（§6.10 に詳細）。

**逆に、良い設計は seed 間のばらつきも小さくなる**

| | seed1 | seed2 | seed3 | 幅 |
|---|---|---|---|---|
| v24 横ずれ（個体差あり）[%] | 7.36 | 10.71 | 18.46 | 11.1 pt |
| **v25 横ずれ（個体差あり）[%]** | 2.13 | 2.85 | 3.66 | **1.5 pt** |
| **v27 着地時の足裏傾き [°]** | 4.11 | 4.82 | 4.29 | **0.71** |

→ **seed 間のばらつきが小さいこと自体が、設計の良さの指標になる。**

#### 4.32.7 【重要】seed には 2 種類ある

本研究では性質の異なる 2 つの seed を使っている。**混同すると議論が破綻する。**

| | **① 学習 seed** | **② 測定 seed** |
|---|---|---|
| 指定場所 | `khr_train_quad*.py --seed` | `khr_quad_eval_metrics.py --repeats`（種 0/1/2） |
| 変わるもの | **方策そのもの** | **試験条件**（引く個体差・指令列・初期位相） |
| 方策は | 別物になる | **完全に同一** |
| 測っているもの | 「この設計はどんな方策を生みやすいか」 | 「同じ方策を別の条件で試すと」 |

**両者を分離して定量した**（§4.28）

| 条件 | 合計 σ（旧ノイズ床） | 測定のみの σ | → 学習 seed 由来 σ |
|---|---|---|---|
| 個体差なし | 1.89 | **0.39** | ≈1.85（**大半が学習 seed 由来**） |
| 個体差あり | 2.07 | **1.66** | ≈1.23（**大半が測定由来**） |

個体差ありでばらつきの大半が測定由来なのは、**どんな個体（関節オフセットの引き）を 8 体引いたかで
結果が変わる**ため。4 seed 各 1 回の測定から出した旧ノイズ床 σ=2.07 は、
**学習 seed のばらつきを過大評価していた**（σ² = σ²_train + σ²_meas の分解）。

#### 4.32.9 中間発表・審査での答え方

- **seed とは何か** → 4.32.1〜4.32.3。「乱数列の出発点。設定点は `gs.init` の 1 か所。
  影響するのは初期重み・行動サンプリング・指令・DR・観測ノイズ・開始位相の 6 つ」
- **何が変わらないか** → 4.32.4 を明示する。**これを先に言うと誤解が防げる。**
- **なぜ複数 seed 回すのか** → 4.32.6。「単一 seed では結論が逆転しうる。実際 v24 で誤った結論を出し、
  seed 2・3 を追加して撤回した」
- **4 seed で足りるのか** → 足りないのは自覚している。4 seed の σ 推定自体に約 35%
  （1/√(2(n−1))）の不確かさがある。ただし ablation では 4.8σ・2.9σ といった大きな効果を
  検出できており、**主張している効果量に対しては十分**。境界事例は「有意とは言えない」と明記している。
- **最良 seed を選ぶのは恣意的では** → 統計的判断には**必ず全 seed の平均±σ**を使っている。
  実機に載せる 1 つのチェックポイントを選ぶのは実装上の選択であり、結論の根拠にはしていない
  （§4.31 / `khr-quadruped27/results.md` に明記）。

### 4.33 v28 — 報酬を 27 → 18 項目に整理（中間発表の指摘への回答）

**この指摘は正しかった。** v27 の有効な報酬 27 項目のうち、ablation 済みは 4 項目だけだった。

#### 4.33.1 「寄与が小さい＝不要」ではないという罠

**罰項は、効いているほど自分の値がゼロに近づく**（方策が罰を避けるように学習するため）。

#### 4.33.3 結果 — 9 項目を外しても劣化しない

削除した 9 項目: `heading_drift`, `leg_load_balance`, `similar_to_default`, `hip_pos`,

#### 4.33.4 必須と実証された報酬

| 報酬 | 外すとどうなるか |
|---|---|
| **`feet_orientation`** | **着地時の足裏傾き 4.41 → 34.33°（30.3σ）**。v4〜v6 の「足の縁で歩く」状態に逆戻り |

#### 4.33.5 この過程で見つかった測定手法の誤り（重要）

**(a) 「トルクピーク < 90%」という安全判定は無効だった。**
同一ポリシーを体数だけ変えて測ると **8 体 85.4% → 32 体 91.5% → 128 体 94.7%** と単調に上がる。
ピークは最大値＝**極値統計**で、母数を増やせば必ず大きくなる。
一方 99%点（59.3/59.2/59.4）と 90%超の延べ時間は体数にほとんど依存しない。
→ **閾値判定には体数に依存しない統計を使う。**

**(b) 横ずれ率は 8 体では信用できない。**
評価ツールに**読み取りを 2 行足しただけ**で、横ずれが 0.996 → 3.614（263%）動いた
（トルク平均は 0.01% しか動かない）。接触物理のカオス性で float32 の丸め差が 600 ステップで
増幅される。体数を増やすと σ は 8 体 0.63 → 32 体 0.20 → **128 体 0.06** と縮む。
→ **指標ごとに必要なサンプル数が違う。**

**(c) 測定していない軸では何も言えなかった。**
全 ablation を**前進指令だけ**で測り、**転倒も歩容も見ていなかった**。
評価ツールに転倒回数と歩容一致率を追加したが、
push 外乱が `push_curriculum_steps = 50000` のため評価の 600 ステップでは
`push_scale = 0.012` ＝**実質無外乱**で測っていたことも判明した。

#### 4.33.6 副産物: 前脚（腕）が構造的な弱点

歩容一致率を前後に分解すると、**前脚 83.2% に対し後脚 87.7%** で一貫して 4〜5pt 低い。
腕を前脚として使う本機の形態上の弱点が、初めて定量的に見えた。

#### 4.33.7 方向別の検証 — 横移動 66 → 77 % という予想外の収穫

`verify_v28.sh` を cron に登録し、翌日 12:05 に自動実行した（12:15 完了、10.5 分）。
**v27 も同条件（128 体）で測り直して比較**した（以前の v27 方向別は 8 体で、体数が違うと
公平に比べられない。§4.33.5(b)）。

| 方向 | 指令値 | v27 | **v28** | 追従率 |
|---|---|---|---|---|
| 前進 (vx=+0.3) | 0.300 m/s | 0.2298 ± 0.0063 | **0.2410 ± 0.0050** | 77 % → **80 %** |
| 後退 (vx=−0.3) | 0.300 m/s | 0.2341 ± 0.0119 | **0.2462 ± 0.0038** | 78 % → **82 %** |

##### 横移動が 11pt 改善したことの意味

横移動は **v23 69 % / v25 67 % / v27 66 %** と長く停滞した弱点で、どの版でも動かなかった。
それが**報酬を 9 項目減らしただけで 66 → 77 % に改善した。**

削除した項目のうち次の 3 つは、**横移動に必要な動きを直接妨げていた**と考えられる。

| 削除した報酬 | 何を罰していたか | 横移動との衝突 |
|---|---|---|
| `similar_to_default` | 初期姿勢からの逸脱 | 横に踏み出すには姿勢を崩す必要がある |
| `hip_pos` | 脚の横開き・ねじれ | **横移動はまさに脚を横に開く動き** |
| `contact_no_vel` | 接地中の足の滑り | 横移動では足を横に滑らせる場面がある |

> **本研究で最も重要な知見のひとつ。**
> v1〜v27 は「できないこと」を 1 つずつ報酬で潰してきたが、
> **その拘束が別の能力を抑えていた。報酬を足すことには、見えないコストがある。**
>
> これは「不要な報酬を削れた」という整理の話ではなく、
> **「不要な報酬は性能を落としていた」**という積極的な主張になる。
> 中間発表の指摘（本当に効いているのか確かめられていないのでは）への回答として、
> 当初想定していたより強い結論が得られた。

#### 4.33.8 正直な限界

1. `alive` / `gait_contact` / `tracking_ang_vel` も単独では「削除可」で、全部外せば **27 → 15** だが、
   **まとめての検証はしていない。**
2. **`alive` は判定不能。** 19 秒・押し 1.0 m/s で v27 が 1 件、除去版が 2 件の転倒。区別できない。
3. 群で検証した項目は**個々まで切り分けていない。**
4. すべてシミュレーション上の結果。**実機での確認は未実施。**

#### 4.36.3 この確認で分かった、要対応の 2 点

**(1) PC からの指令が約 50 ms 遅れて効く（梶田版の元からの挙動）→ khr-getup.4 で 15〜20 ms に。**
ESP32 は受信バッファから、毎フレーム（10 ms）**一番古いパケットを 1 つだけ**読む。
いったん溜まった分は減らないので、PC の指令は 4〜5 フレーム遅れて処理される。

| 測り方 | 往復の遅れ |
|---|---|
| PC が 100 Hz で送り続ける | 中央値 61 ms（溜まり 5 パケット） |
| 受信したら即 1 つ返す | 中央値 52 ms、p99 382 ms、最大 512 ms |
| 頭ヨーの指令 → 実測角が PC に戻るまで | 112 ms |

梶田研のコンソールは ESP32 の送信に合わせて送る時刻を調整しているので、コンソール使用時にも同じだけ遅れるかは**未確認**。
方策は 50 Hz（20 ms）なので、この遅れは Sim2Real の差の候補になる。
ユーザーの了承を得て、**khr-getup.4 で、受けたあとに溜まっている通常パケットを読み捨てて最新だけを使う**ようにした。
脱力・トリム設定などの特殊コマンドは読み捨てず、読み捨てた分は梶田版のスキップ検出に数えない（単体テストで確認）。

| 測り方 | .3 まで | **.4** |
|---|---|---|
| PC が 100 Hz で送り続ける | 中央値 61 ms | **14.8 ms**（p99 34） |
| 受信したら即 1 つ返す | 中央値 52 ms、p99 382 ms | **19.9 ms**（p99 38） |

代わりに、PC のパケットが ESP32 の受信の待ち（3 ms）に間に合わないフレームが約 18 % 出る（そのフレームは前の指令を使う）。
**これにより歩行の実機条件（指令の遅れ）も v8・v19 のときから変わった**。厳密に同じ条件が必要なら `KHR_UDP_DRAIN 0`。

**(2) 重力ベクトルの更新が 100 Hz に届かない → khr-getup.3 で解決（約 100 Hz）。**

| 版 | 新しい値が届いたフレーム | 実効の更新頻度 |
|---|---|---|
| khr-getup.1 | 3.8 % | 約 4 Hz（最大 0.72 秒の空白） |
| khr-getup.2 | 20.6 % | 約 21 Hz |
| **khr-getup.3** | — | **99.8〜100 Hz** |

原因は 2 つ重なっていた。

1. **読み取り途中の値を、別のコアが読んでいた**（.2 で解決）。
   IMU スレッドの読み取り（約 6 ms）が終わる前に、メインループは最大 3 ms 待っただけで値を使っていた。
   その時点で読み取り中の変数は 0 になっている。梶田版の「Euler 角が全部 0 なら前回の値を使う」は、この症状への対処だった。
2. **個別に読むと、重力ベクトルの読み取りの約 9 割が 0 を返す**（I2C は成功したように見えて値が全部 0）。
   スレッドは毎フレーム動いている（起動時刻 [83] で確認）のに、値が得られるのは 1〜2 割だった。
   **khr-getup.3 で、加速度・ジャイロ・Euler 角・重力を 1 回の I2C 読み取り（0x08〜0x33 の 44 バイト）でまとめて取る**ように変えた。
   同じ回に、静止したまま読み取り方を切り替えて比べた（`fw_check imu-ab`、5 秒ずつ）。

   | 読み取り方 | 重力の更新 | 読み取りの失敗 |
   |---|---|---|
   | 一括（.3） | **99.8 / 100.0 Hz**（2 回） | 0 / 0.4 回/秒 |
   | 個別（梶田版と同じ＋重力） | 11.4 Hz | 88.5 回/秒（すべて「重力だけ 0」） |

   静止中の平均値は 2 つの読み方で一致した（加速度の最大差 0.002 m/s²、重力・Euler 角は差 0）。
   個別に読むと 0 になる原因そのものは特定していない（一括読み取りで回避した）。

四脚歩行のデプロイヤは、方策に入れる重力を **Euler 角 [12..13] から作っている**。
.3 では Euler 角も同じ一括読み取りから毎周更新されるので、**歩行の入力の鮮度も変わる**（値は同じ）。
改造前（v8・v19 の実機歩行）の Euler 角がどれだけ古かったかは未測定（静止していたため）。
厳密に同じ条件で歩行を比べたいときは `KHR_IMU_BURST 0` でビルドすれば梶田版と同じ読み方に戻る。

#### 4.36.4 IMU の 6 姿勢試験（1 回目 不合格 → 2 回目 合格）

脱力のままでは手足が崩れて姿勢を保てないので、全 22 サーボに電源を入れてその瞬間の関節角のまま保持し
（`real/pose_session.py`、指令とのずれが 5° を 0.3 s 超えたら全サーボ脱力）、ロボットを一体の箱として向きを変えて置いた。
記録は `experiments/real/20261013_imu_pose/`。

5 姿勢（逆さは後述の不具合で取れず）での誤差は prone 6.5° / supine 6.2° / left_down 27.5° / right_down 22.8° / upright 2.9° で、**不合格**（基準 < 3°）。
姿勢どうしのなす角から、ずれの出どころが分かった。

- 左右は、背中のケースで支えたため**仰向け側へ 20〜30° 転がっていた**（左右のなす角 129.9°、理想 180°）
- うつ伏せ・仰向けは、**どちらも頭の側が約 6° 高かった**（なす角 168.3°、直立とはどちらも 84°）
- upright・prone・supine で解くと誤差は 0.1° / 5.8° / 5.9° で、残りは置き方の傾きで説明できる。
  取り付け回転そのものはおおむね合っている見込みだが、基準での確認はまだ

**2 回目（19:25〜19:36）で合格（最大誤差 2.94°）。** 変えたのは 2 点:
ユーザーの提案で**全関節 0°（コンソールの Home と同じ初期姿勢、膝を伸ばした形）で保持**したこと
（Home は一瞬で動くが、ここでは 4 秒かけて動かした）と、胸・背中の板に**水準器**を当てて置いたこと。

| 手順 | 最大誤差 |
|---|---|
| 6 姿勢 | 4.93°（逆さ）・4.57°（うつ伏せ） |
| 逆さを取り直し | 4.27°（うつ伏せ） |
| **うつ伏せを取り直し** | **2.94°**（全 6 姿勢: 直立 1.94 / 逆さ 2.55 / うつ伏せ 2.94 / 仰向け 1.39 / 左 1.18 / 右 2.56） |

途中で「BNO055 の重力の符号が逆」という解が出たが、原因は**左右の取り違え**だった。
私の指示「左側面を下に」が向かい合った人から見た左と取られ、ロボット自身の右が下になっていた。
1 回目と左向きの値が逆向きで、直立・うつ伏せ・1 回目とはロボット自身の左右として整合するので、ラベルを入れ替えた。

**取り付け回転は 4.89°、ほぼ縦軸まわり。** これを無視すると、直立では重力の誤差 1.6° で済むが、
**四脚・うつ伏せの向きでは 4.7°（横へ約 4.6° 傾いて見える）**。起き上がりでは `gravity_base()` でこの回転を使う。
四脚歩行のデプロイヤは Euler 角と開始時のロール・ピッチのゼロ合わせを使っており、この回転は直接は入っていない。

**逆さの記録中に全サーボが脱力した（ツールの不具合）。** PC 側ツールがシーケンス番号（0〜59999）を int16 の配列に
そのまま入れていたため、保持を始めて約 5.5 分（32768 個目のパケット）で例外になって落ちた。
送信が止まったので、改造ファームの通信監視が 0.2 s で保持 → 1.2 s で全サーボ脱力に入った（**安全系は設計どおり**）。
3 つのツールで番号を uint16 として入れるよう直し、32767 以上の番号の回帰試験を足した（§6.15）。

最初の run はエピソード長 12.5 のまま学習が崩壊。`init_std` が高すぎて探索 std が

**教訓**: 「学習が全く進まない」ときはまず探索量（std）の推移を疑う。

### 6.2 後ろ倒れ四足になった理由（初期姿勢）
最初の試作は胴体ピッチ −90°＝**後ろに倒れる**四足だった。KHR には首（ピッチ）関節が
無く、頭を前に向けられないため、頭を上に保つと自然に後傾解になっていた。見た目・心理面
（「後ろ倒れはホラー」）から**前倒れ（+90°）に変更**。機能上の問題ではなく設計判断。

### 6.3 「速くしようとして遅くなる」報酬設計の罠（v2→v3）
追従判定を厳しくする（sigma を下げる）だけでは速くならない。**静止でも追従報酬の大半が
得られ、動くと罰が勝つ**なら静止が最適解になる。解決は「厳しさ」ではなく
「歩く報酬 > 歩く罰」に**バランスを組み替える**こと（tracking を上げ、動作系の罰を下げる）。

### 6.4 頑健性↔性能のトレードオフ（v5→v6）
強い外乱を最初から与えると方策が守りに入り歩行が鈍る。**カリキュラム**（まず歩行、
その後で外乱漸増）で両立。legged_gym の定番と整合。

### 6.5 報酬の副作用の連鎖（v6→v7→v8）
足裏を水平化する報酬（v7）を足したら、別の関節（hip_yaw/ankle_roll）が飽和した。
さらに調べると膝が下限にロックしていた（v8 で解明）。**一つの報酬追加が別の関節に
しわ寄せする**ため、単一指標でなく「全 22 関節のトルク duty・可動幅」を横断で監視する
必要がある。これが v8 の詳細計測（膝 ROM・duty）につながった。

### 6.6 膝の片方向可動域の見落とし（v8）
`knee_pitch` の可動域 [0.0, 2.793] は片方向。初期値 0.10 は下限の 5.7° 上に過ぎず、
主動力の膝が事実上ロックしていた。**URDF の joint limit を初期姿勢設計に織り込む**べきだった。

### 6.7 計測時の座標系ミス（v8 6 方向計測）
旋回速度を base 座標系で測ると −4% と誤って出た。胴体 90° ピッチのため
**`loco_ang_vel` を使う**必要がある（§2.1）。報酬計算だけでなく評価計測でも同じ補正が要る。

### 6.8 GPU の競合（運用上の教訓）
録画（GPU）を学習中に実行し、学習を落としたことがある。**学習中に GPU 作業を重ねない**。

### 6.9 実機ネットワークの誤診（記録）
UDP タイムアウトの原因を最初 ufw と推測したが、`ufw status` は非アクティブ＝遮断していない
（無実）。真因は **PC の IP が DHCP なのに ESP32 の `keys.h` が送信先 IP を固定**していたこと。
実機フェーズで PC の IP 固定（DHCP 予約）が必要。

### 6.10 単一 seed・単一測定で結論を出した失敗（v24 の誤報）

**v24 の初回報告で「横ずれを 7.84% → 2.53%、2.8σ で改善した」と結論したが、これは誤りだった。**

- 同じチェックポイントを測り直すと **7.49%** で、2.53% は**再現しなかった**。
  原因は測定側で、`gs.init(seed=None)` は numpy/random をシードしないため、
  **1 回きりの測定値が安定していなかった**（同一プロセス内では決定的なので気づきにくい）。
- さらに seed 2・3 で追認したところ、v24 の横ずれは seed ごとに **7.65 / 12.22 / 18.99%** と
  2.5 倍ばらついた。**seed 1 だけ見れば「baseline と同等」、seed 3 だけ見れば「大幅悪化」**と
  正反対の結論になる。

**再発防止として実装したもの**:
- `khr_quad_eval_metrics.py` に全 RNG（torch / cuda / numpy / random）の明示シードと
  `--repeats`（複数回測定して平均±σ）を実装。
- `khr_quad_compare.py` でノイズ床に対する 2σ 判定を機械化し、恣意的な解釈を排除。
- `experiments/noise_floor.json` にノイズ床を正式な資産として保存。

> **教訓**: 誤りを訂正できたのは**追認（seed 2・3）を実施したから**である。
> 追認を省いていれば、誤った結論がそのまま卒論に残っていた。

### 6.11 「罰の配分」と「罰の効き所」を混同した失敗（v26）

足裏水平の罰 `tilt²` の配分を測ると、**7 割が蹴り出し期に費やされ、着地には 1 割**しか
掛かっていなかった。**この測定自体は正しい。** 誤りは、そこから
**「だから蹴り出しの罰を外せば着地に圧力が集中する」**と推論した点にある。

実際には蹴り出し期の水平要求が**着地の足裏姿勢を間接的に規定しており**、
外した結果、着地時の傾きは 5.80° → **8.80°** と悪化し、
**トルクピークは 3 seed 中 2 seed で 99% を超え、1 seed は 100.0% に達した**（要件違反）。

> **教訓**: 「罰がどこに掛かっているか（量の配分）」と「罰がどこで効いているか（因果）」は別である。
> **配分が偏っていること自体は、その罰が無駄である証拠にはならない。**
> 局面を絞る前に、その局面の拘束が他の局面に影響していないかを確認すること。

### 6.12 統計的有意性とハードな安全要件は別（v26）

v26 のトルクピーク（97.9%）は、baseline のばらつきが大きい（±4.99）ため
**2σ 検定では「変化なし」と判定される**。しかしユーザ要件「100% は絶対 NG」は
**ハードな制約**であり、統計的有意性とは無関係に守らねばならない。

> **教訓**: 2σ 検定は「改善したと言ってよいか」の判断には有効だが、
> **安全要件の合否判定には使ってはならない**。安全は seed 別の最悪値で見る。

### 6.13 読み取り途中の値を別のコアが読んでいた（ESP32 の IMU、§4.36）

ESP32 は IMU をコア 0 のスレッドで読み、メインループ（コア 1）がその値を使う。
読み取り先の変数に直接代入していたため、読み取りの途中では値が 0 に見えることがあった。
梶田版はこれを「全部 0 なら前回の値を使う」で回避していたが、それでは**値が古いことが外から分からない**。
改造版では、読み終えた値だけを排他制御つきで渡し、通し番号で「新しい値か」を PC に知らせる。

> **教訓**: 「0 なら前回値」のような回避は、症状は消すが**データの鮮度を隠す**。
> 鮮度（通し番号・時刻）を一緒に送り、受け取る側で数えられるようにすること。

### 6.14 測定ツールの前提が実機と違った（通信監視の試験、§4.36）

通信監視の試験を最初に実機で走らせたとき、HOLD 265 ms・LIMP 1266 ms で「不合格」になった。
ファームの計時は正しく（HOLD → LIMP の間隔は 1001 ms）、ずれの正体は
**ESP32 の受信バッファに溜まったパケットの分（約 50 ms）**だった。ツールは「最後に送った時刻」を起点にしていた。
送るパケットに番号を入れ、ESP32 が返してくる番号から「ESP32 が最後のパケットを処理した時刻」を起点にしたところ、
HOLD 196〜207 ms・LIMP 1198〜1220 ms と設計どおりになった。

> **教訓**: 偽の装置（fake）で合格しても、実機の通信の性質（溜まり・遅れ）が違えば測り方が崩れる。
> 時刻の起点は「相手が実際に処理した時刻」を、相手から返してもらって取る。

### 6.15 長く動かして初めて出る桁あふれ（IMU の 6 姿勢試験、§4.36.4）

シーケンス番号は 0〜59999 だが、送る配列は int16（最大 32767）。それまでの試験はどれも数十秒で、
番号が 32768 に届かなかったので見つからなかった。全サーボに電源を入れて保持している最中（約 5.5 分）に初めて落ち、
ユーザーがロボットを逆さに持っている最中に全サーボが脱力した。ファームの通信監視が働いたので被害はなかった。

> **教訓**: 数え上げる値は「型の上限を超える値」で必ず試験する（短い試験では出ない）。
> 実機に電源を入れる道具は、想定外の例外でも必ず脱力の指令を送ってから終える作りにする。
> そして PC 側が落ちても機体側で止まる仕組み（通信監視）を先に入れておく価値は、実際に一度証明された。

同じ日のうちに、同じ型の不具合をもう 1 つ見つけた。往復遅れを測るために送る返り番号は 30000 で一巡するので、
保持が 300 秒を超えると、返ってきた番号を一巡前の送信と組んでしまい、遅れが「300 秒」と集計された（制御には影響なし）。
時刻順にたどって「その番号を最後に送った時刻」とだけ組むよう直した。

### 6.16 「左」はだれから見た左か（IMU の 6 姿勢試験、§4.36.4）

「左側面を下に」と頼んだら、向かい合った人から見た左（＝ロボット自身の右）が下になった。
左右を取り違えたデータで解くと、「センサの符号の約束が逆」というもっともらしい別の解が出る（誤差 4.9° で、一見ほぼ合格）。
1 回目のデータと向きが逆だったことで気づけた。

> **教訓**: 左右・前後の指示は「ロボット自身の」と書く。解が「符号が逆」と言ったら、まずラベルを疑う。
> 同じ量を別の回にも測っておくと、こうした取り違えを見つけられる。

### 6.17 比較用のシミュに学習用の設定が残っていた（§4.37.6）

実機と比べるための学習環境で、ドメインランダム化は切っていたが、押しの外乱（`Mode_push_vel`）だけ切り忘れていた。
新しく作った同時シミュと既存の 1 体版を突き合わせたら、3 秒（押しの間隔）までビット単位で一致し、そこから先だけずれたので気づけた。

> **教訓**: 比較用の環境は「学習用の乱れを全部切る」ではなく、切ったものを列挙して確かめる。同じ計算を 2 通りで書いて突き合わせると、こうした漏れが見つかる。

### 6.18 Genesis の摩擦は max(床, 機体)（§4.37.2）

接触の摩擦は床と機体の大きい方。床 0.5 のままだと、機体の摩擦の比率を 1 未満にしても効かない。
四脚の学習環境の摩擦のランダム化（比率 0.1〜1.5）は、実効では 0.5〜0.75 だった（計画書 F12）。起き上がりの環境では床を 0.01 にして機体側で決める。

### 6.19 結果を見てから判定の手順を足したときは、そう書く（§4.37.1）

符号の判定で 2 関節が「+1 と反転のちょうど中間」になり、平均を除いた波形の形だけで比べる手順を後から足して +1 とした。
手順を後から足すと、望む結論に寄せることができてしまう。

> **教訓**: 後から足した手順は、記録にそう明記する（`joints.json` の rule、`walk_joints.py` のコメント）。
> 本当に確かめるには、別のデータ（次の実機で 1 関節ずつ動かす）を使う。

### 6.20 学習中の成功率は、探索のゆらぎで 0 になりうる（§4.37.7）

起き上がりの成功は「全条件を 1 秒続けて満たす」で、条件に胴体の角速度 < 0.5 rad/s が入っている。学習中は行動に毎歩ゆらぎ（std 0.3）が乗るので、
角速度の条件が切れ、決定的な行動なら 33 % 成功する方策でも、学習中の記録は 0 % になった。
カリキュラムの昇格をこの学習中の成功率で判定していたので、このままでは std が十分小さくなるまで昇格しない。

> **教訓**: 「長く続ける」「静かに止まる」を含む成功の定義は、探索のゆらぎに弱い。学習中に記録する値（昇格の判定に使う値）と、
> 評価で使う値（決定的な行動）を区別し、短い試験で両方を測ってから本番を回す。
